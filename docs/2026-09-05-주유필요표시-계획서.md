## 0. 요청 원문

> 주유가 필요한 차량을 주유필요 표시할 수 있는 기능을 만들 수 있나요?
> 마지막 운전자가 일지를 작성할때 주유가 필요하다고 체크를 해두면
> 다음 운전자가 예약할때 주유 필요 안내문이 뜰 수 있게 나오면 좋을 것같습니다

## 1. 전제 도전

**진짜 문제**: 다음 운전자가 연료가 부족한 줄 모르고 출발한다. 계기판을 봐야만 알 수 있고, 그때는 이미 차에 타 있다.

**실제 결과(outcome)**: 운전자가 **차에 타기 전에** 안다. "체크박스를 만든다"는 수단이고, 이 문장이 목표다. 그래서 표시 위치가 기능의 절반이다 — 예약 시점과 운행 직전 두 곳에 보여준다.

**아무것도 안 하면 뭐가 깨지나**: 대부분은 아무 일도 없다. 계기판을 보고 주유하면 된다. 다만 **장거리 운행 직전**이거나 **주유소가 먼 분관**이면 실제로 곤란해진다. 치명적이지는 않으나 반복되는 마찰이고, 이용자가 직접 요청했다.

**대리 지표 위험**: "주유 필요 체크율"을 성과로 보면 안 된다. 체크가 적다는 건 필요가 없었다는 뜻일 수도 있다. 관측 대상은 체크 수가 아니라 **표시가 켜진 채로 운행이 시작된 횟수**(= 안내가 무시된 경우)다. 다만 이번 범위에는 계측을 넣지 않는다(§7 참고).

## 2. 기존 코드 레버리지

**핵심 발견 — 구조가 동일한 선례가 이미 있다.** 2026-09-04에 배포한 **차량 현재 위치**(`currentSiteId`) 기능이 이 요청과 데이터 흐름이 같다.

| 단계 | 차량 현재 위치 (기존) | 주유 필요 (신규) |
|---|---|---|
| 운전자 입력 | 운행일지의 `endSiteId`(차를 세운 곳) | 운행일지의 `needsRefuel` 체크 |
| 반영 주체 | **서버 트리거** `syncDriveLogKm.ts` | 같은 트리거에 추가 |
| 차량 문서 | `currentSiteId`, `currentSiteUpdatedAt` | `needsRefuel`, `needsRefuelAt` |
| 표시 | `ReservationCard`의 "○○ · 9/1 17:20 기준" | 같은 카드 + `VehicleSelector` 배지 |
| 수동 보정 | 관리자 [차량 관리] | 같음 |

그래서 **새로 설계할 것이 거의 없다.** [syncDriveLogKm.ts:200-225](../functions/src/handlers/triggers/syncDriveLogKm.ts)의 `applyVehicleCurrentSite`가 이미 갖춘 세 가지 가드를 그대로 물려받는다:

1. **기관 격리** — 차량이 그 일지의 기관 소속인지 확인 후 갱신
2. **소급 차단** — `isEffectivelyRetroactive`면 갱신하지 않음
3. **신선도 가드** — 마지막 확인 시각보다 과거의 운행은 상태를 되돌리지 않음
4. **실패 격리** — 표시 갱신 실패가 `currentKm` 회계까지 날리지 않도록 분리 실행

**배지 UI도 기존 자리가 있다.** [VehicleSelector.tsx:40-72](../src/components/common/reservation/VehicleSelector.tsx)는 이미 `정비 중`(🔧)·`지정 차량`(🔒) 배지를 그리고 있다. `주유 필요`(⛽)를 같은 자리에 얹는다.

**신규 파일은 없다.** 전부 기존 파일 편집이다.

## 3. 구현 대안과 선택

| 안 | 내용 | 노력 | 결정 |
|---|---|---|---|
| A (최소) | 체크 → 배지. 해제는 관리자 수동만 | ~4h | |
| **B (선택)** | A + 주유일지 작성 시 **자동 해제** | ~7h | **✅ 채택** |
| C (이상) | B + 연료 3단계 + 전기차 배터리 자동판정 + 알림 | ~20h+ | 미채택 |

**B를 고른 이유**: A는 해제를 사람이 해야 해서 배지가 켜진 채 방치되기 쉽다. 배지가 늘 켜져 있으면 아무도 안 본다 — 기능이 스스로를 무력화한다. 주유일지는 이미 쓰는 기관이 많으므로 자동 해제가 자연스럽다.

**다만 주유일지를 안 쓰는 기관이 있다.** 그래서 자동 해제를 넣더라도 **관리자 수동 해제 경로는 반드시 함께 남긴다**(A의 경로). 자동만 두면 그 기관들은 영영 못 끈다.

**C를 미룬 이유**: 연료 3단계는 운전자 입력 부담이 늘고, 임계값이 기관마다 달라 설정 화면까지 붙는다. 요청은 "주유 필요 여부"였지 "연료 잔량 관리"가 아니다. 규모 적합 원칙에 따라 축소한다.

## 3-1. 기관별 기능 토글 (2026-09-05 추가 결정)

이 프로젝트에는 이미 [orgFeatures](../src/lib/orgFeatures.ts)에 기관별 기능 토글이 14개 있다
(하이패스·정비·동승자·공동운전자·캘린더 등). 새 기능도 같은 방식으로 켜고 끈다.

**규칙은 두 가지다:**

| 규칙 | 적용 대상 | 의미 |
|---|---|---|
| 미설정 = **켜짐** | `hipass`, `maintenance`, `passenger` … | 플래그 도입 *이전부터* 있던 기능. 기존 기관의 화면이 바뀌면 안 되므로 |
| 미설정 = **꺼짐** (opt-in) | `reservationPassenger` | 플래그 체계가 생긴 *뒤에* 추가된 새 기능 |

**주유 필요는 opt-in(미설정 = 꺼짐)으로 한다.**

이유는 화면 변화의 크기다. `VehicleStatusSection`은 지금 **전기차가 아니고 하이패스 카드도 없으면 아무것도 그리지 않는다**. 여기에 주유 체크박스를 켜짐 기본으로 넣으면, 그 조건의 기관들에는 **없던 카드가 갑자기 생긴다**. 200곳에 예고 없이 새 입력칸이 나타나는 셈이다.

opt-in으로 두면 켜지 않은 기관의 화면은 지금과 완전히 같다. 대신 **아무도 모르는 기능이 될 위험**이 있으므로, 공지에 켜는 경로를 반드시 적는다 — [release-notes 규칙](../.agent/skills/release-notes/SKILL.md) §4가 "기관이 켜야 보이는 기능이면 그 사실이 공지의 핵심"이라고 못박고 있다.

**표시 쪽도 이 플래그로 가린다.** 기관이 나중에 기능을 끄면 이미 켜져 있던 ⛽ 배지도 함께 사라져야 한다. 다만 **서버 트리거는 플래그를 보지 않는다** — 체크박스가 보여야만 값이 저장되므로 입력 자체가 이미 걸러져 있고, 트리거가 기관 문서를 추가로 읽으면 운행일지마다 읽기가 한 번 늘어난다.

## 4. 합의된 범위

### 4.1 하는 것

**데이터**
- `vehicle` 스키마: `needsRefuel`(boolean), `needsRefuelAt`(timestamp)
- `driveLog` 스키마: `needsRefuel`(boolean)
- `organization` 스키마: `refuelFlagEnabled`(boolean) — **opt-in**(미설정 = 꺼짐)

**기관 설정**
- [설정] → [기능 사용 설정]에 토글 1개. 끄면 체크박스와 배지가 모두 사라진다

**입력**
- 운행일지 폼에 체크박스. 전기차·수소차는 문구만 **"충전 필요"**로 바꿔 동일 동작
- 위치는 `VehicleStatusSection`(배터리·하이패스가 있는 그 카드)

**반영**
- `syncDriveLogKm` 트리거가 `driveLog.needsRefuel` → `vehicle.needsRefuel` 갱신
- 새 트리거: 주유일지(`fuelLogs`) 생성 시 해당 차량의 `needsRefuel` 해제

**표시** (합의된 두 곳)
- 예약 시 **차량 선택 화면** — ⛽ 배지. **선택을 막지 않는다**(정비 중과 다름 — 안내지 차단이 아니다)
- **오늘의 예약 카드** — 운행 직전 재확인

**해제**
- 자동: 주유일지 작성
- 수동: 관리자 [차량 관리]의 차량 수정 화면 (목록 배지는 이번 범위 밖)

### 4.2 하지 않는 것 (명시적 제외)

- 연료 잔량 단계(가득/절반/부족) — C안
- 전기차 배터리 % 자동 판정 — C안
- 관리자 알림(메일·알림톡·Discord)
- 관리자 차량 관리 **목록**의 배지 (해제 UI는 수정 화면에만)
- "누가 표시했는지" 기록 — 필요해지면 후속. 개인정보를 늘리지 않는 쪽을 기본으로 둔다
- 표시가 켜진 채 운행이 시작된 횟수 계측

## 6. 가드레일

### 6.1 명명된 에러

| 상황 | 트리거 | 처리 | 사용자 영향 |
|---|---|---|---|
| 차량 문서가 다른 기관 소속 | 트리거 내 org 불일치 | `console.warn` 후 갱신 건너뜀 | 없음(표시 안 켜짐) |
| 차량 문서 갱신 실패 (UNAVAILABLE 등) | Firestore 오류 | **`currentKm` 회계와 분리 실행** — 바깥 catch로 올리지 않음 | 표시만 누락, 다음 운행이 복구 |
| 주유일지 트리거 실패 | Firestore 오류 | `captureError` 후 삼킴 | 표시가 안 꺼짐 → 관리자 수동 해제로 복구 가능 |
| 스키마에 필드 누락 | 컨버터가 조용히 제거 | 스키마부터 추가(1번 단계가 먼저인 이유) | — |

### 6.2 섀도 경로 (오늘 하이패스에서 배운 것)

**오늘 `#319`에서 정확히 이 함정에 빠졌다.** 과거 일지를 수정·소급 입력할 때 "오늘의 차량 상태"를 건드리면 안 된다. 같은 실수를 반복하지 않도록 명시한다:

- **소급 입력**(`isRetroactive`)·**과거 일지 수정**에서는 `vehicle.needsRefuel`을 갱신하지 않는다. 기존 트리거의 `isEffectivelyRetroactive` 가드를 그대로 쓴다
- 3일 전 운행에 "주유 필요"를 뒤늦게 체크해도, 그 사이 누가 주유했을 수 있으므로 지금 상태를 덮지 않는다
- **신선도 가드**: `needsRefuelAt`보다 과거의 운행은 상태를 되돌리지 않는다. 관리자가 방금 해제했는데 오전 운행이 뒤늦게 저장되어 다시 켜지는 일을 막는다
- `needsRefuel`이 `undefined`인 기존 차량 문서 → 거짓으로 취급. 마이그레이션 불필요

### 6.3 엣지케이스

- **더블 제출** — 트리거는 멱등(같은 값을 다시 써도 결과 동일)
- **두 운전자 연속 체크** — 두 번째도 참으로 유지. 문제없음
- **주유했는데 주유일지를 안 씀** — 표시가 안 꺼짐 → 관리자 수동 해제 (그래서 6번 단계가 필요하다)
- **주유일지를 과거 날짜로 작성** — 신선도 가드로 지금 상태를 건드리지 않음
- **주유일지 수정·삭제** — 표시를 다시 켜지 않는다(되돌리지 않음). 단순함을 택한다
- **정비 중 차량** — 예약 자체가 막혀 있어 충돌 없음
- **오프라인 저장** — 일지는 큐에 쌓이고, 온라인 복귀 후 트리거가 돈다. 그때는 소급 판정에 걸릴 수 있다 — **의도된 동작**이다

### 6.4 권한 (Firestore Rules)

`vehicle.needsRefuel`은 **서버 트리거와 관리자만** 쓴다. 운전자는 자기 운행일지의 `needsRefuel`만 쓰고 차량 문서는 못 건드린다. 기존 `vehicles` 규칙이 이미 관리자 쓰기로 제한돼 있으므로 **Rules 변경이 필요한지 확인만 하고**, 필요 없으면 그대로 둔다. 변경이 필요하면 `npm run test:rules:all`로 검증한다.

### 6.5 관측성

- 트리거 실패는 `captureError`로 보고 (Functions Sentry)
- 오늘 배포한 스크러빙 규칙에 맞춰 컨텍스트에는 `vehicleId`·`orgId`만 싣는다. **자유 입력을 넣지 않는다**
- 별도 대시보드·health 체크는 만들지 않는다 (규모 대비 과함)

| E2E | 넣지 않는다 — 단위로 로직이 덮이고, 표시 확인은 회귀 위험이 낮다 |
| 전체 | `verify:full` (스키마·트리거 변경이므로 큰 구조 변경으로 취급) |

**목 호출 횟수로 "동작한다"고 주장하지 않는다.** 트리거 테스트는 기존 `syncDriveLogKm.test.ts`가 쓰는 인메모리 db 하네스를 그대로 써서 **차량 문서의 최종 상태**를 단언한다.
