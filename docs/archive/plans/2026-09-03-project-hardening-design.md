# 프로젝트 안정화 설계

## 목적

2026-09-03 프로젝트 평가에서 확인한 운영·보안·테스트·성능·유지보수 위험을 우선순위에 따라 줄인다. 기능을 확장하지 않고, 현재 사용자 동작과 Firebase 데이터 모델을 보존하면서 검증 가능한 안전망을 강화한다.

## 스코프 모드

`SELECTIVE`로 진행한다. 평가에서 명시적으로 권장한 개선만 포함하고, 발견되는 인접 리팩터링이나 새 기능은 자동으로 끼워 넣지 않는다. 각 단계는 독립적으로 검증·검토할 수 있어야 하며 다음 단계의 선행 조건이 된다.

## 전제와 판단

- 실제 문제는 단순 점수 상승이 아니라 운영자가 잘못된 배포 경로를 실행하거나, 전역 평균에 가려진 중요 모듈의 회귀가 프로덕션에 들어가는 위험이다.
- 첫 로드 번들은 이미 작다. 전체 번들 크기를 사용자 다운로드량으로 오해해 무리하게 줄이지 않고, 예산 여유와 서비스워커 프리캐시만 근거로 최적화한다.
- 대형 파일은 크기만으로 분리하지 않는다. 변경 빈도, 책임 수, 테스트 가능성을 함께 보고 위험이 가장 낮은 경계부터 추출한다.
- Firebase Functions 런타임 메이저 이관은 독립 트랙으로 다룬다. 보안 취약점 해소를 위해 필요하더라도 다른 리팩터링과 한 커밋에 섞지 않는다.

## 비목표

- 새 사용자 기능, UI 재설계, Firestore 스키마·권한 체계 변경
- 로컬 `firebase deploy` 또는 프로덕션 배포
- 근거 없이 번들 예산 상향
- 커버리지 숫자만 올리기 위한 의미 없는 렌더 테스트
- 모든 대형 파일의 일괄 분리

## 단계 1: 즉시 위험 제거

### 의존성 취약점

Functions의 `qs@6.15.2`에서 보고된 moderate 취약점과 이를 포함하는 `body-parser@1.20.6`, `express@4.22.2`를 해소한다. 먼저 `npm audit`과 의존성 트리로 유입 경로를 고정하고, 다음 순서로 최소 변경안을 선택한다.

1. 현재 메이저 범위 안의 잠금 파일 갱신으로 해결되는지 확인한다.
2. 해결되지 않으면 직접 의존성의 호환 가능한 마이너·패치 갱신을 검토한다.
3. 메이저 이관만이 해법이면 `firebase-admin 14`와 `firebase-functions 7`을 한 묶음으로 올리고, 기존 유지보수 백로그에 기록된 타입 변경을 함께 처리한다.

`overrides`로 취약 하위 패키지만 강제하는 방식은 해당 상위 패키지가 새 버전을 공식 지원하고 전체 Functions 테스트·에뮬레이터 검증을 통과할 때만 사용한다.

### 배포 문서 정합성

`OPERATIONS.md`와 `ROLLBACK.md`의 일반 배포 절차를 CI 단일 경로로 통일한다. 운영 배포와 롤백은 Git 커밋·PR·CI 성공을 거쳐 Deploy 워크플로가 수행하도록 안내한다. 로컬 Firebase CLI 명령은 원본 프로젝트 운영 절차에서 제거하고, 셀프호스터 문서에만 유지한다.

긴급 복구가 필요한 경우에도 GitHub Actions의 `workflow_dispatch`를 기본 경로로 안내한다. 콘솔에서 직접 되돌리는 절차는 Hosting 트래픽 복구처럼 Git 재배포보다 빠른 경우에 한해 명확히 구분한다.

### 문서 수치 드리프트

README에 수동으로 적힌 테스트 수가 실제 테스트 목록과 어긋나지 않도록 기존 하네스 검사에 검증을 추가한다. 테스트 이름이나 실행 결과 전체를 파싱하지 않고, 저장소에서 안정적으로 계산 가능한 파일 수를 검증한다. 실행 시점에 따라 달라질 수 있는 테스트 케이스 수는 자동 생성 근거가 없으면 제거하거나 “현재 실행 결과”로 명시한다.

## 단계 2: 테스트 신뢰도 강화

### 중요 모듈 커버리지

전역 평균에 가려진 0% 모듈 중 위험도 순으로 테스트한다.

1. 암호화·서명·인증 경계: `tokenCrypto`, Slack API 경계
2. 테넌트·권한·비용 경계: OCR 호출형 함수, 통계 재계산·대시보드 집계
3. 외부 통신 경계: 메일·Gemini·캘린더 연동

각 테스트는 성공 경로보다 먼저 인증 실패, 잘못된 입력, 타 기관 접근, 외부 API 실패, 재시도·중복 실행을 검증한다. 테스트가 충분히 붙은 모듈에는 파일 또는 디렉터리별 커버리지 하한을 추가한다. 하한은 현재 실측보다 안전 여유를 둔 회귀 방지선이며 목표 수치로 사용하지 않는다.

### 테스트 출력과 종료 안정성

공통 테스트 설정에서 실제 브라우저에만 있는 API를 최소 구현으로 제공하고, 테스트가 사용하지 않는 네트워크 요청은 명시적으로 실패시키거나 모킹한다. 다음 잡음을 제거한다.

- `HTMLFormElement.requestSubmit()` 미구현 메시지
- 빈 문자열 이미지 `src` 경고
- `releaseNotes.json` 전역 fetch 미모킹
- 예상 오류 시나리오의 미검증 `console.error`·`console.warn`
- `ServiceDashboard.test.tsx` 워커 종료 타임아웃

콘솔을 무조건 숨기지 않는다. 예상 로그는 호출 내용을 단언하고, 예상하지 않은 로그는 테스트 실패로 드러나게 한다.

## 단계 3: 성능·유지보수성 개선

### 번들·서비스워커

첫 로드 예산을 최우선 지표로 유지한다. 전체 JS, CSS, 최대 청크, 서비스워커 프리캐시는 드리프트 지표로 추적한다.

- Firebase DB, Recharts, XLSX가 엔트리에 정적으로 유입되지 않는지 확인한다.
- 라우트별 동적 import가 유지되는지 번들 산출물로 검증한다.
- 서비스워커가 사용 가능성이 낮은 모든 지연 청크를 선제 캐시한다면 런타임 캐시로 전환한다.
- 최적화 전후 첫 로드, 전체 gzip, 프리캐시 바이트를 같은 환경에서 비교한다.

기능 안정성을 해치거나 초기 로드를 늘리는 최적화는 적용하지 않는다.

### 타입 예외 제거

`ServiceDashboard.tsx`의 파일 단위 `no-explicit-any` 비활성화를 제거하고, API 상태·차트 데이터에 구체 타입 또는 `unknown` 타입 가드를 적용한다. `updateAggregatedStats.ts`와 `MileageInput.tsx`의 국소 예외도 실제 필요성을 확인해 제거한다.

### 대형 파일 분리

`useAuth.tsx`, `handleAssistantMessage.ts`, `apiHealthCheck.ts`는 각각 다음 원칙을 따른다.

- 먼저 현재 동작을 고정하는 특성화 테스트를 추가한다.
- 순수 계산·응답 매핑·진단 프로브처럼 IO와 분리 가능한 책임만 추출한다.
- 공개 인터페이스와 사용자 메시지는 유지한다.
- 한 번에 한 경계만 옮기고 관련 테스트와 전체 타입 검사를 통과시킨다.

## 오류 처리와 안전장치

- 의존성 갱신 후 타입 오류가 발생하면 기존 API 계약을 유지하는 어댑터를 사용하며, 권한·테넌트 검증을 약화하지 않는다.
- 테스트 모킹은 실제 SDK 계약을 과도하게 단순화하지 않는다. 보안·동시성 경계는 가능하면 에뮬레이터 테스트를 병행한다.
- 번들 최적화로 lazy import 실패 경로가 바뀌면 기존 `lazyWithRetry` 패턴을 유지한다.
- 배포 문서 변경은 원본 운영자와 셀프호스터 절차를 구분하며, 셀프호스팅 문서의 직접 배포 예시는 보존한다.

## 검증 전략

모든 코드 변경은 Node 22에서 테스트 우선으로 진행한다.

1. 새 검증 또는 회귀 테스트를 작성하고 기대한 이유로 실패하는지 확인한다.
2. 최소 구현으로 테스트를 통과시킨다.
3. 관련 테스트를 다시 실행하고 출력에 예상하지 않은 오류·경고가 없는지 확인한다.
4. 변경 묶음마다 `verify:fast`와 필요한 Functions·Rules·빌드 검증을 실행한다.
5. 최종적으로 `verify:harness`, 커버리지, Functions 테스트, 빌드, Rules 테스트를 실행한다.

E2E와 Lighthouse는 영향을 받는 단계에서 실행한다. 프로덕션 배포는 수행하지 않는다.

## 완료 기준

- Functions `npm audit`에 high·critical이 없고, 현재 보고된 moderate 3건이 제거된다.
- 운영·롤백 문서가 CI 단일 배포 원칙과 충돌하지 않는다.
- README의 테스트 규모가 기계 검증되거나 자동으로 계산 가능한 표현으로 바뀐다.
- 선정한 보안·외부연동 모듈에 의미 있는 회귀 테스트와 국소 커버리지 하한이 생긴다.
- 프론트 단위 테스트에서 확인된 브라우저 API·fetch·빈 `src`·워커 종료 잡음이 제거된다.
- 첫 로드 번들은 기존 예산을 유지하고, 전체 번들·CSS·프리캐시 여유가 악화되지 않는다.
- 선정한 프로덕션 파일의 광범위한 ESLint 비활성화가 제거된다.
- 모든 변경 후 Git 상태와 검증 결과가 명확히 보고된다.
