- **작성일**: 2026-09-16
- **기준 커밋**: `3610faf`
- **스코프 모드**: HOLD (버그 수정 — 명시 범위에 엄격, 스코프 확장 없음)
- **절차**: [planning-scope-review](../.agent/rules/planning-scope-review.md)

## 0. 요청 원문 (두 건)

**① 전화 문의**

> 이동시간 ×2 + 1시간이 잡히는데… 이 이후에 장소를 변경한 것이 아닌가??? 라고…
> 기본이 이 설정인데, 기관 관리자 페이지에서 이 설정이 들어가지 않게 끌 수 있을까?
> 수동으로만 시간을 넣을 수 있게 한다거나 하는 거지.

**② 게시판 의견**

> 예약 수정으로 들어갈 경우 기존에 설정해놨던 예약시간이 자꾸 자동 변경이 되어 버립니다.
> 그래서 예약 장소나 다른 내용을 수정하기 위해 수정에 들어간건데 시간이 자동 변경된 걸
> 미처 확인하지 못하고 완료를 해버리는 경우가 종종 발생합니다.

## 1. 전제 도전

**진짜 문제**: 사용자가 정한 종료시간이 **본인 모르게 다른 값으로 바뀐 채 저장**된다.

**증상이 아니라 결과로 적으면**: 예약을 수정하러 들어갔다 나온 사람의 **시간이 들어갈 때와 같다.** "자동 계산을 끈다"는 수단이고 이 문장이 목표다.

**두 신고는 한 자리다.** ②는 명시적으로 수정 화면을 말한다. ①의 *"이 이후에 장소를 변경한 것이 아닌가"*도 같은 의심이다 — 종료시간을 맞춰 놔도 목적지를 바꾸거나 경로 조회가 늦게 끝나면 다시 덮인다. 두 분이 같은 코드 한 줄을 서로 다른 각도에서 보신 것이다.

**신고자가 제안한 해법(기관 설정으로 끄기)을 그대로 받지 않는 이유**: 설정을 달아도 **켜지 않은 나머지 기관은 그대로 당한다.** 기본값이 깨져 있는데 옆에 스위치를 놓는 모양이다. 그리고 켠 기관은 편의 기능 자체를 잃는다(매번 손으로 종료시간 입력). 요청은 "시간이 안 바뀌게 해 달라"로 읽고, 설정은 이 수정 뒤에도 요청이 남으면 그때 판단한다.

**아무것도 안 하면 뭐가 깨지나**: 예약 수정을 쓰는 모든 기관에서 계속 깨진다. ②의 *"종종 발생합니다"*가 이미 반복 피해를 말하고 있다. 특히 **다일 예약**은 조용히 뭉개진다(§2.3).

**대리 지표 위험**: "자동 계산 사용률"을 성과로 보면 안 된다. 관측 대상은 **사용자가 정한 종료시간이 저장 때까지 유지되는가**이고, 고치고 나면 항상 유지되어야 한다. 이번 범위에 계측은 넣지 않는다.

## 2. 원인 (코드 확인 결과)

### 2.1 덮어쓰는 자리는 하나다

[useRouteInfo.ts:97-103](../src/hooks/reservationCalendar/useRouteInfo.ts):

```ts
useEffect(() => {
    if (form.startTime && routeInfo?.duration) {
        const autoEnd = calcEndTime(form.startTime, routeInfo.duration);
        setForm(prev => ({ ...prev, endTime: autoEnd }));
    }
}, [form.startTime, routeInfo?.duration]);
```

`routeInfo.duration`이 **도착할 때마다** 무조건 덮는다. 사용자가 그 칸을 직접 채웠는지, 수정 모드인지 보지 않는다.

`editingReservation`은 [useReservationCalendar.ts:30](../src/hooks/useReservationCalendar.ts)에 있지만 [:58](../src/hooks/useReservationCalendar.ts)에서 `useRouteInfo`에 **넘기지 않는다.** 훅은 수정 모드의 존재를 모른다.

### 2.2 수정 화면을 열기만 해도 도는 경로

[editActions.ts:23-105](../src/hooks/reservationCalendar/actions/editActions.ts)의 `handleEdit`이 단건·다일·반복 세 갈래 모두 `endTime`을 **저장된 값**으로 채운다. 그 직후:

1. 목적지·차량이 이미 채워져 있으므로 [useRouteInfo.ts:35](../src/hooks/reservationCalendar/useRouteInfo.ts)의 경로 조회 effect가 돈다
2. 1.2초 디바운스 뒤 TMAP 결과 → `setRouteInfo(...)`
3. `duration`이 바뀌었으므로 §2.1 effect가 돌아 **저장돼 있던 종료시간을 덮는다**

사용자는 목적지만 고치러 들어왔는데 시간 칸이 바뀐다. **화면에 아무 안내도 없다.**

### 2.3 다일 예약은 더 나쁘게 깨진다

`handleEdit`의 다일 갈래는 `endTime: last.endTime` — **마지막 날의 종료시간**을 넣는다([editActions.ts:84](../src/hooks/reservationCalendar/actions/editActions.ts)). 그런데 덮어쓰기는 `form.startTime`(**첫날 시작**) 기준으로 계산한다. 3일짜리 예약을 열면 마지막 날 18:00이 첫날 11:40 같은 값으로 뭉개진다.

> ⚠️ **구현 중 정정(머지 전 리뷰)**: 처음에는 여기에 *"저장하면 예약 기간 자체가 줄어든다"*고 썼는데 **틀렸다.** 일수는 `form.endDate`가 정하고(`submitActions`의 `eachDayOfInterval`) 덮어쓰기는 `form.endTime` 한 칸만 바꾼다. 3일은 3일로 남고 **마지막 날 반납 시각만** 뭉개진다. 피해는 실재하지만(그 시각 뒤로 남이 예약할 수 있게 된다) 공지에 쓴 문장은 과장이었다. 실제로 하루짜리가 되는 경로는 **종료일 입력의 빈 값 가드 부재**였고, 그쪽도 함께 막았다.

### 2.4 이전 조회 결과가 남아 즉시 덮는 경로도 있다

`routeInfo`는 `useRouteInfo`의 state이고 `useReservationCalendar`가 떠 있는 동안 산다. 목적지·차량이 바뀔 때 [:53](../src/hooks/reservationCalendar/useRouteInfo.ts)은 `setFreeRoadRoute(null)`만 하고 **`setRouteInfo(null)`은 목적지가 빈 경우에만** 한다. 그래서 신규 폼에서 경로를 한 번 조회한 뒤 수정 화면을 열면, 새 조회가 끝나기 전에 **옛 목적지의 소요시간**으로 한 번 덮고 1.2초 뒤 또 덮는다.

### 2.5 덮지 않는 자리 하나 — 여기는 타당하다

[ReservationSidePanel.tsx:363-369](../src/components/common/ReservationSidePanel.tsx)는 **사용자가 시작시간을 바꿀 때** 종료시간을 다시 계산한다. 명시적 행동에 대한 반응이라 이번 범위에서 성질을 바꾸지 않는다(단 §3-1의 규칙은 적용한다).

## 3. 구현 대안과 선택

| 안 | 내용 | 노력 | 결정 |
|---|---|---|---|
| A1 (최소) | 사람이 정한 종료시간은 덮지 않는다. UI 추가 없음 | ~2h | |
| **A2 (선택)** | A1 + 경로가 바뀌면 **덮는 대신 제안 줄**을 띄운다 | ~4h | **✅ 권고** |
| A3 (이상) | A2 + 다일/반복 종료시간 의미 정리 + 기관 설정 토글 | ~12h+ | 미채택 |

**A1만으로 부족한 이유**: 목적지를 멀리 바꿨을 때 편의가 사라진다. 지금은 자동으로 맞춰 주던 것이 침묵이 된다 — 사용자가 종료시간을 스스로 계산해야 한다. 다만 **손해는 크지 않다**(원래 손으로 고칠 수 있는 칸이다). 예산이 빠듯하면 A1으로 줄여도 두 신고는 해결된다.

**A3를 미룬 이유**: 다일 예약의 종료시간이 "마지막 날 종료"라는 의미는 폼·검증·저장·캘린더 동기화에 얽혀 있어 손대면 범위가 커진다. 기관 설정은 §1에서 적은 이유로 뺀다. 규모 적합 원칙(CLAUDE.md)에 따라 축소한다.

### 3-1. 규칙은 하나다 — "사람이 정한 값은 덮지 않는다"

`endTimeTouched` 플래그 하나로 전부 판정한다. 갈래를 늘리지 않는 것이 핵심이다.

| 시점 | touched | 근거 |
|---|---|---|
| `handleEdit` 진입 | **true** | 저장된 값은 사람이 정한 값이다 |
| 사용자가 종료시간 칸을 직접 입력 | **true** | 명시적 행동 |
| 폼 리셋(`resetFormState`) | false | 새로 시작한다 |
| 자동 계산으로 채운 직후 | false | 우리가 넣은 값이다 |

동작:

| 상황 | touched=false | touched=true |
|---|---|---|
| 경로 소요시간 도착·변경 | 자동으로 채운다(지금과 같다) | **덮지 않는다.** 제안 줄을 띄운다 |
| 사용자가 시작시간 변경 | 자동으로 다시 계산 | **덮지 않는다.** 제안 줄을 띄운다 |

> 시작시간을 바꿨을 때도 touched면 덮지 않는 이유: `09:00~18:00`(종일)을 잡아 둔 사람이 시작을 10:00으로 옮겼다고 해서 18:00을 버릴 이유가 없다. 바꾸고 싶으면 제안 줄을 누르면 된다.

### 3-2. 제안 줄 (A2)

운행 시간 입력 바로 아래 한 줄:

> 🕒 경로 기준 예상 종료 **15:40** · [적용]

- **계산값이 지금 종료시간과 다를 때만** 띄운다(같으면 보여 줄 것이 없다)
- [적용]을 누르면 그 값을 넣는다. touched는 **true로 유지**한다(사람이 고른 것이다)
- `routeInfo`가 없거나 조회 중이면 띄우지 않는다
- **다일 예약에서는 띄우지 않는다** — §2.3의 이유로 계산값과 칸의 의미가 다르다. 잘못된 제안은 침묵보다 나쁘다
- ⚠️ **구현 중 정정**: 처음에는 반복 예약도 함께 뺐으나 근거가 틀렸다. 반복은 회차마다 그날 안에 끝나므로(`date`·`startTime`·`endTime`이 단건과 같다) 제외할 이유가 없다

### 3-3. §2.4를 함께 고친다

경로 파라미터(목적지·차량)가 바뀌면 조회를 시작할 때 `setRouteInfo(null)`로 비운다. 안 그러면 **제안 줄이 옛 목적지 기준 값을 권한다** — A2에서는 덮어쓰기보다 더 나쁜 오정보가 된다. 덮어쓰기를 없애는 것만으로는 이 구멍이 닫히지 않으므로 같은 범위에서 처리한다.

## 4. 비목표 (건드리지 않는 것)

- **`calcEndTime`의 공식(이동시간 ×2 + 여유 1시간)** — 신고 내용이 아니다. 기본값이 마음에 안 든다는 요청이 따로 오면 그때 본다
- **기관 설정 토글** — §1의 이유
- **`useQuickDriveStart`의 `calcEndTime` 사용**([:269](../src/hooks/useQuickDriveStart.ts)) — 바로 운행에는 사람이 정해 둔 종료시간이 없다. 덮을 것이 없으므로 대상이 아니다
- **다일 예약 `endTime`의 의미 정리** — §3의 A3. 미룬다
- **이미 저장된 예약** — 잘못 저장된 시간이 있어도 우리가 추측으로 고치지 않는다. 무엇이 원래 값이었는지 알 수 없다

## 6. 가드레일

### 6-1. 명명된 실패

| 상황 | 지금 | 이후 |
|---|---|---|
| TMAP 조회 실패·미설정 | `routeInfo=null` → 덮지 않음 | 같다. 제안 줄도 안 뜬다 |
| 경로 조회 중 사용자가 목적지를 또 바꿈 | 옛 결과로 덮을 수 있음(§2.4) | `routeInfo` 초기화로 옛 값이 제안되지 않는다 |
| `duration=0`(같은 주소 등) | `+1시간`만 더해 덮음 | touched면 안 덮는다. 제안값이 현재와 같으면 줄도 안 뜬다 |

### 6-2. 섀도 경로 / 엣지케이스

- **수정 → 취소 → 다시 신규 작성**: `resetFormState`에서 touched=false. 안 내리면 신규 폼에서 자동 계산이 영영 안 돈다 — **이번 변경의 가장 큰 회귀 위험**이고 테스트로 못 박는다
- **즐겨찾기 불러오기**: 목적지만 채운다. touched에 영향 없음(확인 완료)
- **반복 → 단건 전환, 다일 → 단건 전환**: 폼이 유지된 채 모드만 바뀐다. touched는 그대로 둔다(사용자가 정한 값이라는 사실이 바뀌지 않는다)
- **느린 연결**: 디바운스 1.2초 + TMAP 응답. 그 사이 저장하면 제안 줄 없이 저장된다 — 사용자가 정한 값이 나가므로 안전한 쪽이다
- **더블클릭 [적용]**: 같은 값을 두 번 넣을 뿐, 부작용 없음

### 6-3. 관측성

Sentry 이벤트는 새로 만들지 않는다. **조용히 안 하게 되는 변경**이라 잡을 예외가 없다. 대신 계약을 단위 테스트로 고정한다(§5).

## 7. 검증 계획

- `useRouteInfo` 신규 spec: touched=false면 채운다 / touched=true면 안 채운다 / 경로 변경 시 옛 routeInfo가 남지 않는다 / 제안값 계산
- 수정 진입 시 저장된 종료시간이 유지되는지(세 갈래 전부 — 단건·다일·반복)
- 리셋 후 신규 작성에서 자동 계산이 **다시 돈다**(§6-2의 회귀)
- lint · type-check · 빌드 · `check:release-notes` · `check:faq`
- Rules·Functions는 돌리지 않는다 — 프런트 폼 경로만 바뀌고 서버·권한·스키마는 그대로다

## 8. 남을 것 (미룬 작업 — 기록해 둔다)

1. **다일 예약의 `endTime` 의미**(첫날 기준 vs 마지막 날)가 폼 한 칸에 섞여 있다 — A3
2. **`이동시간 ×2 + 1시간` 공식**은 그대로다. 기관별로 맞지 않는다는 요청이 다시 오면 그때 설정을 판단한다(신고 ①에 되물어 확인 필요)
3. **이미 잘못 저장된 예약**은 고치지 않는다
