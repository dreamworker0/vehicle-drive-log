## 1. 전제 도전

**진짜 문제**: 다음 운전자가 **차를 찾지 못한다.** 비고가 안 보이는 것은 증상이고, 결과(outcome)는 "차를 가지러 가는 사람이 출발 전에 어디 세워져 있는지 안다"다.

**그래서 표시 위치가 기능의 전부다.** 그리고 여기에 함정이 하나 있다:

> **운행일지 작성 폼은 운행이 *끝난 뒤* 여는 화면이다.**
> 예약 → [운행 시작] → 도착 → 일지 작성 순서이므로, "직전 운전 정보" 배너에 비고를 띄워도
> **차를 찾으러 갈 때는 이미 차 안에 있다.** 이 화면만으로는 민원이 해결되지 않는다.

차를 가지러 가기 **직전**에 사람이 실제로 보는 화면은 [오늘의 예약 카드](../src/components/employee/ReservationCard.tsx)다. 위치 배지(🚩)와 주유 필요 배지(⛽)를 그 자리에 둔 것도 같은 이유였다.

**아무것도 안 하면 뭐가 깨지나**: 본관 주차장을 쓰는 대다수 기관은 아무 일도 없다. 차고지가 외부 주차타워·이면도로인 기관에서만, 다음 운전자가 층·구역을 몰라 헤맨다. 치명적이지 않으나 매 운행마다 반복되고, 이용 기관이 직접 요청했다.

**대리 지표 위험**: "비고 작성률"을 성과로 보면 안 된다. 비고를 적을 일이 없으면 안 적는 게 정상이다. 관측 대상은 굳이 꼽자면 **비고가 있는 차량의 예약 카드가 열린 횟수**인데, 이번 범위에 계측은 넣지 않는다(규모 대비 과함).

## 2. 기존 코드 레버리지

**선례가 둘이나 있고, 둘 다 데이터 흐름이 같다.** 차량 현재 위치(`currentSiteId`, 2026-09-04)와 주유 필요 표시(`needsRefuel`, 2026-09-05)다.

| 단계 | 현재 위치 (기존) | 주유 필요 (기존) | 직전 비고 (신규) |
|---|---|---|---|
| 운전자 입력 | 일지의 `endSiteId` | 일지의 `needsRefuel` | **일지의 `notes` — 이미 있다** |
| 반영 주체 | `syncDriveLogKm` 트리거 | 같은 트리거 | 같은 트리거 |
| 차량 문서 | `currentSiteId`/`...UpdatedAt` | `needsRefuel`/`needsRefuelAt` | `lastDriveNote`/`...At`/`...By` |
| 표시 | 예약 카드 🚩 배지 | 예약 카드 + 차량 선택 ⛽ 배지 | 예약 카드 📝 한 줄 |

**입력 쪽은 만들 것이 없다.** 새 체크박스도, 새 입력칸도, 새 일지 필드도 없다 — 운전자는 지금 하던 대로 비고를 적는다. 이번 작업은 **표시만** 붙인다.

[syncDriveLogKm.ts:220-290](../functions/src/handlers/triggers/syncDriveLogKm.ts)의 `applyVehicleCurrentSite`·`applyVehicleNeedsRefuel`이 갖춘 가드를 그대로 물려받는다:

1. **기관 격리** — 차량이 그 일지의 기관 소속인지 확인 후 갱신
2. **소급 차단** — `isEffectivelyRetroactive`면 갱신하지 않음
3. **신선도 가드** — 마지막 갱신 시각보다 과거의 운행은 상태를 되돌리지 않음
4. **실패 격리** — `...Safely` 래퍼로 표시 갱신 실패가 `currentKm` 회계를 날리지 않게 분리

호출 지점도 이미 `onDriveLogCreated`(404행)·`onDriveLogUpdated`(514행) 두 곳에 나란히 있다. 한 줄씩 추가하면 된다.

**신규 파일은 없다.** 전부 기존 파일 편집이다.

## 3. 구현 대안과 선택

| 안 | 내용 | 노력 | 결정 |
|---|---|---|---|
| A (최소) | 차량 이용 내역에 비고 한 줄만 추가 | ~1.5h | |
| **B (선택)** | A + **오늘의 예약 카드**에 직전 비고 + 운행일지 폼 배너에 비고 | ~6.5h | **✅ 권고** |
| C (이상) | B + "세운 위치" 전용 자유입력 필드 + 기관 토글 + 관리자 편집 | ~14h+ | 미채택 |

**A를 단독으로 쓰지 않는 이유**: 민원 문구는 그대로 해소되지만(그 화면에서 비고가 보인다), 차를 가지러 가는 사람이 **[더보기 → 차량 이용 내역]에 일부러 들어가야** 한다. 지금도 그 경로를 몰라서 못 본 게 아니라 들어가도 없어서 못 본 것이므로, A만으로는 "출발 전에 안다"가 성립하지 않는다. 다만 **A는 B에 통째로 포함**되고, 혼자서도 배포 가능한 최소 단위다.

**C를 미룬 이유**: 전용 필드를 만들면 입력 부담이 늘고(비고와 위치 칸이 둘로 나뉜다), 기관 토글·관리자 편집·마이그레이션이 줄줄이 붙는다. 그런데 이 기관은 **이미 비고에 적고 있다** — 없는 것은 입력 수단이 아니라 표시다. 규모 적합 원칙(CLAUDE.md 작업 스타일)에 따라 축소한다. 비고 표시가 실제로 쓰이는지 본 뒤에 판단해도 늦지 않다.

### 3-1. 예약 카드에 직전 비고를 싣는 두 방식

| 방식 | 읽기 비용 | 판단 |
|---|---|---|
| (a) 클라이언트가 차량별 직전 일지 조회 | 예약 카드마다 Firestore 읽기 +1 | 오늘의 대시보드는 전 운전자가 매일 여는 화면이다. 표시 하나에 상시 읽기를 붙인다 |
| **(b) 차량 문서에 비정규화** | **+0** — `vehicles`는 이미 로드돼 있다 | **✅ 채택** |

(b)는 선례 둘과 완전히 같은 구조이고, 트리거가 이미 같은 차량 문서를 `update`하고 있어 **쓰기도 늘지 않는다**(같은 update에 필드 세 개 추가).

**권한 범위 변화 없음 — 확인함.** [firestore.rules:239](../firestore.rules)의 `vehicles` 읽기는 `belongsToMyOrg() || isSuperAdmin()`으로 [:309](../firestore.rules)의 `driveLogs` 읽기와 **동일**하다. 비고 원문이 차량 문서로 복사돼도 볼 수 있는 사람이 늘지 않는다.

### 3-2. 기관별 토글을 두지 않는다

주유 필요 표시는 opt-in 토글을 달았다. **없던 입력 카드가 200곳에 갑자기 생기기 때문**이었다. 이번은 다르다:

- 새 입력칸이 생기지 않는다 — 비고는 원래 있던 칸이다
- 예약 카드·차량 이용 내역에 **비고를 적은 기관에서만** 한 줄이 늘어난다. 안 적는 기관의 화면은 지금과 같다
- 토글로 만들면 켜는 기관이 거의 없어 민원이 그대로 남는다

**대신 노출 범위가 바뀌는 것은 사실이므로 공지로 다룬다**(§8). 지금까지 비고는 본인과 관리자만 봤고, 앞으로는 같은 기관 운전자가 본다. 사회복지기관 특성상 비고에 이용자 성함이 적혀 있을 수 있다 — 다만 **목적·행선지는 이미 차량 이용 내역에 전부 노출**되고 있으므로 증분은 크지 않다. 비고 입력칸에 공개 범위 안내 한 줄을 넣는 것을 범위에 포함한다.

**표시 (세 곳)**

**안내**
- 비고 입력칸 하단에 공개 범위 한 줄 (예: "같은 기관 이용자에게 함께 보입니다")

## 6. 가드레일

### 6.1 명명된 에러

| 상황 | 트리거 | 처리 | 사용자 영향 |
|---|---|---|---|
| 차량 문서가 다른 기관 소속 | 트리거 내 org 불일치 | `console.warn` 후 건너뜀 | 없음(비고 안 뜸) |
| 차량 문서 갱신 실패 | Firestore 오류 | `...Safely` 래퍼로 삼킴 — `currentKm` 회계와 분리 | 비고만 누락, 다음 운행이 복구 |
| 비고 필드가 없는 기존 차량 | 필드 미존재 | 없는 것으로 취급, 표시 안 함 | 마이그레이션 불필요 |
| 스키마 누락 | 컨버터가 조용히 제거 | 1번 단계를 먼저 하는 이유 | — |

### 6.2 섀도 경로

- **소급 입력·과거 일지 수정** — `isEffectivelyRetroactive`면 갱신하지 않는다. 3일 전 운행의 "3층 B-12"가 오늘 위치를 덮으면 헛걸음이 된다
- **신선도 가드** — `lastDriveNoteAt`보다 과거의 운행은 값을 되돌리지 않는다
- **비고를 지운 수정** — 빈 문자열로 갱신(= 차량에서 제거). 소급·신선도 가드는 동일하게 적용
- **일지 삭제** — `onDriveLogDeleted`는 건드리지 않는다. 현재 위치·주유 표시와 같은 한계이며, 다음 운행이 덮어쓴다. **14일 신선도 컷이 이 구멍의 실질적 마개다**
- **일지 보존기간 만료** — `driveLogRetentionCutoff`로 일지가 정리돼도 차량 문서의 사본은 남는다. 장기 미운행 차량에서만 발생하고, 14일 컷 때문에 화면에는 나오지 않는다

### 6.3 엣지케이스

- **오래된 비고** — 예약 카드는 **14일 지나면 띄우지 않는다.** 2주 전 주차 위치는 정보가 아니라 오정보다. 차량 이용 내역은 기록 조회 화면이므로 컷 없이 전부 보인다
- **긴 비고** — 예약 카드 1줄 말줄임(`line-clamp-1`), 배너 2줄, 차량 이용 내역 전문
- **줄바꿈이 섞인 비고** — 카드·배너에서는 공백으로 접어 한 줄로 본다
- **더블 제출** — 트리거는 멱등(같은 값을 다시 써도 결과 동일)
- **오프라인 작성** — 큐에 쌓였다가 온라인 복귀 후 트리거가 돈다. 그때 소급 판정에 걸릴 수 있다 — **의도된 동작**
- **차량 미배정 예약** — `vehicle`이 없으면 줄 자체를 그리지 않는다
- **XSS** — React가 이스케이프한다. PDF 경로는 기존 `escapeHtml`을 이미 통과한다(변경 없음)

### 6.4 권한 (Firestore Rules)

**변경 없음 — 확인 완료.** `vehicles` 읽기와 `driveLogs` 읽기가 모두 `belongsToMyOrg()`라 노출 범위가 같다. 쓰기는 서버 트리거(Admin SDK)와 관리자만 하고, 운전자 쪽 규칙([firestore.rules:249](../firestore.rules))은 `currentKm`만 쓰도록 `hasOnly`로 묶여 있어 `lastDriveNote`를 조작할 수 없다. **규칙 파일은 손대지 않는다.**

### 6.5 관측성

- 트리거 실패는 `captureError`(Functions Sentry)
- **Sentry 컨텍스트에 비고 본문을 싣지 않는다.** `vehicleId`·`orgId`만. 비고는 [sentryScrub](../src/lib/sentryScrub.ts)이 이미 민감 자유입력으로 다루는 값이다
- 별도 health 체크·대시보드는 만들지 않는다

## 7. 검증 계획

| 항목 | 범위 |
|---|---|
| 단위 (Functions) | 트리거 5종 — 정상 반영 / 빈 비고로 제거 / 소급 무시 / 신선도 역전 / 타 기관 차단 |
| 단위 (프론트) | 예약 카드 — 14일 이내 표시 · 15일 이전 미표시 · 비고 없으면 줄 없음 |
| 단위 (프론트) | 차량 이용 내역 — 비고 있는 기록에만 줄이 붙는다 |
| Rules | **불필요** (규칙 변경 없음) |
| E2E | 넣지 않는다 — 표시 전용이고 단위로 덮인다 |
| 전체 | `verify:full` (스키마·트리거 변경이므로 큰 구조 변경으로 취급) |

트리거 테스트는 기존 `syncDriveLogKm.test.ts`의 인메모리 db 하네스를 그대로 써서 **차량 문서의 최종 상태**를 단언한다. 목 호출 횟수로 "동작한다"고 주장하지 않는다.
