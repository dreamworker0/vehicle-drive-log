## 발견 1 — 승인된 예약을 '수정'하면 날짜·시간·차량을 마음대로 바꿔도 승인 상태가 유지된다

- **심각도**: HIGH
- **확신도**: 9/10 — Rules 에뮬레이터 PoC로 실행 확인. 정상 화면 경로에서도 같은 결과가 나는 것을 코드로 추적했다
- **상태**: VERIFIED
- **카테고리**: 멀티테넌트(A01) — 기관 내 역할 경계(승인권·차량 사용 제한) 우회

### 근거

2026-07-10 감사 #5에서 예약 **생성**을 콜러블 전용으로 잠갔다. 생성 시 서버가 강제하는 정책은 이렇다([createReservationCore.ts](../../functions/src/services/reservation/createReservationCore.ts)):

- 승인제 기관이면 `status: "pending"`(:315)
- 차량 사용 가능 직원 제한 `allowedUserIds`(:219–225)
- 정비 중 차량 차단(:215)
- 같은 차량·같은 명의자 시간 겹침
- (현재 브랜치) 승인제 + 바로 운행 끔이면 거부(:236)

그런데 **수정**은 여전히 클라이언트가 Firestore에 직접 쓴다. Rules의 소유자 update 분기는 세 가지만 본다. [firestore.rules:357](../../firestore.rules)

```
(resource.data.reservedByUid == request.auth.uid
    && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['organizationId', 'reservedByUid'])
    && !(resource.data.status == 'pending' && request.resource.data.status == 'reserved'))
```

즉 `vehicleId`·`date`·`startTime`·`endTime`은 자유롭게 바뀌고, `status`가 이미 `reserved`라면 **그대로 남는다.**

이것은 SDK를 직접 쓰는 공격자만의 문제가 아니다. 앱의 예약 수정 화면이 바로 이 경로를 쓴다. [submitActions.ts:398](../../src/hooks/reservationCalendar/actions/submitActions.ts)

```ts
await updateReservation(editingReservation.id, {
    ...baseData,          // vehicleId 포함 (:45)
    ...passengersForUpdate,
    startTime: form.startTime,
    endTime: form.endTime,
});
```

`baseData`에는 `status`가 없으므로 승인된 예약을 고쳐도 상태는 `reserved`로 남는다. 클라이언트 쪽에 `requireReservationApproval`을 참조하는 코드는 설정 화면 말고는 없다. 차량 사용 제한은 화면에서만 검사한다(`isVehicleRestrictedForUser`, 같은 파일 :17).

사후 방어도 빈틈이 있다. 수정 트리거의 겹침 검사는 **시간·상태 변경에만** 반응하고 **차량 변경은 보지 않는다.** [reservationTriggers.ts:223](../../functions/src/handlers/triggers/reservationTriggers.ts)

```ts
const timeChanged = before.date !== after.date || before.startTime !== after.startTime || before.endTime !== after.endTime || before.status !== after.status;
```

### 실행으로 확인한 것

임시 Rules PoC(에뮬레이터, 테스트 후 삭제). `user_A`(employee) 소유의 `reserved` 예약을 **사용 제한이 걸린 다른 차량, 다른 날짜, 종일**로 바꿨다:

```
update({ vehicleId: 'v_restricted', date: '2026-12-24', startTime: '00:00', endTime: '23:59' })

```

### 익스플로잇 시나리오

1. 승인제(`requireReservationApproval`)를 켠 기관의 평직원이 평일 1시간짜리 예약을 신청한다 → 관리자가 승인(`reserved`).
2. 직원이 **예약 수정** 화면에서 그 예약을 연휴 종일, 다른 차량으로 바꾼다. SDK가 필요 없다 — 정상 화면이다.
3. 상태는 `reserved` 그대로이고 관리자 승인 대기 목록(`status == 'pending'` 조회)에 나타나지 않는다. 관리자는 바뀐 사실을 알기 어렵다.
4. SDK를 쓰면 화면이 막는 것까지 넘는다: `allowedUserIds`로 특정 직원에게만 허용된 차량, 정비로 막힌 차량을 지정할 수 있고, 차량만 바꾸면 트리거의 겹침 검사도 돌지 않아 **다른 사람의 확정 예약과 겹친 이중 예약**이 생긴다.

테넌트 경계는 넘지 않는다(`belongsToMyOrg`, `organizationId` 불변, 트리거의 차량-기관 대조가 살아 있다). 그러나 **승인제·차량 사용 제한은 기관이 직원에게 거는 통제 그 자체**라, 이 둘이 수정 한 번에 풀리는 것은 역할 경계 위반이다. 현재 브랜치가 추가하는 "바로 운행 끔"도 같은 승인제 위에 서 있어 효과가 반감된다.

### 권고 조치

생성에서 했던 것을 수정에도 한다 — **정책을 바꾸는 필드는 서버만 쓴다.**

1. **Rules**: 소유자 분기에서 `vehicleId`·`date`·`startTime`·`endTime`(및 `groupId`·`recurringGroupId`·`isQuickDrive`) 변경을 금지한다. 소유자는 취소·운행 종료·목적지/목적/동승자 같은 정보 수정만 남긴다. 관리자 분기는 그대로 둔다.
2. **콜러블 신설**(`modifyReservationSafe`): 이미 있는 [modifyReservationCore.ts](../../functions/src/services/reservation/modifyReservationCore.ts)(메신저 어시스턴트용, 조직·소유자·상태·겹침 검사 보유)를 확장해 차량 변경 시 `allowedUserIds`·정비 검사를 추가하고, **승인제 기관이면 일정·차량 변경 시 `status`를 `pending`으로 되돌린다.** 화면의 `updateReservation`·`detachFromRecurringGroup`을 이 콜러블로 옮긴다.
3. **트리거 보강**(심층 방어): `timeChanged`에 `before.vehicleId !== after.vehicleId`를 넣는다.

> **조치(같은 날)**: 1~3을 모두 반영했다 — `updateReservationSafe` 콜러블(`updateReservationCore`), Rules 소유자 분기의 정책 필드 잠금 + 상태 전이 제한(부록 3번째 관찰도 함께 닫음), 트리거의 차량 변경 겹침 검사. 회귀 고정은 아래 "강제 환류" 표 참고.
