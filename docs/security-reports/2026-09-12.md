## 발견 1 — 포크 PR의 브랜치 이름을 `master`로 지으면, 그 PR의 코드가 프로덕션 배포 잡에서 실행된다

- **심각도**: CRITICAL
- **확신도**: 9/10 — 트리거 필터가 `head_branch`에 걸린다는 것을 6건의 실제 배포 이력으로 실증했다. 남는 불확실성은 기술이 아니라 **사람**이다(아래 "유일한 방벽")
- **상태**: VERIFIED
- **카테고리**: CI/CD (거짓양성 제외 #4의 명시 예외)

### 근거

이 저장소는 **공개(PUBLIC)**다(`gh repo view` → `"visibility":"PUBLIC"`). 따라서 누구나 포크해 PR을 열 수 있다.

CI는 포크 PR에서도 돈다. [ci.yml:11](../../.github/workflows/ci.yml)

```yaml
  pull_request:
    branches: [master]
```

그리고 배포는 그 CI의 성공에 이어 붙는다. [deploy.yml:6](../../.github/workflows/deploy.yml)

```yaml
on:
  workflow_run:
    workflows: ["CI — 린트 · 테스트 · 빌드"]
    types: [completed]
    branches: [master]
```

**`workflow_run`의 `branches` 필터는 base 브랜치가 아니라 선행 실행의 `head_branch`에 걸린다.** 그리고 `pull_request` 실행의 `head_branch`는 **PR 소스 브랜치 이름**이다. 실측(최근 CI 실행):

```
push          master                                  7d0e743
pull_request  chore/check-truncated-numbers           08c55ee
pull_request  fix/number-input-parse-and-balance-...  5bdd70c
pull_request  feat/admin-edit-fuel-hipass             6eb168a
```

같은 구간의 Deploy 실행은 **push/master 건에만 1:1로 대응**한다(`7d0e743`·`66f015a`·`fe0262b`·`527aceb`·`1c7db91`·`a0a632e` — 6건 전부 일치, PR 브랜치발 배포는 0건). 즉 이 필터가 지금까지 포크를 걸러 온 것처럼 보인 이유는 **관리자가 브랜치를 `chore/…`·`fix/…`로 이름 지어 왔기 때문**이다. 그것은 규칙이 아니라 습관이다.

방벽은 하나가 아니었다 — **세 겹이 있었고, 셋 다 우회 가능했다**(아래 "방벽 셋" 참고). 우연한 방벽을 경계로 세지 않기 위해 셋을 각각 적는다.

**포크 저장소의 기본 브랜치 이름은 원본과 같다 — 즉 `master`다.** 공격자가 포크하고 그 `master`에서 PR을 열면 `head_branch == "master"`가 되어 필터를 통과한다.

통과한 뒤 배포 잡이 하는 일은 **PR의 코드를 체크아웃해서 실행하는 것**이다. [deploy.yml:38](../../.github/workflows/deploy.yml)

```yaml
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.workflow_run.head_sha || github.sha }}
```

그 뒤 `npm ci`(공격자의 `package.json` 라이프사이클 스크립트 실행) → `npm run build`(공격자의 prebuild·postbuild·vite 설정 실행) → 배포가 이어지고, 그 잡은 프로덕션 자격증명 전부를 들고 있다. [deploy.yml:95](../../.github/workflows/deploy.yml)

```yaml
          export GOOGLE_APPLICATION_CREDENTIALS=$(mktemp)
          echo '${{ secrets.FIREBASE_SERVICE_ACCOUNT }}' > "$GOOGLE_APPLICATION_CREDENTIALS"
          npx firebase-tools deploy --only functions,firestore:rules,storage --force --project vehicle-drive-log
```

잡이 참조하는 시크릿: `FIREBASE_SERVICE_ACCOUNT`, `ENV_FILE`, `FUNCTIONS_ENV_FILE`, `SENTRY_AUTH_TOKEN`.

**같은 저장소의 다른 워크플로는 이 위험을 이미 알고 막아 두었다.** [preview.yml:11](../../.github/workflows/preview.yml)

```yaml
    if: github.event.action != 'closed' && github.event.pull_request.head.repo.full_name == github.repository
```

미리보기 배포에는 "포크발이면 돌지 않는다"가 있고, **프로덕션 배포에는 없다.** 방어가 더 약한 쪽에 더 센 권한이 붙어 있다.

### 익스플로잇 시나리오

1. 공격자가 `dreamworker0/vehicle-drive-log`를 포크한다. 포크의 기본 브랜치는 `master`.
2. 포크의 `master`에 `package.json`의 `postinstall`을 고친 커밋을 올린다 — 내용은 환경변수 덤프를 외부로 보내거나, `firebase deploy` 직전의 빌드 산출물에 자격증명 탈취 코드를 끼워 넣는 것. **같은 커밋에서 `ci.yml`과 `scripts/`도 손본다** — 그래야 시크릿 없는 포크 컨텍스트에서도 CI가 초록으로 끝난다(위 방벽 3).
3. `attacker:master → dreamworker0:master`로 PR을 연다.
4. CI가 돈다(→ "방벽 셋" 참고). **공격자가 고친 CI가 공격자 코드를 검사하므로** 초록으로 끝난다. 이 실행 자체는 포크 컨텍스트라 시크릿이 없어 무해하고, 그래서 관리자 눈에도 평범한 초록 PR로 보인다.
5. CI 성공 → `head_branch == "master"` → **Deploy가 base 저장소 컨텍스트에서, 전체 시크릿을 들고, 공격자의 SHA를 체크아웃해 실행된다.**
6. `npm ci` 시점에 이미 임의 코드 실행. 서비스 계정으로 Functions·Rules·Storage 규칙·Hosting을 갈아치울 수 있고, 시크릿 4종이 전부 유출된다. 이용 기관 전체의 데이터가 한 번에 넘어간다.

### 방벽 셋 — 그리고 셋 다 왜 충분하지 않은가

**1. 브랜치 이름 습관.** 위에서 본 것. 규칙이 아니라 관행이고, 포크의 기본 브랜치 이름은 애초에 `master`다.

**2. 최초 기여자 승인.**

```
GET /repos/dreamworker0/vehicle-drive-log/actions/permissions/fork-pr-contributor-approval
{"approval_policy":"first_time_contributors"}
```

GitHub 기본값이다. **처음 기여하는 사람**의 워크플로 실행만 관리자 승인을 요구한다. 두 가지 이유로 이것에 프로덕션을 걸어 둘 수 없다:

- 승인 버튼은 "이 PR을 머지하겠다"가 아니라 **"CI를 돌려 보겠다"**는 뜻으로 눌린다. 공개 저장소 관리자가 일상적으로 누르는 버튼이고, 누르는 순간 배포까지 이어진다는 것이 화면에 드러나지 않는다.
- 한 번이라도 기여가 머지된 계정은 **그 뒤로 승인 없이 실행**된다. 오타 수정 PR 하나면 자격이 생긴다.

즉 이 방벽은 기술적 경계가 아니라 **클릭 한 번에 달린 사회적 장벽**이다.

**3. prebuild 환경변수 게이트 — 가장 튼튼해 보였고, 가장 확실하게 뚫린다.**

무수정 포크 PR은 CI가 초록으로 끝나지 못한다. [generate-sw-config.ts](../../scripts/generate-sw-config.ts)가 `prebuild`에서 Firebase 환경변수 누락을 치명 오류로 다루기 때문이다.

```ts
if (missing.length > 0) {
    console.error('❌ Firebase 환경변수가 비어 있어 firebase-messaging-sw.js 생성을 중단합니다.');
    ...
    process.exit(1);
}
```

포크 PR에는 시크릿이 주어지지 않아 `.env`가 빈 값이 되고([ci.yml:234](../../.github/workflows/ci.yml)의 `echo "${{ secrets.ENV_FILE }}" > .env`), `npm run build`가 여기서 죽고, CI가 실패해 `conclusion != 'success'`가 되어 배포로 이어지지 않는다.

**그런데 이것이 방벽이 못 되는 이유가 이 취약점의 핵심이다.** `pull_request` 이벤트의 워크플로와 스크립트는 **PR의 머지 커밋에서 읽힌다.** 공격자는 자기 포크에서 `ci.yml`과 `scripts/`를 통째로 고쳐 모든 스텝을 통과시킬 수 있다 — 워크플로 `name:`까지 맞추면 `workflows: ["CI — 린트 · 테스트 · 빌드"]` 필터도 통과한다.

즉 **선행 CI가 무엇을 검사하든 그 검사 자체가 공격자 소유**다. "CI가 초록이었다"는 배포 잡의 신뢰 근거가 될 수 없고, 그래서 경계는 CI 결과가 아니라 **실행의 출처**(`event`·`head_repository`)에 그어야 한다.

### 권고 조치

`deploy.yml`에 preview.yml과 같은 기준의 가드를 둔다. 이 배포는 **원본 저장소의 push로만** 일어나야 한다.

```yaml
    if: >-
      github.event_name == 'workflow_dispatch'
      || (github.event.workflow_run.conclusion == 'success'
          && github.event.workflow_run.event == 'push'
          && github.event.workflow_run.head_repository.full_name == github.repository)
```

`workflow_run.event == 'push'`가 핵심이다 — 포크 PR발 실행은 `pull_request`라 여기서 잘린다. `head_repository` 비교는 두 번째 자물쇠다.

## 발견 2 — 직원이 기록의 **날짜 칸**에 스크립트를 적어 두면, 관리자가 그 PDF를 뽑는 순간 관리자 권한으로 실행된다

- **심각도**: HIGH
- **확신도**: 10/10 — PoC 테스트를 작성해 **5개 경로 전부에서 `<script>`가 살아 있는 노드로 파싱되는 것을 실행으로 확인**했다
- **상태**: VERIFIED
- **카테고리**: 멀티테넌트(A01) — 역할 경계 상승

### 근거

PDF 내보내기는 전부 새 창에 HTML 문자열을 그대로 써 넣는 구조다. [pdfEngine.ts:284](../../src/lib/pdf/pdfEngine.ts)

```ts
    const printWindow = window.open('', '_blank', 'width=1100,height=800');
    ...
    printWindow.document.write(html);
```

`window.open('')`이 여는 `about:blank`는 **여는 쪽의 오리진을 상속한다.** 즉 이 문서에서 실행되는 스크립트는 `vehicle-drive-log.web.app`의 스크립트이며, 그 오리진의 IndexedDB(= Firebase 인증 세션)에 접근한다.

그래서 이 경로의 사용자 입력은 전부 `escapeHtml`을 지나며, 그것을 고정하는 테스트도 있다([printWindowHarness.ts:104](../../src/__tests__/lib/pdf/printWindowHarness.ts)). **한 종류만 빠져 있다 — 날짜다.** [pdfStyles.ts:234](../../src/lib/pdf/pdfStyles.ts)

```ts
export function formatDate(dateStr: string) {
    if (!dateStr || dateStr === '-') return '-';
    const parts = dateStr.split('-');
    if (parts.length === 3) {
        return `${parts[0]}-${parts[1]}-${parts[2]}`;
    }
    return dateStr;
}
```

두 갈래 모두 **입력 문자를 그대로 돌려준다.** 이 함수는 이스케이프가 아니라 재조립일 뿐인데, 호출부는 그것을 이스케이프처럼 신뢰한다 — 다섯 곳 전부 `escapeHtml` 없이 보간한다:

| 파일 | 줄 | 필드 |
|---|---|---|
| [pdfExport.ts](../../src/lib/pdf/pdfExport.ts) | 146 | 운행일지 `date` |
| [fuelLogPdfExport.ts](../../src/lib/pdf/fuelLogPdfExport.ts) | 44 | 주유기록 `date` |
| [hipassChargePdfExport.ts](../../src/lib/pdf/hipassChargePdfExport.ts) | 39 | 하이패스 충전 `date` |
| [maintenancePdfExport.ts](../../src/lib/pdf/maintenancePdfExport.ts) | 45 | 정비기록 `date` |
| [maintenancePdfExport.ts](../../src/lib/pdf/maintenancePdfExport.ts) | 52 | 정비기록 `nextDueDate` |

같은 파일의 같은 행에서 **이름·목적지·비고는 이스케이프되고 날짜만 안 된다**([fuelLogPdfExport.ts:44](../../src/lib/pdf/fuelLogPdfExport.ts)) — 누락이지 설계가 아니다. 대조군: 일일 운행일지의 `formatDateKorean`은 **호출부가 감싸서** 안전하다([dailyLogPdfExport.ts:220](../../src/lib/pdf/dailyLogPdfExport.ts)의 `escapeHtml(formatDateKorean(date))`).

**이 값은 공격자가 정한다.** Rules는 날짜 필드에 아무 제약을 걸지 않는다 — 주유기록 create는 소속·작성자·금액 부호만 본다([firestore.rules](../../firestore.rules) `fuelLogs`).

```
      allow create: if newBelongsToMyOrg()
                    && request.resource.data.keys().hasAll(['organizationId', 'vehicleId', 'driverUid'])
                    && request.resource.data.driverUid == request.auth.uid
```

Zod 컨버터도 통과시킨다 — [fuelLog.ts:23](../../src/schemas/fuelLog.ts)의 `date: z.string().catch('')`에는 형식 검사가 없다(driveLog·hipassCharge·maintenance 동일). 읽을 때 원문 그대로 돌아온다([driveLogExportFields.ts:47](../../src/lib/driveLogExportFields.ts)의 `return log.date || …`).

### 실행으로 확인한 것

임시 PoC 테스트(기존 하네스의 `XSS_PAYLOAD` = `<script>alert(1)</script><img src=x onerror=alert(2)>`를 `date`에만 넣음)를 다섯 경로에 돌렸다:

FAIL  PoC — date 필드 XSS > 정비 기록 nextDueDate
FAIL  PoC — date 필드 XSS > 운행일지

Test Files  1 failed (1) / Tests  5 failed (5)

기존 XSS 테스트가 이것을 놓친 이유도 확인했다 — 페이로드를 `destination`·`notes`·`driverName`·`vehicleName`·`shop`·`description`에만 넣고 **`date`에는 넣지 않는다**([reportPdfExports.test.ts:105](../../src/__tests__/lib/pdf/reportPdfExports.test.ts), [pdfExport.test.ts:481](../../src/__tests__/lib/pdf/pdfExport.test.ts)).

### 익스플로잇 시나리오

1. 공격자는 어느 기관의 **평직원 계정 하나**면 된다(가장 낮은 권한).
2. 브라우저 콘솔에서 Firebase SDK로 주유기록을 하나 쓴다. 화면 대신 SDK를 직접 쓰는 이유는 입력칸이 날짜 선택기이기 때문이고, Rules는 이를 막지 않는다:
   `{ organizationId: <내 기관>, vehicleId: <아무 차량>, driverUid: <내 uid>, date: "<script>…</script>" }`
3. 기록은 정상 저장되고 목록 화면에서는 React가 이스케이프해 **그냥 이상한 날짜로 보인다**(눈에 띄지 않는다).
4. 기관 관리자가 월말에 **주유·충전 기록 → PDF 다운로드**를 누른다.
5. 인쇄 창(앱 오리진)에서 공격자 스크립트가 **관리자 세션으로** 실행된다. IndexedDB의 Firebase 토큰으로 관리자 권한 행위가 가능하다 — 공격자 계정을 `admin`으로 올리기(Rules의 `isOrgAdmin` 분기가 역할 변경을 허용), 기관 전체 데이터 열람·반출, 초대 코드 재발급 호출 등.
6. 즉 **직원 → 기관관리자 권한 상승**이 성립한다. 삽입 시점과 실행 시점이 분리돼 있어(저장형) 공격자는 접속해 있을 필요도 없다.

### 권고 조치

1. 호출부 다섯 곳을 `escapeHtml(formatDate(...))`로 감싼다(일일 운행일지가 이미 쓰는 방식과 동일).
2. 더 나은 곳은 **`formatDate` 안**이다 — 이 함수는 날짜 문자열을 표시용으로 바꾸는 것이 유일한 역할이므로, 여기서 이스케이프하면 앞으로 추가되는 호출부가 같은 함정을 밟지 않는다.
3. 회귀 고정: PoC를 정식 테스트로 승격해 기존 XSS 테스트의 페이로드 대상에 `date`·`nextDueDate`를 넣는다.

## 확인했고 문제 없던 것 (회귀 확인)

- **Firestore Rules**: 24개 컬렉션 전수 재검토. `organizationId` 불변 강제, `consent` 필드 잠금, 서버 소유 필드(`inviteCode`·`status`·`applicant*`) 차단, `favorites` 모양 검사, 서버 전용 컬렉션 9종 `if false` — 모두 유효.
- **콜러블 권한**: 36개 전수. `sendAdminNotice`의 2026-09-02 조치(직원 차단) 포함해 역할 재검증 누락 없음. `wrapCallableHandler`가 인증을 공통 강제.
- **Storage Rules**: 증빙서류는 superAdmin만, 업로드는 Admin SDK만, 피드백 이미지는 본인 폴더·5MB·image/* 제한.
- **Slack 연동**: `slackEvents`는 v0 HMAC + timestamp ±5분을 `timingSafeEqual`로 검증하고 실패 시 IP 상한까지 건다. OAuth state도 HMAC 서명 + 상수시간 비교.
- **Gemini/OCR**: `ocrDashboard`는 인증 + App Check + 분당 상한(fail-closed) + 일일 사용자·기관 쿼터 + 5MB 상한을 모두 지나고, 응답은 `Number()`로 강제 변환돼 프롬프트 인젝션이 값으로 새지 않는다.
- **시크릿**: 추적 파일·커밋 이력 전수 스캔. 실키 형식 일치 0건(테스트 픽스처와 Firebase 공개 키 제외). `.env`는 `.gitignore`에서 차단되고 히스토리에도 없다.
- **스킬 공급망**: `.agent/skills`·`.agent/workflows`에서 외부 전송·임의 실행 패턴 0건.
- **다른 워크플로**: `gemini-review.yml`은 `pull_request_target`이지만 **ref 미지정 + 의존성 설치 없음**으로 PR 코드가 실행될 경로가 없다(안전한 사용례). `preview.yml`은 포크 가드 보유.
- **의존성**: `npm run audit` 프론트·Functions 모두 0건.
