## 발견 1 — 인증 사용자가 `feedbacks` 문서를 직접 만들어 Gemini·Discord·Functions를 무제한 증폭시킬 수 있다

- **심각도**: HIGH
- **확신도**: 9/10 — Rules 원문·트리거 코드·경로 전체에 상한 부재를 각각 인용 대조
- **상태**: VERIFIED
- **카테고리**: LLM(비용 증폭) — 거짓양성 제외 #1의 명시 예외

### 근거

`feedbacks` 컬렉션의 생성 규칙에는 **필드 검증도 상한도 없다**. [firestore.rules:424-429](../../firestore.rules)

```
      allow read: if isSuperAdmin();

```

그리고 이 컬렉션의 `onCreate`가 곧바로 Gemini를 부른다. [functions/src/handlers/triggers/generateFeedbackDraft.ts:64-166](../../functions/src/handlers/triggers/generateFeedbackDraft.ts)

```ts
export const generateFeedbackDraft = onDocumentCreated(
    { document: "feedbacks/{feedbackId}", ... },
```
```ts
        await sendDiscordAlert({ ... fields: [ ... { name: "내용", value: message, inline: false } ] })
```
```ts
            const images = await fetchPromptImages(data.imageUrls, { logName: "generateFeedbackDraft" });
            const text = await generateAiContent(prompt, images.length > 0 ? images : undefined);
```

경로 어디에도 쿼터가 없다 — `generateAiContent`([functions/src/core/gemini.ts:15](../../functions/src/core/gemini.ts))는 호출 계수 없이 그대로 API를 때리고, `checkRateLimitByUid`·`checkDailyOcrQuota`([functions/src/utils/rateLimit.ts:38,97](../../functions/src/utils/rateLimit.ts))는 이 트리거에서 호출되지 않는다. 트리거는 Firestore 쓰기가 방아쇠라 콜러블용 rate limit이 개념상 걸리지 않는다.

### 익스플로잇 시나리오

1. 아무 구글 계정으로 앱에 로그인한다. 기관 소속·승인 여부는 필요 없다 — 규칙이 요구하는 것은 `isSignedIn()`뿐이다.
2. 브라우저 콘솔에서 클라이언트 SDK로 직접 쓴다(화면·훅을 거치지 않으므로 프론트의 어떤 제어도 무의미하다):
   ```js
   for (let i = 0; i < 5000; i++)
     addDoc(collection(db, 'feedbacks'), { message: '분석해줘', imageUrls: [big1, big2, big3] });
   ```
3. 쓰기 1건마다 `generateFeedbackDraft`가 뜬다 → Discord 웹훅 1회 + `feedbacks` 쿼리 1회 + 이미지 최대 3개×5MB 다운로드 + **Gemini 멀티모달 호출 1회** + 문서 업데이트.
4. 상한이 없으므로 호출량은 공격자의 쓰기 속도만큼 늘어난다. 운영자는 Discord 채널이 도배되는 것으로 뒤늦게 안다.

### 영향

무료로 제공되는 비영리 대상 서비스에서 Gemini·Functions·Firestore 요금이 공격자 의지대로 증폭된다. 프로젝트 자체 규칙 [ocr-cost-security §1](../../.agent/rules/ocr-cost-security.md)("반드시 서버사이드에서 호출 제한 검증")의 명시적 위반이며, `ocrDashboard`·`ocrDocument`·`askAI`가 모두 fail-closed 쿼터를 갖는 것과 대조된다.

### 변종 분석

- 같은 트리거는 비인증 경로 [submitPublicFeedback](../../functions/src/handlers/https/submitPublicFeedback.ts)로도 켜진다. 그쪽은 이메일 5회/시간·IP 10회/시간 상한이 있으나 **그 IP 상한이 발견 2로 무력화**되므로 두 발견은 곱해진다.
- 클라이언트가 생성 가능한 다른 컬렉션(`favorites`·`orgApplications`·`users`)은 소유자·이메일 일치를 강제하고 Gemini 트리거가 붙지 않는다. `organizations`의 `autoVerifyDocument`는 superAdmin 전용 생성 + `aiVerifyDetail`·이미지 경로 변화 가드가 있어([functions/src/handlers/triggers/autoVerifyDocument.ts:70-73](../../functions/src/handlers/triggers/autoVerifyDocument.ts)) 반복 호출이 막힌다. **`feedbacks`가 유일한 무검증 창구다.**

## 발견 2 — `X-Forwarded-For` 헤더 하나로 모든 IP 레이트리밋을 우회할 수 있다 (비인증 Gemini 경로 포함)

- **심각도**: HIGH
- **확신도**: 9/10 — 런타임의 `trust proxy` 활성화를 패키지 원문으로 확인
- **상태**: VERIFIED
- **카테고리**: LLM(비용 증폭) + 통합

### 근거

레이트리밋 키가 되는 클라이언트 IP를 두 방식으로 뽑는데, **둘 다 클라이언트가 정할 수 있다.**

[functions/src/handlers/https/submitOrgApplication.ts:113-118](../../functions/src/handlers/https/submitOrgApplication.ts)
```ts
        const clientIp = request.rawRequest?.ip
            || (request.rawRequest?.headers["x-forwarded-for"] as string)
            || "unknown";
        if (await checkRateLimitByIp("submitOrgApplication", clientIp, 10, 3600, "closed")) {
```

폴백(`headers["x-forwarded-for"]`)이 클라이언트 헤더인 것은 자명하고, **1순위인 `req.ip`도 마찬가지다.** Cloud Functions 2세대 런타임인 functions-framework가 Express에 `trust proxy`를 켜 두기 때문이다(`@google-cloud/functions-framework@5.0.5`, `build/src/server.js:89`):

```js
    app.enable('trust proxy'); // To respect X-Forwarded-For header.
```

`trust proxy`가 켜진 Express에서 `req.ip`는 X-Forwarded-For의 **맨 앞 값**이다. 그런데 Google 프런트엔드는 클라이언트가 보낸 XFF를 지우지 않고 실제 IP를 **뒤에 덧붙인다** — 즉 맨 앞 값은 공격자가 넣은 문자열 그대로다. 이 저장소도 같은 사실을 이미 알고 있다([functions/src/handlers/callable/recordSession.ts:45-46](../../functions/src/handlers/callable/recordSession.ts)의 "`x-forwarded-for`의 **첫 번째** 값이 원 클라이언트다").

키는 그대로 문서 ID가 되므로([functions/src/utils/rateLimit.ts:137-138](../../functions/src/utils/rateLimit.ts)) 매 요청 임의 값을 넣으면 매번 새 카운터 버킷이 만들어진다.

```ts
    const safeIp = ip.replace(/[.:]/g, "_");
    const docId = `${functionName}:${safeIp}:${windowKey}`;
```

### 익스플로잇 시나리오

1. 공격자가 `submitOrgApplication`(비인증 콜러블, App Check 비활성 — [코드 주석 59-68행](../../functions/src/handlers/https/submitOrgApplication.ts)에 의도된 설계로 명시)에 요청마다 `X-Forwarded-For: <난수 IP>`를 붙여 보낸다.
2. 이메일 6회/시간 상한([같은 파일:110](../../functions/src/handlers/https/submitOrgApplication.ts))은 `applicantEmail`이 검증되지 않는 임의 문자열이라 애초에 회전으로 무력하다. IP 상한이 유일한 실질 방어선인데 1번으로 뚫린다.
3. 요청마다 5MB 이내 이미지/PDF가 **Storage 업로드·Firestore 쓰기 이전에** Gemini로 간다([같은 파일:151](../../functions/src/handlers/https/submitOrgApplication.ts)의 `prescreenDocument`). 즉 반려되는 요청도 Gemini 비용은 이미 발생한다.
4. 결과: **인증 없이, 상한 없이** 멀티모달 Gemini 호출을 무제한 유발할 수 있다.

### 영향

#195에서 판별을 접수 앞으로 옮기면서 "신청 1건당 Gemini 1회"라는 비용 상한 설계가 성립하려면 IP 상한이 유효해야 하는데, 그 전제가 성립하지 않는다. 같은 우회는 `submitPublicFeedback`(익명 Firestore 쓰기 → 발견 1의 트리거 연쇄)에도 그대로 적용된다.

## 발견 3 — 서버가 클라이언트 지정 임의 URL을 검증 없이 가져온다 (SSRF)

- **심각도**: MEDIUM
- **확신도**: 8/10 — 코드 경로는 확정, 응답을 공격자가 되읽을 수 없어 blind
- **상태**: VERIFIED
- **카테고리**: LLM / 통합 (발견 1과 동일 뿌리)

### 근거

[functions/src/utils/helpers.ts:204-217](../../functions/src/utils/helpers.ts)

```ts
    for (const url of urls) {
        if (typeof url !== "string") continue;
        try {
            const res = await fetch(url);
```

스킴·호스트 검증이 전혀 없다. 이 `urls`는 발견 1에서 본 대로 **클라이언트가 만든 `feedbacks` 문서의 `imageUrls` 필드**이며([generateFeedbackDraft.ts:161](../../functions/src/handlers/triggers/generateFeedbackDraft.ts), [regenerateFeedbackDraft.ts:118](../../functions/src/handlers/callable/regenerateFeedbackDraft.ts)), Rules는 이 필드를 검사하지 않는다.

### 익스플로잇 시나리오

1. 로그인한 사용자가 `imageUrls: ["http://<내부주소>/...", "http://<공격자 서버>/..."]`를 담은 `feedbacks` 문서를 만든다.
2. 트리거가 서버(구글 소유 egress)에서 그 URL을 그대로 요청한다 → 함수가 임의 HTTP 클라이언트로 동작한다. 대상 서버 로그에는 공격자가 아니라 이 서비스가 남는다.
3. URL당 최대 5MB × 3개를 매 문서마다 내려받으므로 대역폭·시간 증폭도 함께 붙는다.

응답 본문은 Gemini 프롬프트로만 들어가고 결과(`aiDraft`)는 superAdmin만 읽으므로([firestore.rules:425](../../firestore.rules)) **직접적인 데이터 회수 경로는 없다**(그래서 CRITICAL이 아니다). GCE 메타데이터 서버는 `Metadata-Flavor` 헤더를 요구해 이 fetch로는 뚫리지 않는다.

## 억제된 잠정 관찰 (발견 아님 — 8/10 미만)

1. **`holidayProxy`의 쿼리 파라미터 미인코딩** (확신도 5/10): [holidayProxy.ts:19-21](../../functions/src/handlers/https/holidayProxy.ts)이 `solYear`·`numOfRows`를 URL에 그대로 보간해 `&`로 공공데이터 API 파라미터를 덧붙일 수 있다. 호스트가 고정이라 SSRF가 아니고 인증도 선행하며, 그 API로 할 수 있는 일이 공휴일 조회뿐이라 익스플로잇 가치가 없다. → 위생 차원의 `encodeURIComponent` 권고.
2. **`submitOrgApplication` IP 상한이 커밋 메시지와 불일치** (보안 발견 아님): #195 커밋 메시지는 "IP 10→15회/시간"이라 적었지만 코드는 10 그대로다([submitOrgApplication.ts:116](../../functions/src/handlers/https/submitOrgApplication.ts)). 더 엄격한 쪽이라 위험은 없고, 발견 2를 고칠 때 함께 정리하면 된다.
3. **Discord 임베드 필드 내용 무제한** (확신도 4/10): [generateFeedbackDraft.ts:119](../../functions/src/handlers/triggers/generateFeedbackDraft.ts)가 사용자 `message`를 자르지 않고 필드 값으로 넣는다. 1024자 초과 시 웹훅이 실패할 뿐이고, 운영 채널 도배 자체는 발견 1의 상한을 걸면 사라진다.
4. **접속기록의 접속지 IP 위조 가능** (확신도 8/10이나 제외 규칙 #8 "로그 스푸핑"에 해당): [recordSession.ts:50-54](../../functions/src/handlers/callable/recordSession.ts)가 XFF 첫 값을 그대로 저장한다. 「개인정보의 안전성 확보조치 기준」 제16조의 접속지 정보라는 점에서 단순 로그 스푸핑보다 무게가 있어 **기록해 둔다** — 발견 2를 고칠 때 IP 추출 지점을 한 곳으로 모으면 함께 해결된다.

### 조치에서 내린 판단 두 가지

- **전역 예산을 왜 따로 뒀는가**: XFF에서 프런트엔드가 덧붙이는 홉 수가 경로마다 다를 수 있다(콜러블은 `*.cloudfunctions.net` 직행, `/api/tmap`·`/api/holiday`는 Hosting 재작성 경유). IP 추정이 어긋나도 비용이 새지 않도록, 주체와 무관한 단일 카운터를 마지막 방어선으로 뒀다. `submitOrgApplication`의 IP 상한을 10 → 30으로 올린 것도 같은 이유다 — 최악의 경우 여러 신청자가 한 버킷을 공유해도 정상 신청이 막히면 안 되고, 비용 상한은 전역 예산이 맡는다.
- **감수한 트레이드오프**: 공격자가 전역 예산(시간당 40건)을 태우면 그 시간 동안 신규 기관 신청이 "잠시 후 다시 시도" 안내를 받는다. 무제한 과금보다 이쪽이 낫다고 판단했다. 실사용은 하루 몇 건 수준이라 정상 신청이 이 한도에 닿을 일은 없다.
