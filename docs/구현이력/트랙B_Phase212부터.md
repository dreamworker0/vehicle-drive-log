### Phase 212: 백업은 걸었는데 끝났는지는 아무도 몰랐다 — 하루 뒤에 확인한다 💾🔍

> 2026-09-06. OPERATIONS.md §4.1이 「알림이 없다고 백업이 있는 것은 아니다」라고 **글로 적어 둔 구멍**을 닫았다. 사람이 버킷을 눈으로 봐야만 알 수 있던 상태였다.

| 항목 | 내용 |
|------|------|
| **호출이 성공한 뒤에 실패하면 아무도 몰랐다** | 관리형 export는 장기 실행 작업이라 코드가 완료를 그 자리에서 기다릴 수 없다. 지금까지는 export를 걸고 「시작됨」만 남긴 뒤 끝났다. 즉 **실패 알림이 오지 않는 것과 백업이 있는 것이 구분되지 않았다** |
| **기다리는 대신 하루 뒤에 본다** | 매일 배치가 어제 폴더에 완료 표식(`<날짜>.overall_export_metadata`)이 있는지 본다. 이 표식은 export가 **끝날 때** 쓰이므로, 출력 파일만 있고 표식이 없으면 시작만 되고 끝나지 않은 것이다. 폴링으로 함수를 몇 분씩 붙잡는 대신 목록 조회 1회로 끝낸다. 발견이 최대 24시간 늦지만 백업 실패는 분 단위로 다툴 일이 아니다 — **「영영 모른다」를 「하루 안에 안다」로 바꾸는 것**이 실질적인 이득이다 |
| **헛경보를 내지 않는 두 경우** | ① 백업 이력이 아예 없으면(첫 배포 직후) 건너뛴다 — 불행한 경로에서만 목록을 한 번 더 부르므로 평소 비용은 그대로다 ② 목록 조회가 실패하면(권한 등) **판정하지 않는다.** 확인 못 한 것을 부재로 단정하면 헛경보가 된다 — 기존 중복 검사와 같은 원칙이다 |
| **이 확인이 실패해도 오늘 백업은 걸린다** | `runStep`이 스텝을 격리한다. 보관 90일·매일 02:20 실행이라 어제 폴더가 수명 주기로 지워질 일도 없다 |
| **점검표 자체가 틀려 있었다** | OPERATIONS.md 빠른 점검표의 기준이 「오늘 날짜 폴더 존재」였는데, **폴더만 있는 것이 바로 이번에 부족하다고 밝힌 상태다.** 진단 기준이 진단하려는 결함을 통과시키고 있었다 |
| **곁들여 닫은 살림 셋** | ① `.claude/launch.json`(도구 자동 생성, 포트가 기기마다 다름)과 일회성 외부 프롬프트 원문을 추적에서 제외 — `.claude/` 아래 스킬·커맨드 브리지 47개는 추적 대상이라 디렉터리째 무시하지 않고 파일만 지정했다 ② 열린 구간 파일을 **184KB에서 리네임만으로** 닫았다(`트랙B_Phase181-211.md`) — 앞선 두 번은 231KB·188KB까지 방치해 내용을 갈라야 했다 ③ eval 베이스라인 재측정 |
| **eval 판정을 내가 하지 않은 이유** | 하네스가 재측정을 권고한 원인이 `update-faq`·`release-notes`·`pre-deploy-check` 변경인데, **그 세 스킬 본문을 이번 세션에서 내가 고쳤다.** 하필 재측정을 유발한 항목에서 내 판단이 부풀려진다. 트리거는 저장소 접근을 막은 판정 에이전트에(24/24), 행동은 케이스마다 깨끗한 에이전트를 띄우는 오케스트레이터에(10/10) 맡겼다. **두 resultsHash 모두 직전과 동일** — 답이 바뀌지 않았다. 하네스 경고 2건 → 0건 |
| **검증** | Functions **77 suite 1,054테스트** · 뮤테이션 4건 · 하네스 18영역 0오류 |
| **남는 것** | ① 발견이 **최대 24시간 늦다** — 설계상 받아들인 지연이다 ② 표식이 있어도 **내용물이 온전한지는 확인하지 않는다.** 복원 리허설은 여전히 사람 몫이다 ③ 목록 조회 실패는 판정 보류라 로그만 남는다 — 권한이 **영구히** 깨지면 조용해진다(헛경보를 피한 대가) |

### Phase 213: 저장 못 한 기록에 대해 사실대로 말한다 — 그 정직함마저 헛돌던 곳 🔌📴

> 2026-09-06. 오프라인·지연 경로에서 사용자에게 하는 말 세 가지가 사실과 어긋나 고쳤는데, **정작 그 정직함을 켜는 스위치가 항상 켜져 있었다**는 것을 리뷰가 찾아냈다.

| 항목 | 내용 |
|------|------|
| **「다시 입력해 주세요」인데 무엇을 입력할지 안 알려 줬다** | 폐기된 기록은 payload를 그대로 들고 있는데 안내는 **건수만** 셌다. 차에서 내린 뒤에는 계기판 숫자를 기억으로 복원할 방법이 없어, **시키는 대로 할 수가 없는 안내**였다. 날짜·목적지·계기판을 함께 적는다 |
| **알리기도 전에 기록을 지웠다** | `drainFailedRecords`가 읽으면서 함께 비웠다. 읽은 직후 화면이 닫히면 기록은 사라지고 사용자는 끝내 듣지 못한다 — **유실을 알리는 장치가 유실되는** 모양이었다. peek → 알림 → clear로 갈랐다 |
| **모르는데 초록색으로 「저장했습니다」라고 했다** | 타임아웃은 실패가 아니라 **모름**이다. `persistentLocalCache`면 Firestore가 미전송 쓰기를 IndexedDB에 남겨 재전송하므로 사실상 맞는 말이지만, 사생활 보호 모드 등으로 `memoryLocalCache`로 떨어진 기기는 **탭을 닫는 순간 사라진다** |
| **그런데 그 내구성 판정이 사실상 항상 참이었다** | 리뷰가 짚었고 확인해 보니 사실이었다. `initializeFirestore`가 persistent 설정으로 반환하는 것은 **아무것도 보증하지 않는다** — SDK는 IndexedDB를 나중에 열고 사생활 보호 모드에서는 **비동기로 조용히** 실패한다. 실제 감지자는 같은 파일의 2단계 `checkIndexedDBAvailability()`인데 내 플래그를 건드리지 않았다. **정작 안내가 필요한 그 기기에서 계속 「저장했다」고 말했고, 공지에 적은 문구가 그대로 거짓이었다.** 판정을 2단계로 옮기고 기본값을 false로 뒀다 |
| **날짜를 알려 준다더니 언제나 비어 있었다** | `describeRecord`가 `data.date`를 읽는데 `buildLogData`가 만드는 것은 `timestamp`뿐이다. `date`는 옛 문서의 레거시다. Date는 `structuredClone`을 그대로 통과하므로 큐에서도 Date로 남아 있다 — 그것을 쓴다 |
| **내부 마커가 날짜로 찍힐 참이었다** | 오프라인 **수정**은 당일 운행의 `startDate`를 `deleteField()`로 지우는데, 큐가 그것을 `'__syncQueue.deleteField__'` 문자열로 바꿔 저장한다. 사용자에게 그 문자열이 날짜라고 보여질 참이었다. **Phase 211에서 내가 넣은 `deleteField`와 이번 변경이 만나 생긴 조합**이다 |
| **스토어를 통째로 비워 사이에 들어온 폐기가 함께 사라졌다** | 읽고 지우기 사이에 서비스워커 flush가 새 폐기를 밀어 넣을 수 있다. **알린 id만** 골라 지운다 |
| **같은 토스트가 두 번 떴다** | `online`·`visibilitychange`는 잠금 화면을 풀며 통신이 돌아올 때 같이 발화한다. `flushQueue`와 같은 방식으로 진행 중 Promise를 공유한다 |
| **배선을 이 세션에서 세 번째로 놓쳤다** | `describeRecord`만 테스트해서 `buildFailureMessage`가 그것을 쓰지 않아도 전부 초록이었다. 앞서 `beforeBreadcrumb`·`beforeSendSpan`에서 같은 실수를 했다(Phase 211). **순수 함수는 테스트하고 배선은 안 하는 패턴**이 세 회차 연속 반복됐다 |
| **공지를 두 번 썼다** | 처음 쓴 세 항목은 **배포되지 않을 동작**을 설명하고 있었다 — 내구성 판정이 헛돌았으니 「폴백 기기에 다르게 안내한다」가 거짓이었다. 리뷰 뒤 실제 동작에 맞춰 다시 썼다 |
| **사용자가 일하는 방식을 짚었다** | 「하나 고치고 CI 돌리고 배포하고를 반복하는 것 말고는 없니?」 재어 보니 PR당 30~40분이고, pre-push 훅(`test`+`build`+`audit`, ~3분)이 **내 수동 실행과 CI를 통째로 중복**하고 있었다. ① 관련 없는 살림은 한 PR로 묶고 ② 수동 전체 스위트 실행을 그만두고 pre-push를 단일 로컬 게이트로 삼고 ③ 겹치지 않는 파일은 병행한다. 원인은 **사용자가 이미 저장해 둔 선호(「연관 변경은 한 PR로 묶기」)를 내가 어기고 있던 것**이다 |
| **검증** | 뮤테이션 **3건 + 리뷰 대응 5건** · lint · type-check · 하네스 0오류 0경고 · CI 전 체크 통과 · 배포 후 프로덕션 번들에서 2단계 내구성 판정(`$e=Me&&e===!0`)·`__syncQueue.` 마커 2종·id 지정 삭제(`store.delete`) 실물 확인 |
| **남는 것** | ① 이미 초기화된 인스턴스를 재사용하는 경로는 어느 쪽인지 알 수 없어 **내구성 없음으로 본다** — 모르면서 있다고 말하는 것보다 낫다는 판단이고, 보수적 오판은 남는다 ② 2단계 판정이 끝나기 전(최대 2초) 타임아웃이 나면 false로 읽혀 **내구성 있는 기기도 경고를 본다** ③ 상세는 3건까지만 적고 나머지는 「외 N건」이다 — 오래 오프라인이었으면 못 보는 항목이 생긴다 |
