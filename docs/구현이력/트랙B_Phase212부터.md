### Phase 212: 백업은 걸었는데 끝났는지는 아무도 몰랐다 — 하루 뒤에 확인한다 💾🔍

> 2026-09-06. OPERATIONS.md §4.1이 「알림이 없다고 백업이 있는 것은 아니다」라고 **글로 적어 둔 구멍**을 닫았다. 사람이 버킷을 눈으로 봐야만 알 수 있던 상태였다.

| 항목 | 내용 |
|------|------|
| **호출이 성공한 뒤에 실패하면 아무도 몰랐다** | 관리형 export는 장기 실행 작업이라 코드가 완료를 그 자리에서 기다릴 수 없다. 지금까지는 export를 걸고 「시작됨」만 남긴 뒤 끝났다. 즉 **실패 알림이 오지 않는 것과 백업이 있는 것이 구분되지 않았다** |
| **기다리는 대신 하루 뒤에 본다** | 매일 배치가 어제 폴더에 완료 표식(`<날짜>.overall_export_metadata`)이 있는지 본다. 이 표식은 export가 **끝날 때** 쓰이므로, 출력 파일만 있고 표식이 없으면 시작만 되고 끝나지 않은 것이다. 폴링으로 함수를 몇 분씩 붙잡는 대신 목록 조회 1회로 끝낸다. 발견이 최대 24시간 늦지만 백업 실패는 분 단위로 다툴 일이 아니다 — **「영영 모른다」를 「하루 안에 안다」로 바꾸는 것**이 실질적인 이득이다 |
| **헛경보를 내지 않는 두 경우** | ① 백업 이력이 아예 없으면(첫 배포 직후) 건너뛴다 — 불행한 경로에서만 목록을 한 번 더 부르므로 평소 비용은 그대로다 ② 목록 조회가 실패하면(권한 등) **판정하지 않는다.** 확인 못 한 것을 부재로 단정하면 헛경보가 된다 — 기존 중복 검사와 같은 원칙이다 |
| **이 확인이 실패해도 오늘 백업은 걸린다** | `runStep`이 스텝을 격리한다. 보관 90일·매일 02:20 실행이라 어제 폴더가 수명 주기로 지워질 일도 없다 |
| **점검표 자체가 틀려 있었다** | OPERATIONS.md 빠른 점검표의 기준이 「오늘 날짜 폴더 존재」였는데, **폴더만 있는 것이 바로 이번에 부족하다고 밝힌 상태다.** 진단 기준이 진단하려는 결함을 통과시키고 있었다 |
| **곁들여 닫은 살림 셋** | ① `.claude/launch.json`(도구 자동 생성, 포트가 기기마다 다름)과 일회성 외부 프롬프트 원문을 추적에서 제외 — `.claude/` 아래 추적 대상 47개(브리지 45개 + 설정·훅 2개)는 남겨야 하므로 디렉터리째 무시하지 않고 파일만 지정했다 ② 열린 구간 파일을 **184KB에서 리네임만으로** 닫았다(`트랙B_Phase181-211.md`) — 앞선 두 번은 231KB·188KB까지 방치해 내용을 갈라야 했다 ③ eval 베이스라인 재측정 |
| **eval 판정을 내가 하지 않은 이유** | 하네스가 재측정을 권고한 원인이 `update-faq`·`release-notes`·`pre-deploy-check` 변경인데, **그 세 스킬 본문을 이번 세션에서 내가 고쳤다.** 하필 재측정을 유발한 항목에서 내 판단이 부풀려진다. 트리거는 저장소 접근을 막은 판정 에이전트에(24/24), 행동은 케이스마다 깨끗한 에이전트를 띄우는 오케스트레이터에(10/10) 맡겼다. **두 resultsHash 모두 직전과 동일** — 답이 바뀌지 않았다. 하네스 경고 2건 → 0건 |
| **검증** | Functions **77 suite 1,054테스트** · 뮤테이션 4건 · 하네스 18영역 0오류 |
| **남는 것** | ① 발견이 **최대 24시간 늦다** — 설계상 받아들인 지연이다 ② 표식이 있어도 **내용물이 온전한지는 확인하지 않는다.** 복원 리허설은 여전히 사람 몫이다 ③ 목록 조회 실패는 판정 보류라 로그만 남는다 — 권한이 **영구히** 깨지면 조용해진다(헛경보를 피한 대가) |

### Phase 213: 저장 못 한 기록에 대해 사실대로 말한다 — 그 정직함마저 헛돌던 곳 🔌📴

> 2026-09-06. 오프라인·지연 경로에서 사용자에게 하는 말 세 가지가 사실과 어긋나 고쳤는데, **정작 그 정직함을 켜는 스위치가 항상 켜져 있었다**는 것을 리뷰가 찾아냈다.

| 항목 | 내용 |
|------|------|
| **「다시 입력해 주세요」인데 무엇을 입력할지 안 알려 줬다** | 폐기된 기록은 payload를 그대로 들고 있는데 안내는 **건수만** 셌다. 차에서 내린 뒤에는 계기판 숫자를 기억으로 복원할 방법이 없어, **시키는 대로 할 수가 없는 안내**였다. 날짜·목적지·계기판을 함께 적는다 |
| **알리기도 전에 기록을 지웠다** | `drainFailedRecords`가 읽으면서 함께 비웠다. 읽은 직후 화면이 닫히면 기록은 사라지고 사용자는 끝내 듣지 못한다 — **유실을 알리는 장치가 유실되는** 모양이었다. peek → 알림 → clear로 갈랐다 |
| **모르는데 초록색으로 「저장했습니다」라고 했다** | 타임아웃은 실패가 아니라 **모름**이다. `persistentLocalCache`면 Firestore가 미전송 쓰기를 IndexedDB에 남겨 재전송하므로 사실상 맞는 말이지만, 사생활 보호 모드 등으로 `memoryLocalCache`로 떨어진 기기는 **탭을 닫는 순간 사라진다** |
| **그런데 그 내구성 판정이 사실상 항상 참이었다** | 리뷰가 짚었고 확인해 보니 사실이었다. `initializeFirestore`가 persistent 설정으로 반환하는 것은 **아무것도 보증하지 않는다** — SDK는 IndexedDB를 나중에 열고 사생활 보호 모드에서는 **비동기로 조용히** 실패한다. 실제 감지자는 같은 파일의 2단계 `checkIndexedDBAvailability()`인데 내 플래그를 건드리지 않았다. **정작 안내가 필요한 그 기기에서 계속 「저장했다」고 말했고, 공지에 적은 문구가 그대로 거짓이었다.** 판정을 2단계로 옮기고 기본값을 false로 뒀다 |
| **날짜를 알려 준다더니 언제나 비어 있었다** | `describeRecord`가 `data.date`를 읽는데 `buildLogData`가 만드는 것은 `timestamp`뿐이다. `date`는 옛 문서의 레거시다. Date는 `structuredClone`을 그대로 통과하므로 큐에서도 Date로 남아 있다 — 그것을 쓴다 |
| **내부 마커가 날짜로 찍힐 참이었다** | 오프라인 **수정**은 당일 운행의 `startDate`를 `deleteField()`로 지우는데, 큐가 그것을 `'__syncQueue.deleteField__'` 문자열로 바꿔 저장한다. 사용자에게 그 문자열이 날짜라고 보여질 참이었다. **Phase 207(#323)에서 내가 넣은 `deleteField`와 이번 변경이 만나 생긴 조합**이다(리뷰 대응 커밋에는 #330이라고 잘못 적었다 — `git log -S` 로 확인하니 둘 다 #323이었다) |
| **스토어를 통째로 비워 사이에 들어온 폐기가 함께 사라졌다** | 읽고 지우기 사이에 서비스워커 flush가 새 폐기를 밀어 넣을 수 있다. **알린 id만** 골라 지운다 |
| **같은 토스트가 두 번 떴다** | `online`·`visibilitychange`는 잠금 화면을 풀며 통신이 돌아올 때 같이 발화한다. `flushQueue`와 같은 방식으로 진행 중 Promise를 공유한다 |
| **배선을 이 세션에서 세 번째로 놓쳤다** | `describeRecord`만 테스트해서 `buildFailureMessage`가 그것을 쓰지 않아도 전부 초록이었다. 앞서 `beforeBreadcrumb`·`beforeSendSpan`에서 같은 실수를 했다(Phase 211). **순수 함수는 테스트하고 배선은 안 하는 패턴**이 세 회차 연속 반복됐다 |
| **공지를 두 번 썼다** | 세 번째 항목은 **배포되지 않을 동작**을 설명하고 있었다 — 내구성 판정이 헛돌았으니 「폴백 기기에 다르게 안내한다」가 거짓이었고, 첫 항목의 날짜도 늘 비어 있었다. 두 번째(알린 뒤에 정리한다)는 처음부터 실제 동작이었고 재작성은 보강이다. 리뷰 뒤 셋을 실제 동작에 맞춰 다시 썼다 |
| **사용자가 일하는 방식을 짚었다** | 「하나 고치고 CI 돌리고 배포하고를 반복하는 것 말고는 없니?」 재어 보니 PR당 30~40분이고, pre-push 훅(`test`+`build`+`audit`, ~3분)이 **내 수동 실행과 CI를 통째로 중복**하고 있었다. ① 관련 없는 살림은 한 PR로 묶고 ② 수동 전체 스위트 실행을 그만두고 pre-push를 단일 로컬 게이트로 삼고 ③ 겹치지 않는 파일은 병행한다. 원인은 **사용자가 이미 저장해 둔 선호(「연관 변경은 한 PR로 묶기」)를 내가 어기고 있던 것**이다 |
| **검증** | 뮤테이션 **3건 + 리뷰 대응 5건** · lint · type-check · 하네스 0오류 0경고 · CI 전 체크 통과 · 배포 후 프로덕션 번들에서 2단계 내구성 판정(`$e=Me&&e===!0`)·`__syncQueue.` 마커 2종·id 지정 삭제(`store.delete`) 실물 확인 |
| **남는 것** | ① 이미 초기화된 인스턴스를 재사용하는 경로는 어느 쪽인지 알 수 없어 **내구성 없음으로 본다** — 모르면서 있다고 말하는 것보다 낫다는 판단이고, 보수적 오판은 남는다 ② 2단계 판정이 끝나기 전(최대 2초) 타임아웃이 나면 false로 읽혀 **내구성 있는 기기도 경고를 본다** ③ 상세는 3건까지만 적고 나머지는 「외 N건」이다 — 오래 오프라인이었으면 못 보는 항목이 생긴다 |

### Phase 214: 안내대로 갔는데 그 버튼이 없었다 — 하이패스 잔액 정정 경로 🖱️♿

> 2026-09-06. 사용자가 "하이패스 잔액 안내 공지 확인해줘"라고 했고, 실물 화면과 대조해 보니 **Phase 210에서 쓴 FAQ가 PC에서는 찾을 수 없는 버튼을 가리키고 있었다.**

| 항목 | 내용 |
|------|------|
| **연필은 있는데 PC에서는 안 보인다** | `opacity-100 pointer-fine:opacity-0 pointer-fine:group-hover:opacity-100` — 마우스를 쓰는 기기에서는 **카드에 올려야** 나타난다. 2026-07 공지가 "터치 기기는 항상, PC는 올렸을 때"라고 밝힌 의도된 동작이다. 그런데 **관리자 업무는 대개 PC에서 한다.** Phase 210의 전제가 「찾아온 사람이 답을 얻는 곳」이었는데 바로 그 자리에서 깨졌다. 고칠 칸 이름(`[현재 잔액]`)도 빠져 있었다 |
| **통계 FAQ는 없는 메뉴를 가리켰다** | `hipass-stats`가 "관리자 메뉴의 '하이패스 일지'"라고 하는데 그런 항목이 관리자 메뉴 10개에 없다. 실제는 `[일지 관리]` → `[하이패스일지]` 탭(띄어쓰기도 없다). 게다가 그 통계 버튼은 **충전 기록이 0건이면 렌더되지 않는다** — 안내대로 가도 없는 경우가 하나 더 있었다 |
| **낭독기에는 이름 없는 버튼이었다** | 수정·삭제 **둘 다** `aria-label`이 없었다. 처음에 "삭제에는 있다"고 보고했는데 그건 `ConfirmModal`의 `title`이었다 — 버튼이 아니라 모달 제목을 보고 착각했다. `OrgSitesSection`이 쓰던 형식을 따랐다 |
| **그 aria-label이 새 유출 경로를 열 뻔했다** | 카드번호를 넣고 "aria-label은 스크러버가 지우니 안전하다"고 PR에 적었는데, **breadcrumb 경로에서만 참이었다.** 리뷰가 짚었고 확인해 보니 INP 스팬 이름으로는 그대로 나간다. 특히 나쁜 점은 카드번호가 지금까지 **텍스트 노드에만** 있어 나갈 경로가 아예 없던 값이라는 것이다 — 접근성을 고치려다 **"안 나가던 값"을 "샘플링되어 나가는 속성"으로 옮길 뻔했다.** 차량명으로 바꿨다(이 경로 자체는 Phase 215에서 닫았다) |
| **설명서에 같은 결함이 그대로 있었다** | `manualSections.json`이 "주유 탭과 하이패스 충전 탭"이라는 **없는 화면**을 안내하고 있었다. FAQ만 고치고 두면 같은 사용자가 두 문서에서 서로 다른 경로를 본다. 리뷰가 `grep`으로 찾아냈다 |
| **낭독기만 챙기고 키보드를 뺐다** | hover 전용이라 데스크톱에서 Tab으로 이동하면 **이름은 읽히는데 버튼은 보이지 않았다.** 접근성을 고치는 회차에 이걸 빼는 것은 앞뒤가 안 맞아 `pointer-fine:group-focus-within:opacity-100`을 더했다 |
| **관행을 알고 어긴 것** | `release-notes` 스킬 §6-2는 배포된 공지 항목을 건드리지 말라고 못박는다. 같은 날 배포분의 정정이고 실제 안내는 FAQ가 담당하므로 새 항목을 만들지 않았는데, `useReleaseNotesStatus`가 배너를 `date` 최댓값으로만 판정하므로 **이미 읽은 관리자는 고쳐진 문구를 다시 보지 못한다.** 그 한계를 PR에 남겼다 |

### Phase 215: 이름이 틀렸다고 지적까지 틀린 것은 아니었다 — 추적 스팬 이름 🔒🏷️

> 2026-09-06. Phase 211에서 **"이 설치본에 없는 패키지"라며 반려한 판단이 틀렸다.** 패키지 이름만 달랐을 뿐 경로는 실재했고, 그 사이 두 회차 동안 열려 있었다.

| 항목 | 내용 |
|------|------|
| **기각의 근거가 이름 하나였다** | 당시 리뷰는 `@sentry-internal/browser-utils`를 인용했고 그 패키지는 정말 없었다. 그래서 **지적 자체를 없는 문제로 처리했다.** 같은 코드가 `@sentry/browser-utils`로 설치돼 있다는 것은 확인하지 않았다. "리뷰를 그대로 믿지 않아 다행이었다"고 적었는데, 사실은 **실재하는 유출을 두 회차 방치한 기록**이었다 |
| **새는 자리는 셋** | ① `metrics/inp.js`가 스팬 **이름**을 `htmlTreeAsString(target)`으로 만든다 — `enableInp` 기본값이 true라 클릭 한 번이 그대로 이름이 된다 ② `browserMetrics.js`의 `_setWebVitalAttributes`가 pageload 루트 스팬에 `lcp.element`·`cls.source.N`을 채운다 ③ `htmlTreeAsString`은 `aria-label`·`title`·`alt`를 **설정과 무관하게 항상** 붙인다. 우리 `beforeSendSpan`은 `span.data`만 씻고 있었고, **이름은 breadcrumb 훅도 `scrubSpanData`도 보지 못하는 자리**다 |
| **한 곳에서 다 막힌다** | standalone 스팬(INP)은 트랜잭션이 아니라 스팬 봉투로 따로 나가서 훅을 건너뛸 줄 알았는데, `createSpanEnvelope`가 같은 콜백을 태운다. 미샘플링이면 아예 전송되지 않으므로 **훅을 우회해 나가는 경로가 없다** |
| **필드 이름 함정이 없다는 것까지 봤다** | `getSpanJSON()`이 `description`·`data`로 반환한다 — 테스트가 먹이는 필드와 프로덕션이 받는 필드가 같다. 여기가 달랐다면 **"테스트는 초록인데 실물은 no-op"**이 될 자리였다. 앞선 세 회차가 배선에서 연달아 미끄러진 뒤라 이번엔 먼저 확인했다 |
| **호출부를 전수로 셌다** | 리뷰가 `htmlTreeAsString` 호출부 12곳을 표로 대조해, 지금 활성인 것(INP 이름·pageload 속성 2종·breadcrumb)과 잠든 것(`_experiments`·스트리밍 전용)을 갈랐다. 잠든 것도 플래그 하나로 켜지므로 함께 잡았다. **breadcrumb 하나뿐이라던 Phase 211의 단언이 여기서 반증됐다** |
| **내 주석이 잠든 파일을 가리켰다** | 근거로 `metrics/lcp.js`·`cls.js`·`webVitalSpans.js`를 인용했는데 셋 다 이 설정에서 한 줄도 돌지 않는다. 실제로 도는 것은 `browserMetrics.js`다. Phase 211이 스스로 **"틀린 근거가 달린 방어는 다음 사람이 지워도 이상하지 않다"**고 적었으므로 그대로 둘 수 없었다 |
| **테스트 입력이 비현실적이었다** | 처음에 `button[aria-label="…"].btn-icon`으로 썼는데, `_htmlElementAsString`의 실제 순서는 태그 → `#id` → `.class` → **속성**이라 속성 뒤에는 아무것도 오지 않는다. 기존 경계 판정이 꼬리를 삼킨 게 아니라 내 입력이 틀렸다 |
| **검증** | 뮤테이션 3건(배선 제거 / 속성 루프 무력화 / `scrubSpanName` 무력화) · Vitest 172파일 **2,105개** · 하네스 0오류 0경고 · 배포 후 프로덕션 번들에서 `beforeSendSpan(t){const n=L(t.data),r=j(t.description);…}`와 키 판정 정규식 실물 확인 |
| **남는 것** | ① **Sentry에 이미 쌓인 개인정보는 코드로 지워지지 않는다** ② resource 스팬 **이름**은 쿼리 포함 전체 URL이라 Storage 이미지의 `?alt=media&token=…`이 실릴 수 있다(`url.full`은 막히지만 이름은 아니다) — 사람 이름은 아니라 별건으로 남긴다 ③ `beforeSendSpan`이 falsy를 반환하면 드롭이 아니라 **스크럽 전 원본**이 나간다. 지금은 항상 객체를 돌려주지만, 나중에 "이 스팬은 버리자"고 `null`을 반환하면 정반대가 된다 |

| **`Vary`가 캐시에 있는 것을 못 찾게 했다** | 미리보기 서버에서 재현됐다 — `cache.match`는 미스인데 `import()`는 히트했다. 캐시 조회가 응답의 `Vary`(호스팅은 `Accept-Encoding`을 붙인다)에 걸린 요청 헤더까지 맞아야 히트하기 때문이다. 담을 때와 오프라인에서 꺼낼 때가 조금이라도 다르면 **캐시에 있는데도 네트워크로 나가고, 오프라인이면 그대로 실패한다.** 해시 URL에는 `Vary`로 구분할 것이 없으므로 `ignoreVary: true`로 굳혔다 |
| **오프라인 범위는 사용자가 정했다** | "운전자 경로만 오프라인 되면 된다"는 답을 받고 그 범위로 한정했다. `warmDriverRoutes`가 `EmployeeLayout` 진입 시 운전자 화면 9종을 유휴 시점에 **순차로**(느린 회선에서 현재 화면과 대역폭을 다투지 않게) 미리 받는다. 호출 위치가 곧 역할 판정이다 — 슈퍼관리자 화면에서는 마운트되지 않으므로 역할 분기를 따로 두지 않았다. 데이터 절약 모드에서는 워밍하지 않는다 |
| **게이트를 두 방향으로 뒀다** | 부풀기(전송 예산 130KB)와 **셸 유실**(index.html과 그 참조 자산이 매니페스트에 전부 있는지 대조, fail-closed) 둘 다. 후자가 핵심이다 — `globPatterns`가 엔트리 파일명과 어긋나면 프리캐시가 조용히 비고 **오프라인이 통째로 죽는데, 그 실패는 배포 후 현장에서야 드러난다.** `dist/sw.js`에서 매니페스트를 실제로 빼서 항목 하나를 지워 보고 종료 코드 1을 확인했다. 워밍 목록이 라우트와 어긋나는 드리프트는 단위 테스트가 양방향으로 잡는다(빠짐 = 오프라인 구멍 / 덧붙음 = 좁힌 효과 상실) |
| **테스트 관측 지점을 한 번 잘못 잡았다** | `vi.mock` 팩토리에서 로드된 모듈을 기록해 셌는데, ESM 모듈 레지스트리는 첫 로드 이후 팩토리를 다시 평가하지 않는다 — 두 번째 테스트부터 기록이 비어 실패했다. 실행 여부의 계약은 "워밍을 예약했는가"이므로 스케줄러(`requestIdleCallback`)를 관측하도록 바꿨다 |
| **검증** | lint · type-check · Vitest **173파일 2,112개** · 에뮬레이터 E2E 13건(오프라인 큐 동기화 포함) · chromium E2E 14건 · 빌드/번들 예산 · 프리캐시 게이트 양쪽 상태(정상 0 / 셸 유실 1) · **미리보기 서버를 끄고 오프라인 실측** — 셸이 캐시에서 렌더되고, 지연 라우트(`/faq`)가 의존 청크(`faqData`)까지 캐시돼 완전히 열리며, 워밍 대상이 아닌 관리자 청크(recharts)는 열리지 않는 것까지 확인 |
| **남는 것** | ① **첫 세션에는 워밍이 캐시에 담기지 않는다** — `clientsClaim`을 쓰지 않아(E2E가 깨지므로 의도된 설계) 서비스 워커가 첫 로드에서 페이지를 제어하지 않고, 그때의 `import()`는 워커를 지나지 않는다. 앱을 한 번 다시 열면 해소되지만, **설치 직후 곧바로 신호 없는 곳으로 가면 운전자 화면이 열리지 않는다**(종전 전량 프리캐시에는 없던 공백이다) ② 운전자 경로의 오프라인을 **인증 상태로 E2E 검증하지 못했다** — 에뮬레이터 하네스가 dev 서버라 프로덕션 서비스 워커가 없다. 공개 지연 라우트(`/faq`)로 같은 기제를 대리 검증했다 ③ 하루 약 1,000회 설치 중 익명 방문자 비중과 캐시 미유지 비중을 가르지 못했다(Hosting 요청 로그가 Cloud Logging으로 나가지 않는다) — 어느 쪽이든 이 수정이 함께 줄인다 ④ 배치 두 건(지난달 재집계 창 닫기 · 휴면 기관 스킵)과 취소 예약 서버 필터는 착수하지 않았다

### Phase 218: 내가 만든 수정을 내 테스트가 반증했다 — 권한 오류 뒤의 빈 화면 🧪🔍

> 2026-09-09. 사용자가 프로덕션 콘솔 로그(`permission-denied` 무리)를 보내며 "일시적인 것일까?"라고 물었다. **화면이 빈 채로 남는다고 판단해 수정까지 만들었는데, 그 수정을 검증하려고 쓴 테스트가 원본 코드에서 그대로 통과했다.**

| 항목 | 내용 |
|------|------|
| **증상은 이미 문서화된 것과 같았다** | 기관 상태 감시·예약 조회·driveLogs가 한꺼번에 거부됐다. `firebaseAuth.ts`가 적어 둔 목록과 같은 집합이다. 다만 그 파일이 막은 것은 **persistence 이전 구간**이고, 이번 원인은 달랐다 — 부팅 시 캐시된 커스텀 클레임이 낡으면 `useAuth`가 토큰을 백그라운드로 갱신하면서 **로딩을 막지 않는다**(의도된 설계다: "첫 쿼리가 permission-denied를 받으면 retry+refresh가 자동 복구하므로 로딩을 막지 않는다"). 그래서 첫 쿼리 무리가 옛 토큰으로 나간다 |
| **내 추론이 한 단계를 빠뜨렸다** | "페치가 `useMemo(…, [orgId, user, …])` 안에 있고 그 의존성은 리렌더로 바뀌지 않으니 재시도가 오지 않는다"고 판단했다. 빠뜨린 것은 **`use()`로 서스펜드된 렌더는 커밋되지 않고 버려진다**는 것이다. 프라미스가 풀리면 React가 렌더를 재생하고, 그 자리에서 `useMemo`가 다시 돌아 — 실패 경로가 비워 둔 캐시 때문에 — 새 페치가 시작된다. 갱신된 토큰으로 그것이 성공하므로 **빈 데이터는 화면에 닿기 전에 폐기된다** |
| **반증한 것은 테스트였다** | 재시도 로직을 넣고 테스트를 썼는데, 원본 코드에 대고 돌리니 11개 중 10개가 통과했다(실패한 1개는 "주기당 시도 2회"라는 내 구현 전용 단정이었다). 코드를 읽고 세운 가설을 **실행으로 확인하지 않았다면** 이미 되는 일을 한 번 더 하는 코드를 배포했을 것이다 — 거부 경로의 read만 두 배가 된다 |
| **하네스가 그 오진을 통과시킬 참이었다** | `useAuth` 목이 `() => ({ user: {...}, userData: {...} })`로 **매 렌더마다 새 객체**를 돌려줬다. 그러면 `useMemo` 의존성이 렌더마다 바뀌어 리렌더마다 재페치가 일어난다 — 프로덕션의 Firebase User는 같은 인스턴스가 유지되므로 실제와 다르다. 이 상태에서는 재시도 계약을 어떻게 망가뜨려도 초록이었다(하네스가 대신 다시 받아 왔다). 참조를 안정화했고, **이 수정이 없었다면 잘못된 판단도 초록으로 통과했다** |
| **남긴 것은 테스트뿐** | 프로덕션 코드는 한 줄도 바뀌지 않았다. 대신 복구가 성립하는 **세 조건**을 결과로 고정했다 — ① 실패 경로가 캐시를 비운다 ② 페치가 `useMemo` 안에 있다 ③ 실패를 throw가 아니라 resolve로 돌려준다. 어느 하나만 손대도 조용히 깨져 예약이 있는 운전자가 "예약 없음"을 본다(차를 두고 갈 수 있는 화면이다) |
| **검증** | 뮤테이션 3건(캐시 비우기 제거 / 토큰 갱신 제거 / resolve→throw — 각 2건 실패) · Vitest 174파일 **2,123개** · 하네스 0오류 · CI 전 체크 |
| **남는 것** | ① 계속 거부되는 경우의 호출 **총량**은 고정하지 않았다 — 서스펜스 재생이 몇 주기를 도는지는 스케줄링에 달려 관측 창이 주기를 중간에 끊는다. 결과(빈 데이터로 대체·화면 생존)만 고정했다 ② 이 복구가 React 내부 동작(커밋되지 않은 렌더의 재생)에 의존한다 — 메이저 업그레이드 때 이 테스트가 먼저 깨지는 것이 의도다 ③ 사용자가 실제로 빈 화면을 봤는지는 확인하지 못했다. 로그만으로는 갈리지 않고, 코드상으로는 커밋 전에 폐기된다 |

### Phase 219: 빈 결과도 1 read다 — 야간 집계가 매일 다시 계산하던 것 💰🌙

> 2026-09-09. Phase 217에서 측정한 야간 배치 21,500 read 중 `dailyAggregation`(≈10,600) 쪽을 줄였다. **금액이 아니라 무료 할당량이 이유다** — 배치가 5만/일의 43%를 사용자 접속 전에 쓴다.

| 항목 | 내용 |
|------|------|
| **내가 앞서 말한 절감 폭이 과장이었다** | 사용자에게 "2.15만 → 5천"이라고 했는데, 문서 수로 검산하니 그 두 항목은 `dailyAggregation`(10,600)만 건드리고 `computeDashboardStats`(9,700)는 그대로였다. 실제는 **21,500 → 대부분의 밤 약 15,000**(43% → 31%)이다. 측정 전에 숫자를 말한 것이 원인이고, PR과 사용자 보고에서 정정했다 |
| **가장 큰 몫은 "같은 답을 매일 다시 계산"이었다** | 지각·소급 입력을 흡수하려고 당월+전월을 매일 재집계했는데, 전월은 월초 며칠이 지나면 더 들어올 것이 없다. 창 안 driveLogs 5,428건 중 전월분 약 4,000건을 그달 말일까지 매일 다시 스캔했다. 기준일 10일까지만 2개월로 두고 그 뒤로는 1개월이다 |
| **기준 시각이 −3h라는 것이 경계의 핵심이었다** | `getRecentMonthWindows`가 실행 시각 −3h를 기준으로 대상 월을 정하므로, 1일 02:00 실행의 기준일은 **전월 말일**이 된다 → 그날은 1개월(막 끝난 달)만 집계하고, 2일부터 11일까지 2개월을 돈다. 날짜별로 테스트에 고정했다 — 이 값을 만지면 경계가 조용히 어긋난다 |

| **`not-in`을 쓰지 않은 이유** | Firestore의 `not-in`은 **필드가 없는 문서를 제외**한다. status가 붙기 전의 옛 기관이 조용히 집계에서 빠지므로, 기관 목록은 어차피 전부 읽는 것을 이용해 메모리에서 갈랐다(읽기 비용도 같다). 그 경우를 테스트로 고정했다 |
| **게이트가 공짜인 자리를 골랐다** | 차량·구성원 판정에 쓰는 두 쿼리는 어차피 이름 맵을 만들려고 걸던 것이다. 새로 무언가를 읽어서 판정하면 절감분을 스스로 깎으므로, **이미 읽는 값으로 판정할 수 있는 곳**만 게이트로 삼았다 |
| **검증** | 뮤테이션 3건(상태 게이트 / 차량·구성원 게이트 / 재집계 창 고정 — 각 1~3건 실패) · Functions 77 suite **1,062 테스트** · 에뮬레이터 4 suite 20 테스트 · 배포 후 `nightlyStatsBatch` updateTime이 배포 창 안(`02:04:17Z`)·state ACTIVE 확인 |
| **남는 것** | ① **유예일(10일)이 지난 뒤 들어온 전월 소급 입력은 야간 배치가 반영하지 않는다.** 이 앱은 소급 입력을 지원하므로(Phase 207) 실제로 생길 수 있다 — `backfillMonthlyStats` 콜러블을 큰 recentMonths로 1회 호출한다. 10일이 실무 월 마감과 맞는 값인지는 사용해 보며 조정할 값이다 ② 오늘 02:00 배치는 배포 전에 돌았으므로 **첫 적용은 2026-09-10 02:00**이다 — 절감 실측은 그 뒤에 확인해야 한다 ③ `computeDashboardStats`(≈9,700)는 손대지 않았다. 일별 롤업으로 바꾸면 수만 → 수십이 되지만 금액이 월 ₩2,100인 지금은 과하다(읽기 하루 50만 초과 시 재검토) ④ 차량·구성원이 모두 사라진 기관의 통계는 마지막 값에서 멈춘다 — 원본이 바뀌지 않으므로 값은 같고 차량 이름만 "알 수 없음"으로 남을 수 있다 |

### Phase 222: Sentry 알림 하나가 세 갈래로 — 갱신 버튼 비용·노이즈 필터·그 필터가 가릴 위험 🔔💸🔐

| **⚠️ 원인 진단이 틀렸고, 틀린 자리에 다른 구멍이 있었다** | 필터를 넣으며 "`terminate()`가 실패해 뒤따르는 `clearIndexedDbPersistence()`가 실행되지 않았다"고 사용자에게 말했다. **틀렸다** — `handled=no`인 미처리 거부였으므로 `terminate()`가 돌려준 프라미스는 거부되지 않았고(거부됐다면 우리 `await`가 잡아 `handled=yes`가 된다), 그 경우 폐기는 실행됐다. 그런데 **실제 구멍은 따로 있었다**: 함수 주석이 이미 인정한 다중 탭 경로다 — `persistentMultipleTabManager`로 캐시를 공유하므로 다른 탭이 붙어 있으면 폐기가 `failed-precondition`으로 거부되고, **포기한 사실이 어디에도 남지 않아 캐시가 영구히 남았다**(2026-07-10 감사 #8이 막으려던 상태) |
| **필터가 그 사실을 더 안 보이게 만든다** | 노이즈 보고를 줄이는 것 자체는 맞지만, 같은 계열의 진짜 실패도 함께 조용해진다. 그래서 필터와 잔여 위험을 **같은 회차에** 닫았다. 시도 **전에** `localStorage`에 미완료 표식을 남기고 **성공했을 때만** 지운다. 다음 부팅에서 인스턴스를 만든 직후 — 첫 쿼리가 걸리기 전 — 에 다시 시도하므로 **"다른 탭이 닫힌 첫 부팅"**에 정리된다 |
| **`localStorage`인 것이 요점이다** | 로그아웃은 곧 하드 내비게이션이고, 실패의 대표 원인인 다중 탭은 **브라우저를 닫아야 풀리는** 경우가 많아 세션 저장소로는 그 부팅까지 살아남지 못한다. `sessionStorage`로 옮기는 뮤테이션도 테스트가 잡는다 |
| **테스트를 위해 모듈을 하나 뺐다** | `firebase.ts`는 모듈 로드 시 Firebase 전체를 초기화해 단위 테스트로 들이기 어렵다. 그런데 이 판정은 보안 관련이라 테스트가 필요했으므로 표식·순서 계약만 `offline/cacheClearMarker.ts`로 떼고 실제 `terminate`·`clearIndexedDbPersistence`는 호출부가 주입한다 |
| **검증** | 뮤테이션 **8건** — 필터 2(패턴 제거 / 이름 무관하게 넓힘) · 안내 문구 1 · 표식 계약 4(시도 후에 적음 / 실패해도 지움 / 표식 없이도 시도 / sessionStorage) · lint · type-check · Vitest **176파일 2,151개** · 에뮬레이터 E2E 13건(부팅 경로 로드 확인) · 하네스 0오류 |

### Phase 223: 세션을 가장 먼저 지워지는 자리에 두고 있었다 — 그리고 그것을 볼 계측도 상수였다 📱🔍

> 2026-09-11. 사용자가 "핸드폰에 PWA 설치했는데 20분 정도 뒤에 다시 들어갔더니 로그아웃이 됐다"고 했다(안드로이드 Chrome). **앱에는 자동 로그아웃도 세션 타임아웃도 없고** Firebase 리프레시 토큰은 스스로 만료되지 않는다 — 기기에 저장된 세션이 사라진 것이고, 그 사라짐을 우리가 자초하고 있었다.

| 항목 | 내용 |
|------|------|
| **`setPersistence` 한 줄이 세션을 가장 약한 저장소에 고정했다** | `getAuth()`의 기본 우선순위는 `[IndexedDB, localStorage, sessionStorage]`인데 `firebaseAuth.ts`가 `setPersistence(browserLocalPersistence)`로 **localStorage에 못 박고** 있었다. 휴대폰에서 가장 먼저 비워지는 저장소다 |
| **그 호출은 설정 변경이 아니라 이전이라, 사본까지 지운다** | 세션이 IndexedDB에 있으면 **읽어서 지우고** localStorage에 다시 쓴다 — Phase 149가 스택 트레이스로 이미 확인해 주석에 적어 둔 사실이다. 결과적으로 **사본이 한 곳에만** 남는다. 그때는 그 사실을 "부팅 중 빈 구간"의 원인으로만 읽었고, **"남는 사본이 하나뿐"이라는 다른 절반은 읽지 않았다** |
| **모바일이면 1초 폴링이고, 한 번 비면 그대로 로그아웃이다** | SDK 소스에서 확인했다 — `fallbackToPolling = _isMobileBrowser()`(iOS·Android 모두 참). storage 이벤트 대신 1초마다 `localStorage.getItem`을 읽고, 값이 비면 **재시도도 다른 저장소 조회도 없이** `_updateCurrentUser(null)`로 간다. ①과 겹쳐 "휴대폰에서만, 잠깐 뒀다 열면" 이 된다 |
| **주석이 막아 둔 길이 사실은 막혀 있지 않았다** | Phase 149는 "기본 스택으로 되돌리면 **기존 사용자가 1회 로그아웃될 위험**(218개 기관)"이라며 근본안을 접었다. 그런데 `PersistenceUserManager.create`는 우선순위 목록 **전체**를 뒤져 세션을 찾고 1순위로 **옮겨 쓴 뒤** 나머지를 지운다(`@firebase/auth`). **그 위험은 없었다.** 210개+ 기관이 한 번에 로그아웃되는 것이 이 변경에서 가장 값비싼 실패라 코드를 읽는 데서 멈추지 않고 E2E로 재현했다 — 세션을 localStorage로 옮기고 IndexedDB 원본을 지운 뒤 새로고침해도 로그인이 유지되고 세션은 IndexedDB로 돌아온다. 원래 이 줄이 막으려던 "새 탭 로그아웃"은 나중에 붙은 `authStateReady()` 대기가 막는다 — **그쪽이 진짜 처방이었다** |
| **이 증상만 유일하게 아무 기록이 없었다** | 앱이 켜져 있는 동안 끊기는 경우는 `useAuth`가 원인까지 분류해 Sentry로 올린다(Phase 185·194). 그런데 **"껐다 켰더니 로그인 화면"은 `main.tsx`가 조용히 경량 진입점을 띄우고 끝**이라 이벤트도 토스트도 없었다 — 이번 제보가 정확히 그 모양이고, 그래서 원인을 단정할 근거가 처음부터 없었다. 세션 없이 부팅했는데 세션이 있었어야 하는 기기면 증거를 적어 두고, 다시 로그인해 `appEntry`가 뜰 때 올린다(경량 경로에서 `@sentry/react`를 끌어오면 lightEntry 분리로 아낀 것을 되돌린다) |
| **⚠️ 그 계측이 사실상 상수만 찍는다는 것을 머지 전 리뷰가 반증했다** | 세 가지가 겹쳤고 셋 다 같은 종류다. ① **증거를 Firebase 초기화 뒤에 읽었다** — `create`가 1순위 아닌 저장소의 세션 키를 이미 지웠고 가용성 검사가 `firebaseLocalStorageDb`를 이미 만들었다. "localStorage에 세션이 있었나"는 언제나 아니오, "auth DB가 있었나"는 언제나 예. → 부팅 스냅숏을 **모듈 평가 시점에 동기적으로** 찍는다(SDK의 정리는 전부 마이크로태스크 뒤다). ② **문자열 증거가 Sentry에 도착하지 않았다** — `sentryScrub`은 자유 입력 유출을 막으려 허용 목록 밖 문자열을 통째로 지운다. `at`·`userAgent`가 `[redacted string(n)]`이 된다. → 숫자·불리언으로만 구성하고 `uid`만 따로 싣는다(`isIdKey`가 통과시킨다). 문자열이 섞이면 실패하는 계약 테스트를 뒀다 |
| **정작 가장 유력한 시나리오를 구조적으로 볼 수 없었다** | 발동 조건인 재방문 힌트가 세션과 **같은 localStorage**에 있었다. 저장소 축출은 localStorage와 IndexedDB를 **함께** 비우므로 힌트도 사라지고, 그 부팅은 "처음 온 사람"과 구분되지 않는다 — **보고 싶은 사건만 침묵하는 계측**이었다. 같은 표식을 쿠키(`vdl_seen`, 값 `1`뿐)에도 남긴다. 쿠키는 용량 축출 대상이 아니라 그 구분이 된다. 앱 키 개수에서 힌트를 빼 `appKeys === 0`이 실제로 "비워졌다"를 뜻하게 했다(종전에는 힌트 때문에 하한이 1이라 도달 불가였다) |
| **오탐 둘도 같은 회차에 닫았다** | ① 서버가 끊은 세션(계정 비활성화·소속 변경·토큰 무효화)이 다음 부팅에서 **원인 없이 한 번 더** 올라갔다 — `useAuth`가 이미 보고한 사건이므로 `commitSignedOut`에서 표식을 내린다. ② `main.tsx`에서 "판정 먼저, 표식 내리기 나중"이 **두 줄의 순서로만** 유지됐다. 뒤바꿔도 타입도 테스트도 통과하고 계측만 조용히 죽는다 — `noteUnauthenticatedBoot()` 하나로 묶었다 |
| **CodeQL 고위험이 붙었고, 억제 대신 이름을 고쳤다** | `js/clear-text-storage-of-sensitive-data` — "자격증명을 평문으로 저장한다". 실제로는 예전 사본의 **존재 여부 불리언**이고 값은 읽지도 싣지도 않는데, 필드 이름 `authKeyInLocalStorage`의 `authKey`만 보고 판정한 것이다. 오탐이지만 억제 주석을 달지 않았다 — 그렇게 읽히는 이름은 다음 사람에게도 같은 오해를 만들고, 억제는 쌓이면 진짜 경보를 가린다. `legacyLocalCopy`가 하는 일도 더 정확하다 |
| **롤아웃 순간의 한 번은 남고, 그래서 공지에 적었다** | 신버전이 부팅하면 localStorage 사본을 지우는데, 같은 브라우저에 **구버전 탭**이 떠 있으면 그 탭의 리스너가 삭제를 로그아웃으로 읽는다. 우리가 막을 수 있는 것이 아니라 공지에서 밝혔다("여러 개 띄워 두셨다면 그 순간 한 번은 — 그 한 번뿐입니다"). 리뷰가 없었으면 "다시 로그인하실 필요 없어요"가 그 사용자들에게 거짓이 될 뻔했다 |
| **곁들여 — 갱신 비용 안내를 도로 뺐다** | Phase 222에서 "운영자가 한 명이라 화면에 적어 두는 것이 가장 값싼 대책"이라며 넣은 문구를, **그 운영자 본인이 필요 없다고 해서** 배포 이틀 만에 뺐다(테스트도 함께). 비용 사실 자체는 Phase 222에 남아 있으므로 잃는 것은 없고, **읽는 사람이 한 명인 화면에서는 그 한 명의 판단이 근거보다 앞선다.** 슈퍼관리자 전용 화면이라 공지 대상도 아니다 |
| **검증** | Vitest **177파일 2,177개** · 에뮬레이터 E2E **15건**(신규 2건 — 저장 위치 고정 · 옛 세션 이관) · lint · type-check · 빌드(번들 예산 이내) · 하네스 Doctor 0오류 · CI 전 체크 · **배포 후 프로덕션에서 옛 빌드의 표식 문자열(`persistence 설정 실패`)이 스크립트 12개 어디에도 없음을 실물 확인** · 공지 실물 확인 |
| **남는 것** | ① **원인을 단정하지 않았다** — 제보 시점의 기록이 없어서다. 계측이 그 공백을 메우므로 재발 시 어느 저장소가 비었는지까지 남는다 ② 저장소 축출 대비(`navigator.storage.persist()`)와 Tmap 지오·경로 캐시의 **크기 상한 부재**(현재 무제한)는 사용자가 고른 범위 밖이라 뺐다 ③ 쿠키까지 지워지는 경우(사이트 데이터 삭제·ITP)는 여전히 "첫 방문"과 구분되지 않는다 — 사용자가 의도한 삭제라 받아들인 한계다 ④ E2E는 chromium 데스크톱 1개에서만 돌아, 이번 버그의 본체인 **모바일 폴링 경로는 E2E로 검증되지 않는다**(그 경로를 없앤 것이 수정이다) ⑤ **실기기 확인은 아직 사용자 몫**이다 |

### Phase 224: 삭제는 되는데 수정은 안 되던 자리 — 관리자의 주유·하이패스 기록 정정 ⛽✏️

> 2026-09-11. 사용자가 받은 기관 의견에서 시작했다 — *"지출결의서와 주유일지를 체크하는 과정에서 주유량에 오류가 있으면 주유 당사자만 수정이 가능합니다."* **막고 있던 것은 권한이 아니라 화면이었다.**

| 항목 | 내용 |
|------|------|
| **Rules는 처음부터 열려 있었다** | `firestore.rules`의 fuelLogs·hipassCharges update에 `isOrgAdmin(resource.data.organizationId)` 분기가 이미 있었다. 즉 서버는 기관 관리자의 수정을 허용하는데 관리자 화면에는 **되돌릴 수 없는 삭제 버튼만** 있었다 — 현장에서는 "지우고 직원에게 다시 입력 요청"이라는 더 나쁜 우회를 쓰게 된다. 운행일지·정비일지는 이미 관리자 수정이 되므로 주유·하이패스만 남아 있던 구멍이고, 그래서 이번 작업의 본체는 기능 추가가 아니라 **비대칭 해소**다 |
| **하이패스는 기록만 고치면 거짓이 된다** | 충전 기록은 생성 시 카드 잔액을 그만큼 **올린다**(`useHipassCharge`). 즉 잔액은 앱이 유지하는 파생 값이지 사람이 적어 두는 메모가 아니다 — 금액만 정정하면 앱이 들고 있는 잔액이 조용히 틀어진다. 차액만큼 카드 잔액을 함께 조정하되, **얼마가 어떻게 바뀌는지 확인창에 숫자로** 보여 준다(`80,000원 → 60,000원 (−20,000원)`). 카드가 이미 삭제됐으면 그 사실을 알리고 기록만 고친다 |
| **기록 쓰기는 성공하고 잔액만 실패하는 경우를 갈랐다** | 한 try로 묶으면 "수정에 실패했습니다"가 **거짓말**이 된다(기록은 이미 바뀌었다). 잔액 조정만 따로 잡아 "기록은 수정됐지만 카드 잔액 조정에 실패했습니다 — [하이패스 관리]에서 확인해 주세요"로 사실대로 말한다 |
| **주유원·충전자와 카드는 바꾸지 않는다** | 누가 넣은 기록인가는 기록의 정체성이라, 그게 틀렸다면 정정이 아니라 삭제 후 재등록이 맞다. Rules는 관리자에게 `driverUid` 변경까지 허용하지만 화면에서 열지 않았다 |
| **흔적을 남기되 감사 로그는 늘리지 않았다** | `auditLog` 트리거의 화이트리스트는 주유·하이패스를 **자산 데이터**로 보고 의도적으로 제외한다(고시 제16조의 대상은 개인정보·접근 권한이다). 그 판단은 그대로 두고, 대신 이미 있는 `actorStamp()`로 `lastEditedByUid`를 심어 작성자와 다르면 목록에 `✏️ 관리자 수정` 배지를 띄운다 — **직원 화면에도** 뜬다. 금액은 지출 증빙과 대조하는 값이라, 직원 눈에 자기 이름으로 남은 숫자가 조용히 바뀌면 안 된다. 값의 신뢰는 Rules에 `actorStampValid()`를 추가해 담보한다(타인 명의 위조 불가) |
| **⚠️ 머지 전 리뷰가 값이 조용히 틀어지는 경로를 셋 잡았다** | ① **날짜만 고쳐도 `balanceAfter`를 다시 계산**해 덮어썼다 — `balanceBefore`가 비어 있는(스키마 기본값 0) 옛 기록에서 멀쩡하던 충전후잔액 80,000원이 50,000원으로 지워진다. 금액이 바뀔 때만, 그것도 `balanceAfter + 차액` 기준으로 계산하게 고쳤다 ② **검증은 `Number`로 하고 저장은 `parseInt`로** 했다 — `<input type="number">`는 지수 표기(`1e5`)를 유효한 값으로 넘기는데 `parseInt`는 그것을 **1**로 읽는다. 100,000원이 1원으로, 50,000km가 1km로 저장될 수 있었다(`limitFuelDecimals`가 같은 함정을 주석으로 남겨 둔 바로 그 경로다) ③ 0으로 저장된 값이 폼에 **빈 칸**으로 채워져 필수값 검사에 걸렸다 — 그 기록은 아예 정정할 수 없었다 |
| **정정 자체가 막히는 길도 있었다** | 차량이 삭제된 기록은 select에 해당 차량이 없어 `required`에 걸리고, 관리자가 **엉뚱한 차량을 골라야만** 저장됐다(그 순간 기록의 차량이 조작된다). 기록에 남아 있는 이름으로 항목을 만들어 주고, 그 항목을 다시 골라도 `vehicleName`이 지워지지 않게 했다 |
| **Rules 테스트가 차단만 검증하고 있었다** | 새로 건 `actorStampValid()`가 **직원 본인 수정**(가장 흔한 경로)까지 막아도 테스트는 초록이었다 — 차단 케이스만 있었기 때문이다. 성공 경로를 추가했다. 또 하나 배운 것: 스탬프 검사는 '값이 바뀔 때만' 돌기 때문에 **이미 박힌 값을 그대로 다시 쓰는 것은 통과**한다(의도된 설계인데, 처음 쓴 테스트는 그걸 모르고 실패를 기대했다) |
| **E2E는 화면부터 Rules까지 관통하는 것만 한 건** | 단위 테스트는 Firestore를 목으로 대체하므로 **Rules가 실제로 이 쓰기를 통과시키는지** 증명하지 못한다. 관리자가 남의 기록을 고치며 스탬프를 심는 이 경로는 화면·SDK·Rules 셋이 다 맞아야 저장되고, 어긋나면 사용자에게는 토스트 한 줄로만 보인다. 그 테스트가 처음 실패한 이유도 기록해 둔다 — 목록이 모바일·데스크탑 두 벌을 그려 CSS로 한쪽만 보이므로 `.first()`가 **숨은 쪽**을 집었다 |
| **배지 자리는 스크린샷이 정했다** | 데스크탑에서 주유원 칸에 배지를 붙였더니 폭이 좁아 이름이 `E…`로 잘렸다. 실물을 보지 않았으면 몰랐을 것이다 — 날짜 아래로 옮겼다(누가 고쳤나는 사람이 아니라 기록에 대한 표시이기도 하다). 모바일은 줄바꿈되므로 이름 옆에 둔다 |
| **검증** | Vitest **178파일 2,192개**(신규 12건) · Rules **32건**(신규 1건 — 같은 기관 관리자만·타인 명의 차단·타 기관 차단·직원 본인 성공·스탬프 없는 수정 통과) · 에뮬레이터 E2E **16건**(신규 1건) · lint · type-check · 빌드(번들 예산 이내) · 하네스 0오류 · 라이트/다크/모바일 실물 스크린샷 · 배포 후 프로덕션에서 공지 실물 확인 |

> 2026-09-11. Phase 224 보고에 **내가 스스로 적은 「남는 것」** 두 줄을 사용자가 "해결해 줘"로 돌려보냈다. 남겨 두는 판단이 늘 옳은 것은 아니고, **둘 다 한 줄짜리였다.**

| 항목 | 내용 |
|------|------|
| **비대칭을 하나 더 얹은 것은 나였다** | Phase 224가 정정(수정)에서 카드 잔액을 차액만큼 맞추게 하면서 삭제는 그대로 뒀다 — **같은 화면에서 어느 버튼을 누르느냐에 따라 잔액이 맞기도 하고 틀리기도** 하게 됐다. 게다가 원래도 어긋나 있었다: 직원 삭제(`useHipassCharge`)는 `rollbackBalance: true`로 되돌리는데 관리자 삭제만 아니었다. 즉 **기존 비대칭(직원↔관리자) 위에 새 비대칭(수정↔삭제)을 얹은 것**이고, 고치는 데 든 것은 옵션 한 줄이었다. Rules도 Zod(`z.string()`)도 날짜 형식을 검사하지 않아 **평직원 하나면** 임의 문자열을 심을 수 있었고, 목록 화면에서는 React가 막아 그냥 이상한 날짜로 보이다가 **관리자가 PDF를 뽑는 순간 관리자 세션으로 실행**됐다(직원 → 기관관리자 권한 상승). 삽입과 실행이 분리된 저장형이라 공격자는 접속해 있을 필요도 없다 |
| **숫자 필드가 같은 패턴인데 안전한 이유가 날짜만 뚫린 이유였다** | `fuelCost.toLocaleString()`도 문자열이면 같은 구멍이다. 도달하지 않는 이유는 스키마가 `z.coerce.number()`라 `Number("<img …>")`가 `NaN`으로 떨어지기 때문이다. **`date: z.string().catch('')`만 형식 검사 없이 문자열을 통과시킨다.** Phase 225가 "검증과 저장의 해석이 둘이었다"를 고쳤는데, 여기서는 **스키마와 렌더의 신뢰 수준이 둘**이었다 |
| **호출부 다섯을 감싸지 않고 함수 안에서 막았다** | 통과 함수라는 사실이 이름에 드러나지 않으므로 다음 호출부도 같은 함정을 밟는다. 호출부 전수가 `src/lib/pdf/` 안의 HTML 템플릿뿐임을 확인하고 `formatDate` 내부에서 이스케이프했다(`formatDateKorean`은 호출부가 이미 감싸고 있어 그대로 뒀다) |
| **기존 XSS 테스트가 놓친 이유를 먼저 밝혔다** | 페이로드를 `destination`·`notes`·`driverName`·`shop`·`description`에만 넣고 **`date`에는 넣지 않았다.** 그래서 새 파일을 만들지 않고 **기존 테스트의 페이로드 대상에 `date`·`nextDueDate`를 넣었다** — 테스트가 덮지 않던 축을 그 테스트 자신이 덮게 하는 편이 낫다. `formatDate` 자체에도 하이픈 유무 두 갈래 단위 테스트를 뒀다 |
| **PoC로 먼저 실증하고, 고친 뒤 되돌려 다시 확인했다** | 임시 PoC로 5개 경로 전부에서 `<script>`가 살아 있는 노드로 파싱되는 것을 확인한 뒤 보고했고(추정이 아니라 실행), 수정 후에는 이스케이프를 되돌려 **6건이 실제로 빨개지는 것**을 확인했다 — 빈 테스트가 아님을 증명하는 절차다 |
| **머지 후 배포가 도는 것까지가 이 변경의 검증이었다** | 배포 트리거 조건을 건드린 변경이라, 잘못하면 **정상 배포가 조용히 멈춘다**(잡이 아예 생성되지 않는다). 머지 전에 기준점(직전 Deploy `run=34609992338`, sha `7d0e743`)을 잡고, "CI 성공 후 4분간 Deploy가 안 생기면 가드가 정상 경로를 막은 것"으로 판정 조건을 미리 정한 뒤 추적했다. 결과는 정상 생성이었다 |
| **`if: >-` 들여쓰기도 리뷰가 잡았다** | folded scalar는 **더 들여쓴 줄의 줄바꿈을 접지 않아** 표현식 문자열에 `\n`이 남아 있었다(js-yaml 파싱으로 확인). Actions는 그래도 평가하지만, 표현식이 틀리면 잡이 생성되지 않아 실패가 조용하다. 6칸으로 맞춰 한 줄로 접히게 했다 — **관용에 기대지 않는다** |
| **탐지로 끝내지 않고 규칙으로 환류했다** | `/cso`가 요구하는 대로 확정 발견을 강제 수단에 연결했다 — 발견 1은 [ci-cd.md](../../.agent/rules/ci-cd.md) §1.5(시크릿 쥔 잡의 두 자물쇠, 방벽 셋의 우회 경로, `pull_request_target` 사용 조건), 발견 2는 회귀 테스트. 규칙 문서는 오래 남고 다음 사람이 그대로 인용하므로, **우연한 방벽을 경계로 세지 않도록** 셋을 각각 적었다 |
