### Phase 191: 내가 제시한 임계값이 틀렸다 — 일별일지 실측 분할, 상한이 아니라 채우기 기준 📄🔍

### Phase 192: 기록은 늘지 않는데 한도만 깎였다 — 접속기록 세션당 1회·429 해소 🔁🔇

> 2026-09-02, Sentry 신규 이슈 `FirebaseError: 요청이 너무 많습니다. 1시간 후 다시 시도해주세요. [429]` (`/employee/today`, Samsung Internet 30 / Android 10, 직원). **Phase 142가 이 계열의 함정을 이미 적어 뒀는데(`recordSession` 20회/시간), 정작 한도를 깎은 주체가 거기 적힌 것과 달랐다.**

| 항목 | 내용 |
|------|------|
| **정체 확정 — 접미사 `[429]`가 콜러블을 지목했다** | `@firebase/functions`의 `_errorForResponse`는 HTTP 상태를 코드로 옮기면서 메시지를 `` `${description} [${httpStatus}]` ``로 만든다. 우리 서버 문구 뒤의 `[429]`는 그 접미사이므로 이건 **콜러블**이고, 서버가 의도적으로 거부한 것이다(네트워크 실패가 아니다). Phase 142와 같은 방법 — SDK 소스에서 형태를 먼저 확정하고 범위를 좁혔다 |
| **"1시간 후"가 후보를 하나로 줄였다** | 문구는 `checkRateLimitByUid`가 `windowSeconds >= 3600`일 때만 만드는 형태다. `/employee/today`에서 **직원 역할**이 부르는 3600초 창 콜러블은 `recordSession` 하나뿐이다(`recordExport`·`acceptCurrentTerms`는 같은 창이지만 내보내기·재동의라는 명시적 행동에서만 나온다) |
| **Phase 142가 지목한 범인이 아니었다** | 142는 "한도 초과에 재시도를 걸면 남은 한도만 깎는다"며 `resource-exhausted`를 재시도 대상에서 뺐고, 그 판단은 지금도 맞다. 그런데 한도를 깎고 있던 것은 재시도가 아니라 **페이지 재부팅**이었다. 안드로이드는 백그라운드 PWA·웹뷰를 자주 회수하고, 복귀 때마다 페이지가 통째로 다시 뜬다. 그 부팅 하나하나가 `recordSession` 호출 1건이었다 |
| **"쌓이지 않는다"를 "불러도 된다"로 읽고 있었다** | sessionId가 sessionStorage에 남아 있으므로 재부팅한 호출은 `session_{uid}_{sessionId}` **같은 문서를 덮어쓴다**. 그래서 로그는 늘지 않았고, 그 점이 원래 설계의 자랑이었다. 하지만 서버 카운터는 문서가 아니라 **호출**을 센다 — 남는 기록은 그대로인 채 상한만 깎였다. 멱등성은 중복을 막아 줄 뿐 **호출을 공짜로 만들어 주지 않는다** |
| **표식은 성공 뒤에만 남긴다** | `auditSessionRecorded`(값 `uid:sessionId`)를 sessionStorage에 두고, 같은 브라우저 세션의 재부팅에서는 호출 자체를 건너뛴다. 성공 뒤에만 남기는 것이 핵심이다 — 실패한 세션까지 표식을 남기면 그 접속은 영영 기록되지 않는다. 계정을 표식에 넣은 이유는 같은 탭에서 다른 계정으로 로그인하면 별개의 접속이기 때문 |

### Phase 195: 이름 충돌을 피하려다 IAM에서 걸렸다 — 과금 LLM 키 Secret Manager 이관 🔐🚀

> 2026-09-02. Phase 193이 "머지 전에 Secret Manager에 값이 있어야 하므로 별건"이라며 미뤄 둔 `defineSecret` 이관 중 `GEMINI_API_KEY` 한 건을 처리했다. 코드 변경은 사실상 한 줄(`defineString` → `defineSecret`)이었는데 **배포 경로에서 두 번 걸렸다** — GitHub Secret에 남은 옛 줄(이름 충돌)과, 새로 만든 시크릿에만 필요한 IAM 바인딩. 둘 다 코드가 아니라 배포 환경의 문제라 로컬 검증으로는 드러나지 않는 자리다.

| 항목 | 내용 |
|------|------|
| **왜 Gemini만 옮겼나** | 함께 지적됐던 `TMAP_API_KEY`·`HOLIDAY_API_KEY`는 **같은 키가 프론트 번들에 `VITE_` 접두사로 이미 공개**돼 있어 서버 사본만 감춰도 얻는 것이 없다. `DISCORD_WEBHOOK_URL`은 셀프호스팅 선택 항목이라 시크릿으로 강제하면 값이 없는 배포가 막힌다. 남는 것은 **과금되는 LLM 키** 하나뿐이고, 그것만 옮겼다. 소비 함수 9개(간접 사용 포함 — `submitOrgApplication`의 프리스크린, `onSlackTaskCreated`의 어시스턴트까지)에 `secrets: [...]`를 선언해야 런타임에 주입된다 |
| **시크릿은 "한 줄만" 고칠 수 없다** | 배포 워크플로가 GitHub Secret `FUNCTIONS_ENV_FILE`을 그대로 `functions/.env`로 쓰는데, `.env`에 `defineSecret`과 같은 이름이 있으면 Firebase가 이름 충돌로 배포를 거부한다. 그런데 **GitHub Secret은 저장된 값을 아무도 다시 볼 수 없다** — "한 줄 제거"가 실제로는 "전체 재입력"이다. 로컬 `functions/.env`로 재구성하려다 보니 CI에만 있던 `SENTRY_DSN_FUNCTIONS`·`ADMIN_NOTIFICATION_EMAIL`이 빠진다: 배포는 성공하고 **Functions 에러 보고와 운영 알림 메일만 조용히 죽는** 형태다 |

| **목록이 비면 실패시킨다** | 추출이 어떤 이유로 빈 문자열을 내면 필터가 아무것도 거르지 않으면서 **성공한 척한다** — Phase 186에서 겪은 '조용한 성공'과 같은 형태다. `-z` 검사로 스텝을 명시적으로 죽인다 |
| **머지 전 리뷰가 잡은 주석 오탐** | 첫 구현은 `defineSecret("KEY"` 패턴을 파일 전체에서 긁었다. 그런데 `params.ts`는 **어떤 키를 이관했고 어떤 키는 안 했는지 산문으로 설명하는 파일**이고 `TMAP_API_KEY`·`HOLIDAY_API_KEY`·`DISCORD_WEBHOOK_URL`이 모두 주석에 이름으로 등장한다. 누군가 설명에 예시 코드를 한 줄 넣으면 그 평문 키가 목록에 섞여 `.env`에서 제거되는데, `defineString`은 값이 없어도 배포를 막지 않으므로 **배포는 초록으로 끝나고 경로 조회만 프로덕션에서 실패**한다. `^export const … = defineSecret("…")`로 앵커해 교정했고, 주석에 예시를 넣은 가짜 파일로 옛 패턴은 2개·새 패턴은 1개를 뽑는 것을 재현해 확인했다 |
| **IAM 403 — 새 시크릿에만 필요한 단계** | 이름 충돌은 해소됐는데 배포가 `secrets/GEMINI_API_KEY:setIamPolicy` 403으로 멈췄다. Firebase는 배포 때 런타임 계정(`…-compute@`)에 시크릿 읽기 권한을 붙이려 하는데 CI 배포 계정에 IAM 변경 권한이 없다. **기존 9개가 여태 안 걸린 이유**는 이미 바인딩이 있어 이 호출 자체를 건너뛰기 때문 — 정책을 실제로 비교해 보니 나머지는 전부 `secretAccessor` 하나씩이고 `GEMINI_API_KEY`만 `{"etag":"ACAB"}`(바인딩 0개)였다. 같은 모양의 바인딩 하나를 붙여 해소. **CI 계정에 `secretmanager.admin`을 주는 대안은 기각** — 그러면 CI가 모든 시크릿의 IAM을 바꿀 수 있게 되는데, 새 시크릿을 만드는 일은 드물다(2026-07 이후 처음) |
| **등록한 값이 키가 아니었다** | 첫 `functions:secrets:set`에서 프롬프트에 키가 아닌 값이 들어가 버전 1로 등록됐다(5글자 한글 자모). **배포는 시크릿의 존재만 보고 내용을 보지 않으므로** 그대로 갔으면 OCR·AI·어시스턴트·프리스크린이 프로덕션에서 전부 조용히 실패했을 것이다. 값을 출력하지 않고 형태만 검사해(길이 39·ASCII·`AIza` 접두어·공백 없음) 잡아냈다. 버전 2가 정상 키 |

| 항목 | 내용 |

| **상시 빨강의 정체** | 응답이 **정확히 5.0초**에 끊긴다 — 인증 거부라면 즉시 에러 응답이 왔을 테니 이건 `PING_TIMEOUT_MS`(5초)에 걸린 것이다. 그런데 **사용자 화면은 이 API를 실시간으로 부르지 않는다**: 프런트(`holidayApi.ts`)는 Firestore `system/holidays`를 먼저 읽고, 그 문서는 월배치가 채우며, 그 배치의 `fetch`에는 타임아웃이 아예 없어 느려도 성공한다. 하트비트를 직접 조회해 **09-01 06시 성공**을 확인했다 — 연동은 살아 있었다 |

### Phase 197: 재시도를 끊었더니 상태도 함께 끊겼다 — 캘린더 연동 일괄 접근 진단 🔍📅

### Phase 198: 실패를 보이게 만든다 — 비례 판정 · 실패 사유 기록 · 기관 통지 🚦📝🔔

### Phase 201: 같은 구조는 같은 방식으로 터진다 — 티맵 프록시 · `updateTime`은 신선도 지표가 아니었다 📡🕰️

> 2026-09-03. Phase 200이 "남는 것 ①"로 남긴 `tmapProxy`를 닫았다. 발생 이력이 0건인데 손댄 근거는 하나다 — **원인이 상대 쪽이 아니라 우리 코드의 구조**였고, 그 구조가 두 프록시에 똑같이 있었다. holidayProxy가 실제로 울린 경보가 그 구조의 증거다. 덤으로 Phase 200이 "그렇게 보인다"로 남겨 둔 `system/holidays` 갱신 의문을 로그로 닫았는데, 결론이 **내가 본 지표 자체가 틀린 지표였다**는 쪽이라 따로 적어 둔다.

| 항목 | 내용 |
|------|------|
| **여섯 곳을 한 곳으로** | `safeFetchJson(response, ctx)` → `fetchTmapJson(url, init, ctx)`. `fetch`를 함수 안으로 들이니 호출부 6곳(`geocode`·`poi`·`route` × 신·구 경로)이 각각 한 줄이 됐다. 예전 구조는 `fetch`가 호출부에 흩어져 있어 **여섯 곳이 모두 타임아웃도 실패 처리도 없는 상태**였다 — 이제 새 엔드포인트를 추가할 때 그것을 빠뜨릴 자리가 없다 |
| **처리 내용** | 연결 실패(DNS·연결 끊김·타임아웃)는 **502 + WARNING**에 원인(`cause.code` 또는 `timeout`)을 남긴다 · 상한 없던 `fetch`에 **10초 타임아웃**(holidayProxy와 같은 값) · 2xx 아님·빈 body·파싱 실패는 종전과 동일 |
| **한 곳은 일부러 다르게 뒀다** | **2xx인데 JSON이 아닌 경우는 ERROR 그대로.** holidayProxy에서 이 경로를 WARNING으로 낮춘 근거는 공공데이터 포털이 오류 문서(XML·HTML)를 상시 돌려주고 월배치 `syncHolidays`가 같은 상황을 `captureWarning`으로 남긴다는 것이었다. 티맵에는 그런 이력이 없고, 2xx 비-JSON이면 상대의 장애보다 엔드포인트·계약 문제일 가능성이 커 조치가 필요하다. **"같은 방식으로 고친다"가 "모든 판정을 같게 한다"는 뜻은 아니다** |

### Phase 203: 왜 도는지 모르는 것과, 검사하지 않는 검사 — 폴백 사유 계측 · 에뮬레이터 테스트를 실물로 🔎🧪

> 2026-09-03. Phase 200·201이 "남는 것"으로 남긴 둘을 닫았다. 성질이 달라 보이지만 같은 병이다 — **둘 다 보고 있다고 착각하던 자리**다. 하나는 폴백이 왜 도는지 알 수 없었고(사유가 클라이언트 콘솔에만 남았다), 하나는 통합 테스트가 실물 대신 자기가 만든 사본을 검사하고 있었다. 원인을 단정하는 대신 **다음 발생이 스스로 답하도록** 근거를 심는 쪽을 골랐다.

| 항목 | 내용 |
|------|------|
| **① 폴백 사유가 어디에도 남지 않았다** | 월배치가 올해·내년을 채우므로 이 폴백은 거의 돌지 않아야 하는데 08-25~09-03에 7건, 전부 올해 조회였다. `holidayApi.ts`의 catch가 `console.warn`으로만 흘려 **서버에서는 원인을 알 방법이 없었다.** Firestore 읽기 결과를 `year-missing`·`doc-missing`·`firestore-<code>`로 갈라 프록시에 실어 보내고, 서버가 모든 로그 줄에 함께 적는다 |
| **조사로 좁힌 원인 후보** | Firestore는 App Check **ENFORCED**다(App Check API로 직접 조회. Storage도 ENFORCED, Auth는 UNENFORCED). reCAPTCHA 토큰이 막히면 SDK가 최대 24시간 스로틀에 들어가 그동안 Firestore 읽기가 `permission-denied`로 거부된다(`firebase.ts` 주석 · Phase 188). 그런데 **프록시는 Auth 토큰만 검사하고 App Check는 보지 않는다** — "Firestore는 막히는데 프록시는 되는" 관찰과 정확히 맞는다. 인앱 브라우저(App Check를 초기화하지 않는다)는 `InAppBrowserGuard`가 로그인 화면에서 막아 이 경로에 닿지 못하므로 후보가 아니다. **확정은 로그를 봐야 한다** |
| **읽는 법을 코드에 적었다** | `firestore-permission-denied`인데 프록시 호출은 성공했다면 그 사용자는 로그인 상태였다는 뜻이다(프록시가 Auth 토큰을 요구한다). Rules는 로그인만 요구하므로(`system/holidays`: `isSignedIn`) 남는 원인은 App Check다. `unavailable`이면 네트워크·오프라인, `failed-precondition`·terminated류면 로그아웃 전환 중 종료된 인스턴스(`firestoreLifecycle`)다. 주석으로 남긴 이유는 **반년 뒤 로그를 보는 사람이 이 추론을 처음부터 다시 해야 하기 때문**이다 |
| **클라이언트 문자열을 로그에 그대로 넣지 않았다** | 64자로 자르고 `[A-Za-z0-9._+-]`만 남긴다. 사유는 화면이 보내는 값이라, 줄바꿈이나 `severity=ERROR` 같은 것을 섞어 **로그 한 줄을 위조할 여지**를 남기면 안 된다. 다듬는 동작을 테스트로 고정했다 |

### Phase 205: 차가 어디 있는지 아는 일 — 출발지 가변화와 현재 위치 🚩🚐

> 2026-09-04. "출발지를 자유 텍스트로 입력하게 해 달라"는 기관 요청에서 출발했다. 요청대로 만들지 않았다. 그 기관의 실제 패턴은 임의 장소가 아니라 **기관 ↔ 숙소 두 고정 지점의 반복**이었고, `startLocation`은 라벨이 아니라 **Tmap 경로 탐색의 출발 주소**라 주소 없는 텍스트를 받으면 거리·소요시간·통행료가 조용히 어긋난다. 요청자가 겪는 문제의 원인만 바뀌고 해결되지는 않는 길이었다.

| 항목 | 내용 |
|------|------|
| **진짜 고통점** | 출발지가 차량 문서(`siteId`)에 붙어 있어 24시간 운영 기관의 차량 1~2대는 관리자가 매일 값을 바꿔 줘야 했다. 자유 입력이 아니라 **운행 시점에 고르는 것**이 필요했다. 기관이 "숙소"를 주소와 함께 등록하면 라벨이 정형화될 뿐 아니라 거리 계산이 처음으로 정확해진다(지금은 숙소에서 출발해도 본관 기준으로 계산된다) |
| **상태와 계획을 갈랐다** | `siteId`는 **기본 차고지**로 남기고 실제 위치를 `currentSiteId`로 분리했다. 예약 문서에는 저장하지 않는다 — 한 달 뒤 예약을 만드는 사람은 그때 차가 어디 있을지 모르고, 저장하면 운행 당일에 낡은 값이 사람을 없는 곳으로 보낸다. 예약 **생성** 화면의 거리 계산은 기본 차고지 기준을 그대로 뒀다(예약 시점 거리는 어차피 예상치이고, 기록에 남는 값은 일지 작성 시 확정된 출발지로 계산된다) |
| **게이트를 기관이 아니라 차량 단위로** | 처음에는 `hasBranchSites`(분관 등록 여부)를 게이트로 삼으려 했는데 틀렸다. **분관 기능은 원래 *분산되어 있지만 고정된* 차량을 위해 만든 것**이라(`shared/orgSites.ts` 주석), 분관을 쓰는 기관의 대다수는 여전히 전 차량 고정이다. 기관 단위 설정으로도 부족했다 — 요청 기관조차 "차량 1~2대 정도"만 유동이라, 기관 토글은 나머지 차량 운전자에게 같은 문제를 재현한다. 그래서 차량 문서에 `siteVaries`를 두고 **출발지 선택·세운 곳 선택·배지의 신선도 표시를 이 하나로** 게이트한다. 판정은 `canChooseSite()` 한 곳에만 둔다 — 화면마다 조합하면 한 곳을 빠뜨렸을 때 고정 차량에 선택 UI가 새는데, 그 화면은 아무도 안 보고 지나간다 |
| **Rules를 건드리지 않았다** | 위치 갱신을 클라이언트가 아니라 이미 차량 부수효과를 전담하는 `syncDriveLogKm` 트리거에 얹었다. 클라이언트는 `currentKm`도 직접 쓰지 않는다(Phase에서 트리거로 이전됨). 그 덕에 교차 테넌트 검증(`organizationId` 일치)과 **소급 입력 방어(`isEffectivelyRetroactive`)를 그대로 재사용**했다. 소급 방어를 새로 만들면 두 규칙이 어긋난다 — 어제 운행을 오늘 입력했다고 오늘 위치를 덮어쓰면 차를 찾으러 간 사람이 엉뚱한 곳으로 간다 |
| **트리거는 플래그를 다시 읽지 않는다** | `endSiteId`는 게이트를 통과한 화면에서만 기록되므로 값의 존재 자체가 이미 판정 결과다. 여기서 플래그를 다시 읽으면 관리자가 플래그를 끈 순간 처리 중이던 기록이 조용히 버려진다. 대신 저장 직전 `buildLogData`에서 한 번 거른다 — 유동 → 고정으로 차량을 바꾼 뒤 폼에 남은 값이 새어 나가면 엉뚱한 차량의 위치가 움직인다 |

### Phase 207: 자정을 건너는 운행을 지어내지 않고 적는 법 — 다일 운행 기록 🌙🚐

> 2026-09-05. 기관 문의. "출발 시작을 누르지 않아 다녀온 뒤 내 기록에서 수정하려는데, 1박2일 운행은 소급 수정이 안 되나요?" **소급 입력 기능 자체는 정상이었다.** 원인은 두 개의 다른 문제가 겹친 것이었고, 그중 하나는 이용자가 말하지 않은 쪽이었다.

| 항목 | 내용 |
|------|------|
| **선례를 일부러 따르지 않았다** | 다일 **예약**은 하루당 문서 하나로 쪼갠다(`submitActions.ts` — 9/1 17:00~23:59 · 9/2 00:00~10:00, `groupId`로 묶음). 예약은 *시간 점유*라 쪼개도 뜻이 보존되고 날짜별 충돌 검사가 오히려 단순해진다. **운행일지는 계기판 기록이라 같은 모델을 쓸 수 없다** — 쪼개려면 자정에 존재하지 않았던 중간 km를 지어내야 하고, 그 순간 이 앱의 핵심 데이터가 허구가 된다. 이번 회차의 핵심 판단은 "선례를 베낀다"가 아니라 **"어디까지 선례인지 가른다"**였다(Phase 206은 정반대로 선례를 그대로 베끼는 것이 답이었다) |

### Phase 211: breadcrumb만 막은 것은 절반이었다 — 추적 스팬과 사용자 이메일 🔒📡

> 2026-09-06. Phase 209(#321)가 남긴 Sentry 유출 두 경로를 닫으려다, **같은 개인정보가 세 번째 경로로도 나가고 있다는 것**을 리뷰가 찾아냈다.

| 항목 | 내용 |
|------|------|
| **목적지가 URL 쿼리로 나간다** | 이 앱은 목적지 검색을 `/api/tmap?action=poi&keyword=김OO 어르신 댁`으로 보낸다(`tmap/geocoding.ts`). fetch·xhr breadcrumb은 URL을 통째로 담으므로, `extra`를 아무리 걸러도 **오류 직전 요청에 검색어가 실려 나갔다.** 경로와 파라미터 **이름**은 남기고 값만 지운다 — 어떤 호출이었는지는 보여야 진단이 된다 |
| **클릭 한 번에 실명이 나간다** | SDK는 `aria-label`·`title`·`alt`를 **설정과 무관하게 항상** 붙인다. `serializeAttribute`로는 막을 수 없다 — `@sentry/core`의 `_htmlElementAsString`에 고정 목록으로 박혀 있다. 이 앱은 거기에 실명을 넣는다(`title="공동 운전자: 홍길동, 김철수"`, `aria-label="홍길동 제거"`). **접근성과 도움말에 필요한 값이라 화면에서 뺄 수 없어** 나가는 길목에서 지운다. 속성이 있었다는 사실(`[title]`)과 태그·id·클래스는 남긴다 |
| **세 번째 경로 — 추적 스팬** | `browserTracingIntegration`이 켜져 있어 요청마다 스팬이 만들어지는데, `getFetchSpanAttributes`가 `url`에 **원본 URL을 통째로**, `http.query`에 쿼리를 그대로 담는다. 위생 처리를 거치는 것은 스팬 **이름**(`GET /api/tmap`)뿐이다. 게다가 트랜잭션 이벤트라 **`beforeSend`도 타지 않는다**(그쪽은 오류 이벤트 전용). `beforeSendSpan`을 더해 `url`·`http.url`·`url.full`·`http.query`·`http.fragment`를 막았다 — 이 훅은 루트 스팬과 자식 스팬 모두에 걸린다 |
| **리뷰를 그대로 믿지 않아 다행이었다** | 리뷰는 INP 스팬 이름과 web-vital 스팬의 `user.email`도 샌다며 `@sentry-internal/browser-utils` 경로를 인용했는데, **이 설치본(10.72.0)에 그 패키지가 없다.** 실제로 `htmlTreeAsString`을 쓰는 곳은 breadcrumb 하나뿐이다. 검증 없이 반영했으면 **존재하지 않는 문제에 코드를 넣을 뻔했다** |
| **이메일은 결국 뺐다** | 처음엔 "사용자 판단"이라며 남겼는데 리뷰 논거가 맞았다 — 같은 모듈의 스크러버가 가장 공들여 지우는 값이 **이메일 모양**인데, 그것을 매 이벤트에 붙여 보내면 앞뒤가 맞지 않는다. `uid`만으로 사용자 수·이슈 묶음·검색이 다 동작하고 누구인지는 Firebase 콘솔에서 조회하면 된다. 바뀌는 것은 이슈 목록의 가독성뿐이고 되돌리기는 한 줄이다 |
| **배선을 두 번 놓쳤다** | 순수 함수만 테스트해서, `beforeBreadcrumb`에 꽂는 코드를 통째로 빼도 전부 초록이었다. 고친 뒤 같은 실수를 `beforeSendSpan`에서 **한 번 더** 했다. 둘 다 뮤테이션으로 잡았지만, 돌리지 않았으면 "테스트 초록인데 프로덕션에서는 안 고쳐진" 상태로 나갔다. 앞선 회차들이 반복해 지적한 패턴이 여전히 남아 있다 |
| **속성값에 닫는 짝이 들어가면 꼬리가 샜다** | SDK는 속성값의 따옴표를 escape하지 않고, 상류 오류 문구를 `title`에 그대로 싣는 화면이 있다(`DashboardApiHealth`). 첫 `"]`에서 끊으면 뒤가 남고, `lastIndexOf`로 고치니 **뒤따르는 멀쩡한 속성까지 삼켰다.** 값의 끝을 경계(문자열 끝·요소 구분자·다음 속성)로 판정하도록 다시 잡았다 |
| **주석이 사실과 달랐다** | 닫히지 않은 값을 버리는 분기에 "잘림(`maxStringLength`) 때문"이라고 적었는데, `htmlTreeAsString`은 값을 중간에서 자르지 않는다. 방어 자체는 fail-closed로 남기되 근거를 고쳐 적었다. **틀린 근거가 달린 방어는 다음 사람이 지워도 이상하지 않다** |
| **검증** | 하네스 18영역 0오류 · lint · type-check · Vitest **172파일 2,081테스트** · 빌드/번들 예산 통과 · 뮤테이션 6건 · 배포 후 프로덕션 번들에서 스크러버 4종과 `setUser({id:t.uid})` 실물 확인 |
| **남는 것** | ① **Sentry에 이미 쌓인 개인정보는 코드로 지워지지 않는다** — 대시보드에서 사람이 확인·정리해야 한다 ② `SAFE_QUERY_PARAMS`는 제3자 호스트를 포함한 **모든** URL에 걸린다. 지금 목록은 전부 고정 코드값이지만 같은 이름에 자유 입력이 실리면 새어 나간다(주의를 주석에 남겼다) ③ 프래그먼트를 항상 버리므로 `#faq-id` 같은 진단 정보도 함께 사라진다 |
