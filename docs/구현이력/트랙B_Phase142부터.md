### Phase 142: `deadline-exceeded`는 거부가 아니라 무응답이었다 — 콜러블 대기 70초 ⏱️🔁

> 2026-08-03, Sentry 신규 이슈 `FirebaseError: deadline-exceeded` (`/admin/logs`, 기관 관리자). 메시지가 코드와 같은 한 단어뿐이라 어느 호출인지도 스택도 없었다. **SDK 소스에서 정체를 먼저 확정**하고 범위를 좁혔다 — 서버가 거부한 것이 아니라 **응답이 70초 안에 돌아오지 않은 것**이었다.

| 항목 | 내용 |
|------|------|
| **정체 확정** | `@firebase/functions`의 `callAtURL`은 `failAfter(options.timeout \|\| 70000)`을 `postJSON`과 race시키고, 타이머가 이기면 `new FunctionsError('deadline-exceeded','deadline-exceeded')`를 던진다. **코드와 메시지가 같은 문자열**이라 Sentry 제목이 한 줄로만 남는다. Firestore 에러였다면 "Deadline exceeded after ..." 형태의 문장이 붙는다 — 그래서 이건 **콜러블**이라고 단정할 수 있었다 |
| **중요한 성질 — 요청을 중단시키지 않는다** | race에서 진 fetch는 취소되지 않는다(AbortController가 없다). 서버 타임아웃은 120초라 **클라이언트가 포기한 뒤에도 서버는 처리를 끝낸다.** 즉 이 에러 중 일부는 "기록은 남았는데 클라이언트만 실패로 본" 경우다 — 재시도해도 중복이 안 생기는 설계인지가 그래서 중요해진다 |
| **범위 좁히기** | `/admin/logs`에서 이 형태로 터질 수 있는 경로는 **이번 배포에 함께 들어간 세 콜러블**뿐이었다: `recordSession`(부팅 1회, Phase 132) · `recordExport`(내보내기, Phase 132) · `acceptCurrentTerms`(재동의, Phase 138). 나머지 호출부는 실패를 토스트로만 처리하고 Sentry에 올리지 않는다. 셋의 공통점 — 호출이 드물어 **콜드 스타트가 겹치기 쉽고**, 재시도가 없고, 실패를 그대로 보고한다 |
| **왜 70초를 기다리나** | 셋 다 문서 한두 건을 쓰는 작업이다(서버 로직에는 느려질 구석이 없다 — 확인함). 70초는 그 사이 사용자가 아무 진전도 못 보는 시간이고, 그 시간이면 이미 실패한 요청이다. `lib/callableRetry.ts`로 **대기 20초 + 짧은 백오프 재시도**를 공통 규약으로 뒀다 |
| **재시도해도 되는 근거를 설계에서 찾았다** | 세 콜러블 모두 **결정론적 문서 ID로 멱등하게** 쓴다 — `session_{uid}_{sessionId}` · `export_{uid}_{exportId}`는 같은 문서를 덮어쓰고, 동의는 merge 쓰기다. 부를 때마다 새 문서를 만드는 콜러블에는 쓰지 않는다는 조건을 헬퍼 주석에 못 박았다 |
| **exportId를 시도마다 만들면 안 된다** | 재시도가 멱등한 것은 **식별자를 재사용할 때뿐**이다. 시도마다 새로 만들면 늦은 응답 한 번이 "두 번 반출"로 기록된다. 그래서 `newExportId()`를 payload 안이 아니라 호출 첫머리로 끌어올렸다(테스트로 고정) |
| **거부는 재시도하지 않는다** | `invalid-argument`·`permission-denied`·`resource-exhausted`는 다시 불러도 같은 답이 온다. 특히 한도 초과에 재시도를 걸면 **남은 한도만 깎는다**(`recordSession` 20회/시간, `acceptCurrentTerms` 10회/시간). 일시적으로 보는 코드는 `deadline-exceeded`·`unavailable`·`internal`·`aborted` 넷뿐 |
| **보고 기준을 갈랐다** | 접속기록·반출기록은 재시도까지 실패한 네트워크 문제를 **Sentry에 올리지 않는다** — fire-and-forget이라 사용자도 우리도 더 할 수 있는 게 없고, 조치로 이어지지 않는 보고가 진짜 결함을 덮는다(console.warn만 남긴다). 반면 **재동의는 계속 올린다** — 관리자에게는 차단 모달이라 실패가 곧 "앱을 못 씀"이고 문의 대응이라는 조치가 있다. 대신 시도는 2회로 제한했다(사용자가 스피너를 보고 있다) |
| **`ignoreErrors`에 넣지 않은 이유** | 가장 쉬운 처리는 `sentry.ts`에 `/FirebaseError.*deadline-exceeded/` 한 줄을 넣는 것이다. 하지만 그러면 **예약 생성·기관 가입처럼 사용자가 결과를 기다리는 콜러블의 같은 증상까지 함께 가려진다.** 소음의 근원은 "보고 여부"가 아니라 "재시도 없는 70초 대기"였으므로 근원에서 고쳤다 |
| **콜드 스타트는 남겨 뒀다** | `index.ts`가 모든 핸들러를 정적 import하므로 **어떤 함수가 뜨든 `googleapis`까지 전부 로드**한다(로컬 계측 710ms, 512MiB 인스턴스에서는 수 배). 지연 import로 줄일 수 있으나 이번 증상의 주원인이라 볼 근거가 없고(70초에는 한참 못 미친다) 캘린더 경로 전반을 건드리는 변경이라 별건으로 남긴다 |
| **검증** | lint · type-check · 프론트 단위 1105 → **1118건**(헬퍼 10 · 훅 2 · 반출 1 신설) · 빌드(gzip 974.0/1050KB) · 하네스 Doctor 0건 |
| **남은 것** | ① 콜드 스타트 지연 import(위) ② 실제로 어느 콜러블이었는지는 확정하지 못했다 — 세 경로 모두에 재시도를 넣었으므로 재발하면 남는 이벤트는 `useConsentGate.accept`(컨텍스트 `transient` 태그 포함)뿐이라 다음 발생부터는 구분된다 ③ 다른 콜러블(예약 생성·OCR)은 여전히 SDK 기본 70초다. 멱등하지 않아 같은 규약을 그대로 적용할 수 없다 — 서버 측 멱등 키가 먼저 필요하다 |
