### Phase 142: `deadline-exceeded`는 거부가 아니라 무응답이었다 — 콜러블 대기 70초 ⏱️🔁

> 2026-08-03, Sentry 신규 이슈 `FirebaseError: deadline-exceeded` (`/admin/logs`, 기관 관리자). 메시지가 코드와 같은 한 단어뿐이라 어느 호출인지도 스택도 없었다. **SDK 소스에서 정체를 먼저 확정**하고 범위를 좁혔다 — 서버가 거부한 것이 아니라 **응답이 70초 안에 돌아오지 않은 것**이었다.

| 항목 | 내용 |
|------|------|
| **정체 확정** | `@firebase/functions`의 `callAtURL`은 `failAfter(options.timeout \|\| 70000)`을 `postJSON`과 race시키고, 타이머가 이기면 `new FunctionsError('deadline-exceeded','deadline-exceeded')`를 던진다. **코드와 메시지가 같은 문자열**이라 Sentry 제목이 한 줄로만 남는다. Firestore 에러였다면 "Deadline exceeded after ..." 형태의 문장이 붙는다 — 그래서 이건 **콜러블**이라고 단정할 수 있었다 |
| **중요한 성질 — 요청을 중단시키지 않는다** | race에서 진 fetch는 취소되지 않는다(AbortController가 없다). 서버 타임아웃은 120초라 **클라이언트가 포기한 뒤에도 서버는 처리를 끝낸다.** 즉 이 에러 중 일부는 "기록은 남았는데 클라이언트만 실패로 본" 경우다 — 재시도해도 중복이 안 생기는 설계인지가 그래서 중요해진다 |
| **범위 좁히기** | `/admin/logs`에서 이 형태로 터질 수 있는 경로는 **이번 배포에 함께 들어간 세 콜러블**뿐이었다: `recordSession`(부팅 1회, Phase 132) · `recordExport`(내보내기, Phase 132) · `acceptCurrentTerms`(재동의, Phase 138). 나머지 호출부는 실패를 토스트로만 처리하고 Sentry에 올리지 않는다. 셋의 공통점 — 호출이 드물어 **콜드 스타트가 겹치기 쉽고**, 재시도가 없고, 실패를 그대로 보고한다 |
| **왜 70초를 기다리나** | 셋 다 문서 한두 건을 쓰는 작업이다(서버 로직에는 느려질 구석이 없다 — 확인함). 70초는 그 사이 사용자가 아무 진전도 못 보는 시간이고, 그 시간이면 이미 실패한 요청이다. `lib/callableRetry.ts`로 **대기 20초 + 짧은 백오프 재시도**를 공통 규약으로 뒀다 |
| **재시도해도 되는 근거를 설계에서 찾았다** | 세 콜러블 모두 **결정론적 문서 ID로 멱등하게** 쓴다 — `session_{uid}_{sessionId}` · `export_{uid}_{exportId}`는 같은 문서를 덮어쓰고, 동의는 merge 쓰기다. 부를 때마다 새 문서를 만드는 콜러블에는 쓰지 않는다는 조건을 헬퍼 주석에 못 박았다 |
| **exportId를 시도마다 만들면 안 된다** | 재시도가 멱등한 것은 **식별자를 재사용할 때뿐**이다. 시도마다 새로 만들면 늦은 응답 한 번이 "두 번 반출"로 기록된다. 그래서 `newExportId()`를 payload 안이 아니라 호출 첫머리로 끌어올렸다(테스트로 고정) |
| **거부는 재시도하지 않는다** | `invalid-argument`·`permission-denied`·`resource-exhausted`는 다시 불러도 같은 답이 온다. 특히 한도 초과에 재시도를 걸면 **남은 한도만 깎는다**(`recordSession` 20회/시간, `acceptCurrentTerms` 10회/시간). 일시적으로 보는 코드는 `deadline-exceeded`·`unavailable`·`internal`·`aborted` 넷뿐 |
| **보고 기준을 갈랐다** | 접속기록·반출기록은 재시도까지 실패한 네트워크 문제를 **Sentry에 올리지 않는다** — fire-and-forget이라 사용자도 우리도 더 할 수 있는 게 없고, 조치로 이어지지 않는 보고가 진짜 결함을 덮는다(console.warn만 남긴다). 반면 **재동의는 계속 올린다** — 관리자에게는 차단 모달이라 실패가 곧 "앱을 못 씀"이고 문의 대응이라는 조치가 있다. 대신 시도는 2회로 제한했다(사용자가 스피너를 보고 있다) |
| **`ignoreErrors`에 넣지 않은 이유** | 가장 쉬운 처리는 `sentry.ts`에 `/FirebaseError.*deadline-exceeded/` 한 줄을 넣는 것이다. 하지만 그러면 **예약 생성·기관 가입처럼 사용자가 결과를 기다리는 콜러블의 같은 증상까지 함께 가려진다.** 소음의 근원은 "보고 여부"가 아니라 "재시도 없는 70초 대기"였으므로 근원에서 고쳤다 |
| **콜드 스타트는 남겨 뒀다** | `index.ts`가 모든 핸들러를 정적 import하므로 **어떤 함수가 뜨든 `googleapis`까지 전부 로드**한다(로컬 계측 710ms, 512MiB 인스턴스에서는 수 배). 지연 import로 줄일 수 있으나 이번 증상의 주원인이라 볼 근거가 없고(70초에는 한참 못 미친다) 캘린더 경로 전반을 건드리는 변경이라 별건으로 남긴다 |
| **검증** | lint · type-check · 프론트 단위 1105 → **1118건**(헬퍼 10 · 훅 2 · 반출 1 신설) · 빌드(gzip 974.0/1050KB) · 하네스 Doctor 0건 |
| **남은 것** | ① 콜드 스타트 지연 import(위) ② 실제로 어느 콜러블이었는지는 확정하지 못했다 — 세 경로 모두에 재시도를 넣었으므로 재발하면 남는 이벤트는 `useConsentGate.accept`(컨텍스트 `transient` 태그 포함)뿐이라 다음 발생부터는 구분된다 ③ 다른 콜러블(예약 생성·OCR)은 여전히 SDK 기본 70초다. 멱등하지 않아 같은 규약을 그대로 적용할 수 없다 — 서버 측 멱등 키가 먼저 필요하다 |

### Phase 143: 반복 예약을 손댈 수 없던 세 증상 — 원인이 각각 달랐다 🔁🔒

> 2026-08-03, 사용자 제보: "한 차량을 평일 같은 시간대로 한 달 반복예약을 넣으려는데 시간이 비어 있음에도 원하는 시간 설정이 안 되며 오후/오전 변경이 안 되고 시간도 변경이 안 됩니다. 다 충돌이라고 뜨구요." 한 문장에 담긴 세 증상은 **서로 다른 원인**이었고, 하나를 고쳐도 나머지가 남아 여전히 손댈 수 없는 상태였다.

| 항목 | 내용 |
|------|------|
| **① 모든 날짜가 충돌 — 비교 대상이 틀렸다** | 미리보기의 충돌 검사가 예약 **문서 ID**를 반복 **그룹 ID**와 비교하고 있었다(`r.id !== editingRecurringGroupId`). 두 값은 형식부터 달라 어떤 예약도 걸러지지 않는다. 그룹 수정은 "지우고 다시 만들기"라 자기 그룹은 충돌이 아닌데, 제외가 전혀 동작하지 않아 **그룹을 열자마자 자기 예약과 100% 충돌**했다(20일 반복이면 "충돌 20건"). 제출 경로에도 같은 구멍이 있어 저장까지 막혔으므로 `findOverlappingReservation`에 그룹 단위 제외를 넣었다 |
| **② 시간 입력 잠김 — 입력 도중의 값으로 되돌리고 있었다** | `if (actualIsToday && val < getCurrentTimeStr()) return;`. time 입력은 오전/오후·시·분을 **한 칸씩** 바꾸며 그때마다 onChange를 부르는데, 중간값이 조건에 걸린다고 state 갱신을 건너뛰면 입력이 즉시 이전 값으로 되돌아간다. 오후 11:30을 오전으로 바꾸는 첫 조작부터 막히니 **시간을 아예 바꿀 수 없었다.** `min` 속성도 함께 문제였다 — 오늘이 반복 날짜에 포함되면 하한이 현재 시각으로 잡혀, 내일 이후에 유효한 오전 시간대를 **브라우저 기본 검증이 제출 단계에서** 막는다. 입력은 자유롭게 두고 판정을 제출 시점으로 옮겼다 |
| **③ 저장 실패 — 반복 그룹 수정이 단건 저장 분기에도 걸렸다** | `else if (editingReservation)`이 반복 그룹 수정까지 받아, 폼을 통째로 단건 저장하려다 `Unsupported field value: undefined (found in field recurringDays)`로 터졌다. 더 나쁜 건 그다음이다 — 그룹 재생성 블록이 **먼저 그룹을 지우고** 날짜를 계산해서, 만들 날짜가 0건이면 그룹만 사라지고 아무것도 남지 않는다. **삭제보다 검증을 앞으로** 옮겼다 |
| **후속 ①: 단건 전환을 제대로 구현** | 직전 조치는 반복 그룹 수정 중 유형 전환을 *막는* 것이었다(반복을 끄면 "다시 만들 대상"이 사라져 그룹만 지워질 수 있었다). 실무에 필요한 동작이라 제대로 넣었다 — 반복 체크를 끄고 제출하면 **수정을 누른 그 회차**만 남고 나머지는 취소된다. "지우고 다시 만들기"를 쓰지 않은 이유가 둘: **삭제 권한**(Rules의 예약 delete는 소유자 한정이라 관리자 경로가 막힌다)과 **명의**(`createReservationSafe`가 reservedByUid를 호출자로 강제해 직원 예약이 관리자 명의로 넘어간다). 그래서 update만 쓴다 — 나머지는 `cancelRecurringGroup(…, exceptId)`로 취소하고, 남길 회차는 `detachFromRecurringGroup`이 그룹 링크만 떼어낸다(`deleteField()` — undefined로 덮으면 Firestore가 거부하고, 남겨 두면 1일짜리 반복 그룹으로 해석돼 단건이 되지 않는다) |
| **후속 ②: 서버가 명의를 받게 하고 Rules를 열었다** | 기관 관리자가 직원의 그룹 예약을 수정하면 **항상 permission-denied**였다. 제약의 근거는 명의 이전이었으므로 **서버를 먼저** 고쳤다 — `createReservationCore`에 `reservedByUid`를 추가하고, 호출자와 다른 값은 **기관 관리자만** 지정할 수 있게 하되 트랜잭션 안에서 **명의자의 users 문서를 읽어 같은 기관인지 재확인**한다(Claims의 role만 믿으면 임의 UID 명의로 예약을 심을 수 있다). 차량 사용 제한(`allowedUserIds`) 판정 기준도 호출자에서 **명의자**로 바꿨다 — 제한은 "누가 이 차를 쓰는가"의 문제이고 대리 생성에서 실제 운행자는 명의자다. 그 뒤 Rules의 delete를 기관 관리자에게 열었다(Rules 주석이 적어 둔 순서 그대로) |
| **순서 결정** | 전환은 **나머지 취소 → 남길 회차 떼어내기**다. 반대로 하면 두 번째 실패 시 단건과 살아 있는 반복 회차가 공존해 무엇이 유효한지 알 수 없다. 이 순서면 실패해도 남는 것은 "아직 그룹에 속한 예약 1건"이고 다시 전환하면 된다 |
| **검증** | lint · type-check(앱·functions) · 프론트 1118 → **1140건** · Functions **684건**(코어 대리 생성 7건 신설) · Rules **22건**(관리자 삭제 허용·타 기관 차단 재작성, 에뮬레이터) · 빌드(gzip 974.6/1050KB) |

| **남은 것** | 다일 예약으로의 전환은 이 시점까지 막아 둔 상태(대응 동작 미정의) → Phase 144에서 해소 |

### Phase 144: 반복 → 다일 전환 — 시작일 회차를 첫날로 고쳐 쓴다 📅

> 2026-08-04, Phase 143이 남겨 둔 제약 해소. 반복 그룹 수정 화면의 다일 체크박스가 잠겨 있어, 한 달치 반복을 며칠짜리 연속 운행으로 바꾸려면 **전부 취소하고 처음부터 다시** 넣어야 했다.

| 항목 | 내용 |
|------|------|
| **동작** | 반복 그룹 수정 중 다일을 체크하고 제출하면, 폼이 '시작일'로 보여 주는 날짜(그룹의 첫 회차)부터 종료일까지 이어지는 연속 예약 한 건이 되고 나머지 회차는 취소된다. 바뀔 구간·취소 건수·중간 날짜의 의미(하루 종일 배정)를 배너에 적고 제출 시 확인을 한 번 더 받는다 |
| **첫날은 새로 만들지 않는다** | 남긴 회차를 `detachFromRecurringGroup`으로 **고쳐 쓴다**(새 `groupId`를 같은 update에 실어 반복 링크를 끊고 다일 그룹에 붙인다). 지우고 다시 만들면 삭제 권한(소유자 한정)에 걸려 관리자 경로가 막히고 명의가 호출자에게 넘어간다 — 단건 전환이 detach를 쓰는 것과 같은 이유다. 둘째 날부터는 `createReservationSafe`로 만들되 폼의 `reservedByUid`를 그대로 넘긴다 |
| **취소가 반드시 앞** | 먼저 만들면 아직 살아 있는 반복 회차와 같은 차량·같은 날짜가 겹쳐 서버가 거부한다. 순서는 나머지 취소 → 첫날 전환 → 둘째 날부터 생성 |
| **전 구간을 먼저 검증한다** | 다일 생성은 여러 날을 한꺼번에 만드는데, 첫날만 보고 시작하면 중간 날짜에서 막히고 **그때는 이미 반복 그룹을 취소한 뒤라 되돌릴 것이 없다.** 날짜별 구간을 `buildMultiDaySlots`(신설 순수 함수) 하나로 만들어 충돌 검사와 실제 생성이 같은 목록을 보게 했다. 같은 그룹의 회차는 전환과 함께 취소되므로 충돌로 보지 않고, 시작일에 남은 회차가 없거나 이미 운행이 끝난(completed) 회차뿐이면 아무것도 건드리지 않는다 |

|------|------|

### Phase 149: 로그인 화면이 번쩍인 이유 — 증상을 가렸다가 원인을 찾았다 🔐⚡

> 2026-08-05, 사용자 제보: "탭 2개를 띄우고 다른 탭에서 페이지를 변경하면 반대편이 잠깐 로그아웃돼. 로그인 버튼 나오는 화면으로 잠깐 전환이 되네." **두 단계로 진행됐다** — 먼저 증상을 가리고(#143), 그 다음 프로덕션 콘솔 로그로 원인을 확정했다(#144).

| 항목 | 내용 |
|------|------|
| **로그인 화면이 나오는 경로는 둘뿐이었다** | `user`가 순간 `null`이 될 때만 나온다 — `AuthGuard`의 `requireAuth && !user` → `/login`, `path="*"`의 `RouteFallback` → `/`(랜딩, "직원 로그인" 버튼). 같은 사용자로 재발화하면 `setLoading(true)`로 되돌아가 **스피너**가 뜬다(로그인 버튼은 안 나온다) — 이 구분이 증상 분류의 기준이 됐다 |
| **1단계(#143) — 유예로 가렸다** | 인증이 한 번 확립된 뒤의 `null`은 2초 유예를 두고 확정한다. 유예 중 **화면·리스너를 아예 건드리지 않는 것**이 핵심이다. 같은 세션 재발화 시 `setLoading(true)`로 되돌리지 않는 것도 함께 고쳤다 — 안 하면 **로그인 플래시가 스피너 플래시로 바뀔 뿐**이다 |
| **로그아웃은 지연되지 않는다** | `logout()`이 끝에서 `window.location.href = '/'`로 페이지를 떠나므로(`lib/auth.ts`) 타이머와 무관하다. 덤으로 **로그아웃이 `clearOfflineCache()`를 기다리는 동안 뜨던 같은 플래시도 사라졌다** |
| **2단계(#144) — 스택 트레이스가 원인을 확정했다** | 사용자가 콘솔 로그를 통째로 보내줬고 거기 결정적인 구간이 있었다: `setPersistence → removeCurrentUser → _remove → _withPendingWrite → IndexedDB`. `getAuth()`는 기본 스택 `[IndexedDB, localStorage, sessionStorage]`로 초기화되는데(IndexedDB 1순위) 그 뒤의 `setPersistence(browserLocalPersistence)`는 단순 설정 변경이 아니라 **이전**이다 — 세션을 읽어서 **지우고** 다시 쓴다. 그 구간에는 currentUser도 토큰도 없다 |
| **플래시보다 심각한 증상이 같이 있었다** | 그 구간에 진행된 Firestore 작업이 전부 `permission-denied`로 실패했다 — 예약 조회·차량 사용 빈도·예약 패턴 분석·휴일 정보·기관 상태 감시가 **한꺼번에** 깨졌다. **깜빡임이 아니라 화면이 빈다.** 세션이 이미 localStorage에 있으면 `setPersistence`가 no-op이라 **간헐적**으로만 재현된다(그래서 매번이 아니었다) |
| **#143이 오히려 가린 부분도 있었다** | 재조회를 하지 않는 일회성 fetch는, 이전에는 플래시 후 리마운트가 **우연히** 재조회를 시켜 복구됐다. 유예를 넣자 리마운트가 없어져 **실패한 채 남는다.** 증상만 가린 수정의 대가다 — 근본 수정이 필요한 이유였다 |
| **왜 setPersistence를 넣었었나** | 주석에 적혀 있었다 — "authReady가 즉시 resolve되어 세션 복원 전에 user=null로 판단 → 새 탭에서 로그아웃". 해결하려던 건 **타이밍**이었는데 그것을 persistence 전환의 부수효과로 얻었고, **그 전환이 `removeCurrentUser`를 유발**했다 |
| **수정 — 전환을 없애지 않고 기다린다** | `setPersistence` 뒤에 `auth.authStateReady()`를 이어 붙였다. `main.tsx`와 `useAuth`가 모두 `authReady`를 await한 뒤 움직이므로 이전 구간이 닫힌 뒤에 구독과 Firestore 작업이 시작된다 — 그 구간의 `null`을 아무도 관측하지 않는다 |
| **더 근본적인 안을 고른 이유가 아니라 안 고른 이유** | `setPersistence`를 제거해 기본 스택에 맡기면 이전 자체가 사라진다. 하지만 세션 저장 위치가 localStorage → IndexedDB로 옮겨져 **기존 사용자가 1회 로그아웃될 위험**이 있다(218개 기관). 증상 제거에는 대기만으로 충분하므로 그 위험을 지지 않았다. 이전은 여전히 일어나 부팅이 수십 ms 늦어질 수 있다 |
| **검증** | 유예의 양면을 단위 테스트로 고정(`useAuth.test.tsx` 2건 — 돌아오면 로그아웃하지 않고, 안 돌아오면 확정한다). 프론트 1195 → **1197건** · lint · type-check · 빌드 |
| **커밋·PR** | `563edce`(PR #143, merge `684380a`, Deploy #315) · `7e8d15f`(PR #144) |
| **남은 것 — 판정이 아직 끝나지 않았다** | 배포 후 창 2개에서 ① 플래시가 없고 ② **콘솔에 `permission-denied` 폭풍이 없어야** 확정이다. #143은 ①만 가렸으므로 ②가 진짜 판정 기준이다. 또 `main.tsx`의 auth 판단은 여전히 **일회성**이다(첫 콜백에서 즉시 `unsubscribe()`) — 그때 null로 잡히면 경량 entry가 로드돼 랜딩 화면에 갇히는 더 나쁜 변종이 남아 있다. `AUTH_DROP_GRACE_MS = 2000`도 실측값이 아니다 |

### Phase 151: 서버는 허용하는데 화면이 막고 있었다 — 지난 예약 취소 · 일찍 반납한 차량의 남는 시간 🗓️🚗

> 2026-08-05, 사용자 문의 두 건. "8월 4일 차량예약을 취소하고 싶은데 예약 내역에서 수정, 취소가 나오지 않더라구요. 날짜가 지나면 수정이나 취소가 불가한 건가요?"와 "9:00~12:00 예약 후 9:00~10:00까지 타고 완료를 했다면 B직원이 같은 차량을 예약할 수 있게 하고 싶습니다." **서로 다른 문의인데 원인 구조가 같았다** — 둘 다 서버는 이미 허용하는 것을 화면이 자기 판단으로 좁게 막고 있었다.

| 항목 | 내용 |
|------|------|
| **① 지난 예약 — 화면 전용 게이트였다** | `ReservationAccordion`이 `resEndDateTime < new Date()`이면 [수정]·[취소] 버튼을 **아예 렌더하지 않았다.** `firestore.rules`의 예약 update·delete에도, `cancelReservation`에도 시간 제약은 없다 — 서버는 처음부터 허용하고 있었고 버튼만 사라진 것이다. 그래서 타지 않은 예약이 기록에 그대로 남고 지울 방법이 없었다 |
| **버튼을 노출하는 것만으로는 부족했다** | `ReservationSidePanel`이 `showForm && !isPastDate`로 폼 자체를 렌더하지 않는다. 이 상태에서 [수정]만 살리면 눌러도 아무 일도 없는 **죽은 버튼**이 된다. 조건을 `!isPastDate \|\| !!editingReservation`으로 바꿔 **수정 중일 때만** 지난 날짜에도 폼을 연다. 덤으로 [운행완료] 탭의 수정 버튼이 지난 날짜에서 이미 죽어 있던 것도 함께 살아났다 — 그 탭은 시간 경과와 무관하게 수정·취소를 노출하고 있었으므로, 두 화면의 정책이 서로 어긋나 있었던 셈이다 |
| **무엇을 계속 막는지가 절반이다** | 지난 날짜에 예약을 **새로** 만드는 길은 그대로 닫아 뒀다(`+ 예약` 버튼 숨김 유지 — 드래그 영역도 `!isPastDate`라 열리지 않는다). 시작 시간을 이미 지난 시각으로 옮기는 것도 `handleSubmit`이 계속 막는다. 연 것은 "이미 있는 예약을 손보는 것" 하나뿐이다 |
| **② 일찍 반납 — 검사는 맞고 그림이 틀렸다** | 겹침 **검사**는 클라이언트(`findOverlappingReservation`)도 서버(`createReservationCore`)도 이미 `completed`면 `actualStartTime/actualEndTime`을 쓴다. 즉 B직원은 폼에 10:00~12:00을 직접 입력하면 **이미 예약할 수 있었다.** 막힌 것은 [시간대 현황]이었다 — `getGaps()`가 예약 시간만 보고 빈 시간을 계산해 12:00까지 꽉 찬 것으로 그렸고, 드래그 예약 영역이 열리지 않았다 |
| **2시간 폴백이 이 기능에 정면으로 반했다** | 블록 렌더에는 "실제 시각이 예약 시각과 2시간 이상 벌어지면 잘못된 완료로 보고 예약 시각으로 폴백"이 있었다. 그런데 **일찍 반납할수록 이 조건에 걸린다** — 09:00~12:00 예약을 09:00~09:30만 타면 `\|09:30 − 12:00\| = 150분 > 120`이라 블록이 12:00까지 그려진다. 서버는 09:30부터 허용하는데 화면은 아니라고 말하는 상태다. 게다가 gap 계산과 블록 렌더가 서로 다른 기준을 쓰면 **블록이 끝난 자리가 빈칸으로 안 보이는** 어긋남까지 난다 |
| **판정 기준을 한 곳으로 모았다** | `resolveEffectiveTimes()`를 두고 gap 계산·블록 렌더·툴팁이 모두 이것을 쓴다. 규칙은 서버와 같다 — `completed`면 실제 운행 시간, 아니면 예약 시간. 2시간 휴리스틱은 제거하고 **형식(`HH:MM`)과 역전(끝 ≤ 시작)만** 폴백 조건으로 남겼다. 이 둘은 데이터가 깨진 경우라 판단이 아니라 방어다 |
| **정렬 전제를 자급자족하게 했다** | `getGaps`는 커서(`cursor = max(cursor, rEnd)`) 방식이라 입력이 시작 시각 순이어야 맞다. 호출부는 **예약** 시작 시각으로 정렬해 넘기는데 실제 운행 시각을 쓰면 어긋날 수 있으므로, 함수 안에서 실제 시작 시각 기준으로 다시 세운다 |

### Phase 152: 한 사람은 같은 시간에 한 대 — Phase 128을 되돌리되 축을 서버로 옮겼다 🚙🚙

> 2026-08-05, 사용자 지시: "한 사람이 동시에 여러 자동차를 예약할 수 있게 변경했는데 다시 되돌리게. 한 사람은 1대만 예약할 수 있어. 같은 시간에는....1대만 예약." Phase 128이 연 것을 닫는 작업이다. **같은 방식으로 되돌리지 않은 것이 요점** — 그때 문제의 절반은 정책이 세 곳에서 어긋나 있었다는 것이었다.

| 항목 | 내용 |
|------|------|
| **Phase 128이 왜 열었었나** | 클라이언트 `handleSubmit`만 사용자 단위 겹침(`findUserOverlappingReservation`)을 검사했고, 서버 코어는 차량 기준만 봤으며, FAQ(`multiple-reservations-same-time`)는 "전혀 막지 않는다"고 **이미 안내 중**이었다. 세 곳이 어긋난 상태에서 **클라이언트 검사를 지우는 쪽으로** 통일했고, Phase 131이 남은 죽은 함수를 제거했다. 이번에는 반대 방향으로 통일하되 **축을 서버에 둔다** |
| **서버가 판정한다** | `createReservationCore`에 `organizationId + reservedByUid + date` 겹침 검사를 트랜잭션 안에 추가했다. 판정 기준은 호출자가 아니라 **명의자**(`ownerUid`)다 — 차량 사용 제한(`allowedUserIds`)을 명의자로 판정하는 것과 같은 이유로, 대리 생성에서 실제 운행자는 명의자다. `modifyReservationCore`에도 같은 검사(자기 자신 제외) |
| **서버에서 자기 그룹을 제외하지 않는 이유** | 다일·반복 그룹 수정은 "지우고 다시 만들기" 경로다(`deleteReservationGroup`·`deleteRecurringGroup`·`cancelRecurringGroup`이 **먼저** 돈다). 재생성 시점에는 옛 회차가 이미 없으므로 제외 인자를 받을 필요가 없다. 그룹 안의 회차끼리는 날짜가 달라 서로 충돌하지 않는다 |

| **다일은 전 구간을 본다** | 차량 검사는 다일 생성에서 첫날만 보고 있다. 중간 날짜에서 서버가 거부하면 **앞 날짜는 이미 만들어진 뒤라 반쪽짜리 그룹이 남는다**(Phase 144가 전환 경로에서 같은 함정을 다뤘다). 사람 검사는 `buildMultiDaySlots`로 전 구간을 먼저 확인한다 — 차량 검사의 첫날 한계는 그대로 남아 있다 |
| **겹침 규칙은 차량과 동일하다** | 취소는 제외하고, 운행을 마친 예약은 실제 운행 시간만 점유한다. 그래서 **본인이 일찍 반납하면 본인도 그 시간에 다른 차를 잡을 수 있다** — Phase 151과 같은 기준을 쓴다. 시간만 겹치지 않으면 하루에 여러 건 예약하는 것은 그대로다 |

| **② 그런데 하루 두 번 돈 이유가 따로 있었다** | 02:00 실행이 백업 직후 `Memory limit of 512 MiB exceeded`로 인스턴스째 죽었다. **OOM은 인스턴스를 통째로 죽이므로 스텝별 try/catch가 잡지 못하고** `retryCount:1`이 배치를 처음부터 재실행한다. ①이 고친 오알림은 그 재실행이 남긴 증상이었고, 여기서 원인을 없앤다(512MiB → 1GiB). `rules/cloud-functions.md` §3.2가 백업·아카이빙에 이미 1GiB를 규정하고 있어 **이 배치만 규칙에서 어긋나 있던 것** |

### Phase 176: 문서가 어긋난 게 아니라 줄바꿈이 어긋났다 — `.gitattributes`로 LF 고정 📄↩️

> 2026-08-29, "깃허브에 있는 내용이 최신이야"로 시작한 동기화 작업. master를 8커밋 당기고 의존성을 재설치한 뒤 `npm run verify:fast`가 멈췄다. 에러는 "README에서 `functions/.env` 코드블록을 찾지 못했습니다"였고 **문서에는 아무 문제가 없었다.** CI는 초록이었다 — 이 종류의 실패는 PR에서 절대 드러나지 않는다.

| 항목 | 내용 |
|------|------|
| **에러 메시지가 가리킨 곳과 원인이 다른 곳에 있었다** | `check-functions-env.ts`는 fail-closed로 설계돼 "블록을 못 찾으면 통과시키지 않는다". 그 판단은 옳았지만, 못 찾은 이유가 **문서 구조 변경이 아니라 CRLF**였다. README를 LF로 정규화해 같은 검사를 돌려 통과를 확인하고서야 문서 드리프트가 아님을 확정했다 — 메시지대로 정규식을 고쳤다면 **없는 문제를 고치고 진짜 원인은 남았을 것** |
| **CI가 초록인 것이 안심의 근거가 아니었다** | 저장소 blob은 LF인데 Git for Windows 전역 기본값 `core.autocrlf=true`가 체크아웃 때 CRLF로 바꾼다. CI는 Linux(LF)라 통과한다. 즉 **각자 PC에서만 터지고 PR에서는 보이지 않는다.** `.gitattributes`가 없어 이를 막을 장치가 아예 없었다 |
| **스크립트를 고치지 않고 저장소를 고쳤다** | `\r?\n`으로 완화하면 그 스크립트만 낫는다. 같은 가정을 한 스크립트가 또 있으면 재발하고, 새로 쓰는 스크립트마다 기억해야 한다. `* text=auto eol=lf` 한 줄로 **입구에서 막는 쪽**을 골랐다. `.bat`/`.cmd`가 없어 CRLF 예외 없이 전부 LF로 갈 수 있었다 |
| **`git status` 815개가 거짓말을 했다** | 워킹트리를 LF로 바꾸자 816개가 수정됨으로 떴는데 `git diff`는 1개만 잡았다. `git hash-object`로 인덱스 blob과 대조해 **해시가 동일**함을 확인 — stat 캐시 노이즈였다. 스테이징하니 실제 변경은 2개 파일로 정리됐다. 숫자를 눈으로 믿었다면 815개 공백 커밋을 만들 뻔했다 |
| **`shared/faqData.ts` 하나만 blob 자체가 CRLF였다** | 파일 끝이 `}` 뒤 단독 CR(최종 개행 없음)이라, **git은 `text=auto`에서 단독 CR이 있는 파일을 안전을 위해 변환하지 않는다.** 그래서 `git add --renormalize`도 이 파일만 조용히 건너뛴다. blob이 CRLF면 `eol=lf`를 걸어도 체크아웃 결과가 CRLF라, 이걸 안 고치면 **`.gitattributes`를 넣고도 이 파일만 계속 어긋난다** |
| **리베이스가 같은 증상을 다시 만들었다** | base 재검증을 위해 리베이스하자 CRLF 파일이 7개 생겼다. 리베이스는 **새 base를 먼저 체크아웃**하는데 그 시점엔 `.gitattributes`가 아직 없다(내 커밋이 뒤에 얹히므로). blob은 전부 LF고 `git status`도 깨끗해 커밋에는 영향이 없었지만, **그 7개에 README.md가 포함돼** 로컬 검사가 다시 깨질 상태였다. 재체크아웃으로 정리했고, 이게 역으로 `.gitattributes`가 동작한다는 확인이 됐다 |
| **배포 순서를 사용자가 먼저 물었다** | "이미 배포한 것과 지금 배포하는 것은 충돌 안 나?" — 충돌 위험은 *동시* 배포일 때만이고 #239 배포는 이미 끝나 있었다. 되돌림 여부는 `git merge-tree`로 병합 트리를 만들어 #239가 바꾼 파일의 해시가 **바이트 단위로 보존됨**을 확인했다(겹치는 파일 0건). 말로 안심시키지 않고 트리를 만들어 본 것이 맞았다 |
| **CI 초록의 유효기간** | #238의 첫 초록은 #239가 들어오기 전 master 기준이었다. GitHub는 base가 앞으로 나가도 PR CI를 다시 돌리지 않는다(`synchronize`는 head 푸시에만 발화, `ci-retarget.yml`은 base **브랜치 변경**용이라 해당 없음). 리베이스 후 재검증해 **실제로 올라갈 트리**로 초록을 받고 머지했다 |
| **검증** | 워킹트리 텍스트 1,028개 중 CRLF **817 → 0** · `git add --renormalize` 내용 변경 0건(blob이 이미 전부 LF임을 확인) · verify:fast · 프론트 **1,763건**(155개 파일) · 하네스 Doctor 13영역 0/0 · `sync:agents --check` · `check:release-notes` · 리베이스 후 CI 9개 전부 초록(ci 3m56s · e2e 7m16s · functions-tests 1m14s) · Deploy 성공(1m40s) |

### Phase 192: 기록은 늘지 않는데 한도만 깎였다 — 접속기록 세션당 1회·429 해소 🔁🔇
