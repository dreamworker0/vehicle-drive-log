# 업데이트 소식 작성 가이드 (release-notes)

사용자가 앱에서 직접 읽는 **공지**를 쓰는 규칙이다. 개발 이력(`docs/구현이력/`)과 다르다 —
여기에는 "무엇이 달라졌고 어떻게 쓰면 되는지"만 사용자 말로 적는다.

## 1. 언제 쓰는가

**사용자 눈에 보이는 변경을 배포할 때마다.** 화면·문구·동작·알림이 달라졌다면 대상이다.
리팩토링·테스트·CI·의존성 갱신처럼 화면이 그대로인 변경은 대상이 아니다.

> ⚠️ 실제로 빠뜨린 적이 있다. 예약 관련 다섯 건이 프로덕션에 나간 뒤 사용자가
> "공지에 설명해 놨니?"라고 물어서 발견했다(Phase 143~145). 체크리스트만으로는 막히지 않아
> **누락 감지 스크립트**를 두었다:
>
> ```bash
> npm run check:release-notes          # 후보가 있으면 종료 코드 1
> npm run check:faq                   # 새 기능 공지에 FAQ 연결이 비었으면 종료 코드 1
> npm run check:release-notes -- --soft # 보고만
> ```
>
> 이 스크립트는 `releaseNotes.json`을 마지막으로 건드린 커밋 이후의 **feat/fix 중 사용자
> 화면 경로를 건드린 것**을 나열한다. 알릴 내용이 아니면 그냥 넘어가면 된다 —
> 스크립트는 후보를 세지만 판단하지는 않는다.

## 2. 파일과 구조

**단일 원본**: `public/data/releaseNotes.json` (번들 크기 절감을 위해 `src/lib/releaseNotes.ts`가
런타임에 fetch한다 — 코드에 데이터를 넣지 않는다.)

```jsonc
[
  {
    "date": "2026-08-04",                    // 배포일 (YYYY-MM-DD). 최신이 배열 맨 앞
    "title": "…해요 🔄🧑‍🤝‍🧑",                  // 한 줄 요약 + 이모지 1~2개
    "items": [
      { "type": "new",      "text": "…" },   // 새 기능
      { "type": "improved", "text": "…" },   // 기존 기능 개선
      { "type": "fixed",    "text": "…" }    // 버그 수정
    ]
  }
]
```

- `type`은 **세 가지뿐**이다(`new` / `improved` / `fixed`). 타입 정의는
  [src/lib/releaseNotes.ts](../../../src/lib/releaseNotes.ts)의 `ReleaseItem`.
- **날짜 하나에 항목 여러 개**를 담는다. 같은 배포에 나간 것은 한 항목씩 쪼개지 말고 한 날짜로 묶는다.
- 이미 배포됐지만 공지를 빠뜨린 건은 **오늘 날짜로** 적는다(사용자가 보는 날이 기준이다).
- JSON이므로 마지막 요소 뒤 쉼표·주석 금지. 편집 후 반드시 파싱을 확인한다.

## 3. 문체

FAQ와 같은 톤이다([update-faq](../update-faq/SKILL.md) §1 참고) — 사회복지기관 실무자가 읽는다.

- **해요체**: "~할 수 있어요", "~고쳤어요", "~해 주세요"
- **무엇이 달라졌는지 → 어떻게 쓰는지 → 주의점** 순서
- 경로는 대괄호로: `[설정] → [기능 사용 설정] → [동승자]`
- 주의·예외는 `⚠️`로 시작하는 문장으로 뒤에 붙인다
- 이모지는 제목에 1~2개, 본문에는 필요할 때만

### 쓰지 않는 말

내부 용어를 그대로 옮기지 않는다. 사용자는 코드를 모른다.

| 쓰지 말 것 | 이렇게 |
|---|---|
| `recurringGroupId`, 콜러블, 트랜잭션 | "반복 예약", "저장", (아예 생략) |
| "핸들러에서 undefined가 저장돼" | "저장이 실패하던 문제" |
| "Rules의 delete 권한을 열었습니다" | "관리자도 수정할 수 있어요" |
| PR 번호·커밋 해시 | 적지 않는다 (개발 이력에만) |

## 4. 반드시 적어야 하는 것

- **기관이 켜야 보이는 기능**이면 그 사실과 켜는 경로. 켜지 않으면 아무 변화가 없는 기능은
  그 사실이 공지의 핵심이다. (예: "기본은 꺼져 있어요 — [설정] → … 에서 켜면 …")
- **재동의·재로그인·앱 재실행이 필요하면** 그 안내. 사용자가 겪게 되는 불편은 미리 밝힌다.
- **되돌릴 수 없는 동작**이면 무엇이 사라지는지. (예: "나머지 회차는 취소됩니다")
- **이미 저장된 데이터에는 적용되지 않는 수정**이면 그 한계. (예: "이미 저장된 기록은
  그대로 남습니다 — 접속기록은 나중에 바꿀 수 없도록 만들어져 있어서예요.")

## 5. 왜 그렇게 했는지 한 줄

기능 설명만 있으면 "왜 이렇게 바뀌었나"라는 문의가 따라온다. 판단의 이유를 한 줄 덧붙인다.

> "예약 목록에는 이름 대신 '👥 3명'처럼 인원수만 표시해요."
> → 이유를 덧붙이면: "예약은 기관 전체가 보는 화면이라 이름은 수정 화면에서만 보여요."

## 6. 절차

1. `npm run check:release-notes -- --soft`로 후보 확인
2. `public/data/releaseNotes.json` **맨 앞**에 오늘 날짜 항목 추가 (기존 항목은 건드리지 않는다)
3. 같은 배포에 FAQ·사용 설명서 변경이 필요한지 확인 → 필요하면 [update-faq](../update-faq/SKILL.md)
4. `npm run check:release-notes`로 게이트 통과 확인
5. 커밋은 `chore:` — 구현이력 Phase 기록과 함께 묶는 것이 관례다
   (예: `chore: 구현이력 Phase 143~145 기록 + 업데이트 소식 갱신 — …`)

## 7. 검증

- JSON 파싱: `node -e "JSON.parse(require('fs').readFileSync('public/data/releaseNotes.json','utf8'))"`
- 화면 확인: 로그인 후 [더보기] → [업데이트 소식], 공개 페이지 `/release-notes`
- 최신 항목의 날짜가 바뀌면 **사용자에게 새 소식 배너가 뜬다**(`useReleaseNotesStatus`).
  날짜를 잘못 넣으면 배너가 안 뜨거나 이미 읽은 소식이 다시 뜬다.
