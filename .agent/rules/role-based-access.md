# 역할 기반 접근 권한 (RBAC) 검증 원칙

차량운행일지는 일반 '운전자'부터 렌트카 업체 성격인 '조직 관리자(최고관리자)'까지 섞여 있는 멀티테넌트(Multi-tenant) 성격의 앱입니다. 
보안과 UX 혼동을 막기 위해 모든 개발과 에이전트의 작업 시 다음 원칙을 따르세요.

## 핵심 규칙

### 1. 클라이언트(React) 상 노출 분리
- **슈퍼관리자 (Role: `superAdmin`) / 기관관리자 (Role: `admin`)**: 관리자 대시보드 접근 활성화, 멤버 승인/거절, 차량 데이터 삭제 등의 버튼이 렌더링 되어야 합니다.
- **일반 직원 (Role: `employee`)**: 관리자 페이지 진입 버튼, 타인의 승인 내역, 설정 변경 탭은 보이지 않아야(hidden) 합니다.
- 컴포넌트 레벨에서는 `useAuth` 훅 등에서 권한 상태를 받아 **조건부 렌더링** (`{isAdmin && <AdminButton />}`) 으로 접근을 막습니다.

### 2. 백엔드(Firestore / Functions) 상 권한 검증 필수
- **프론트에서 버튼을 가렸다고 안전한 것이 아닙니다.** 누군가 API나 브라우저 콘솔에서 우회 요청할 수 있으므로, **Firebase Security Rules**와 **Cloud Functions** 내부 로직에서는 요청자의 role이 `admin` 또는 `superAdmin`인지 재확인해야 합니다.
- **라우터 가드(`AuthGuard`, `ProtectedRoute`)·조건부 렌더링도 전부 "프론트엔드"다.** 페이지 자체가 admin 라우트 뒤에 있어 "직원에겐 안 보인다"는 것은 *노출 분리(§1)*일 뿐, 권한 보장이 아니다. 라우팅으로 가려졌다는 이유로 백엔드 재검증을 생략하지 않는다.
- **권한성 *변이*는 동사로 판단하지 않는다.** `delete`/`삭제`처럼 익숙한 파괴적 동작뿐 아니라 **승인·거절·상태변경·역할부여 등 워크플로우로 포장된 모든 변이**가 대상이다. 이런 변이를 구현하거나 버튼을 붙일 때는, 그 변이가 닿는 **컬렉션·동작의 백엔드 규칙(Rules) 또는 Function이 요청자 role을 실제로 막고 있는지 직접 확인**하고, 막고 있지 않으면 추가한다(확인 없이 "이미 안전하겠지"로 넘기지 않는다).
- Cloud Function 코드 예시:
  ```typescript
  if (context.auth?.token.role !== 'admin' && context.auth?.token.role !== 'superAdmin') {
      throw new HttpsError("permission-denied", "관리자만 접근할 수 있습니다.");
  }
  ```

### 3. 방어적 코딩 (Defensive Coding)
- '권한이 없는 유저'가 해당 권한이 필요한 페이지 진입(직접 URL 타격 등) 시 에러 화면에서 무한 루프에 빠지거나 멈추지 않고, **"접근 권한이 없습니다"**라는 스낵바와 함께 메인 페이지(`/`)로 자연스럽게 리다이렉트(`useNavigate('/')`) 하도록 라우터 가드(Router Guard, 예: `ProtectedRoute.tsx`)를 세심하게 처리합니다.

### 4. 외부 식별자는 서버가 소유를 검증한 뒤에만 신뢰한다

§2는 "요청자가 누구인가"를 서버가 다시 확인하라는 규칙이다. 이 항목은 그 짝이다 — **"요청이 가리키는 대상이 정말 그 기관 것인가"** 도 서버가 확인해야 한다.

이 앱의 테넌트 경계는 `organizationId`·커스텀 클레임으로 서버가 판정한다. 그런데 **외부 시스템의 식별자**(구글 캘린더 ID, Slack 팀 ID, 외부 문서·파일 경로 등)는 클라이언트가 적어 넣고, 형식 검사만 통과하면 서버가 그대로 외부 API에 넘기기 쉽다. 그러면 그 문자열 하나가 테넌트 경계를 대신하게 된다 — Rules를 아무리 조여도 이 경로는 Rules 밖(Admin SDK + 외부 API)에서 일어난다.

- **공용 자격증명 + 클라이언트가 정한 대상 = 교차 테넌트 통로다.** 모든 기관이 같은 서비스 계정에 자기 리소스를 공유하는 구조라면, 그 서비스 계정에게는 전 기관의 리소스가 열려 있다. 남의 식별자를 적어 넣으면 남의 데이터가 유입되고(유출), 우리 쪽 삭제가 남의 원본을 지운다(무결성). 실제로 캘린더 연동이 그랬다 — [2026-08-23 감사 발견 1](../../docs/security-reports/2026-08-23.md).
- **바인딩 정본은 서버가 소유한다.** 식별자 → 기관 매핑을 서버 전용 컬렉션에 두고(`calendarBindings`, Rules에서 `read, write: if false`), 사용 시점에 그 정본과 대조한다. 클라이언트가 쓸 수 있으면 정본이 다시 클라이언트 입력이 되어 의미가 없다.
- **검사는 외부 API 호출 앞에 둔다.** 요청을 보낸 뒤 판정하면 유출·쿼터 소모가 이미 일어난다.
- **판정 불가는 막는다(fail-closed).** 바인딩 조회가 실패했을 때 열어 두면 장애가 곧 유출 창구가 된다. 부가 기능은 멈춰도 되지만 경계는 열려선 안 된다.
- **진단 도구는 선점하지 않는다.** "이 식별자에 접근되나?"를 알려주는 경로는 등록까지 하지 말고 읽기만 한다 — 진단이 선점하면 아직 연동하지 않은 기관의 식별자를 남이 버튼 몇 번으로 차지해 그 기관의 연동을 영구히 막을 수 있다. 그리고 그런 응답 자체가 후보를 훑는 오라클이므로 호출 상한을 함께 건다.
- **바인딩을 새로 도입할 때는 기존 데이터를 먼저 시딩한다.** 선점 등록만 켜면, 아직 그 기능을 쓰지 않은 기존 기관의 식별자가 선점 대상으로 열린 채 남는다(`scripts/seed-calendar-bindings.ts`가 선례).

구현 참고: [functions/src/services/calendar/calendarBinding.ts](../../functions/src/services/calendar/calendarBinding.ts), 회귀 고정: `functions/src/__tests__/calendarBinding.test.ts`.
